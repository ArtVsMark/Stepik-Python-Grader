# Гейты: перед пушем и перед мержем

Канон двух команд, которые заменяют «не забыть» на «проверено машиной»:

```bash
python scripts/preflight.py            # перед коммитом и пушем
python scripts/check_pr_ready.py 1100  # перед мержем PR
```

Документ отвечает на три вопроса: **зачем гейт вообще** (иначе он воспринимается
как лишний шаг и обходится), **что именно он проверяет** и **что делать, когда
он красный**. Компактный триггер — в [`../../CLAUDE.md`](../../CLAUDE.md);
детали не дублировать там.

---

## Почему не «ещё один пункт в чек-листе»

Разбор сессии 2026-08-13 дал одиннадцать инцидентов. Существенно
здесь то, что **девять из них — не незнание правила, а его пропуск**: правило
«прогонять ВЕСЬ набор» уже было в `CLAUDE.md`, когда профильная выборка молча
сломала чужой тест; правило «ветвиться от свежего main» — тоже, когда гейт
прогнали на устаревшей ветке и `main` покраснел после мержа.

Отсюда принцип, по которому здесь всё устроено:

> **Правило, которое надо вспомнить, соблюдается ровно до первой спешки.
> Правило, которое проверяет команда, соблюдается всегда.**

Поэтому текст чек-листа переписан в код, а не дополнен ещё одним пунктом.
Каждая проверка ниже названа вместе с инцидентом, из которого выросла: правило
без причины выглядит формальностью, и его первым обходят.

## `preflight.py` — перед пушем

| Проверка | Инцидент, из которого выросла |
|---|---|
| ветка не `main` | прямые коммиты в `main` запрещены контрактом |
| **ветка от свежего `origin/main`** | гейт прогнали на ветке, созданной до чужого мержа: локально 18 passed, на `main` красные все девять ubuntu-джобов. «Зелено на моей ветке» ≠ «зелено после мержа» |
| **имя ветки не занято** | дважды взята работа соседнего окна; во второй раз совпало и имя ветки — `push` отлетел «tip is behind», а правка чуть не уехала в чужой PR |
| пересечение файлов с чужими ветками | общие файлы расходятся конфликтами, и узнаётся это в момент мержа (`check_work_overlap.py`) |
| **запись о изменении** | требуется в каждом PR, но CI её наличие не проверяет — держалась на памяти и чек-листе. Принимается фрагмент `changelog.d/<slug>.<секция>.md` (основная форма) либо строка в `## Буфер` — чтобы ветки, начатые до перехода на фрагменты, не краснели на ровном месте |
| карта «кто ссылается на правку» | тестовый файл искали по угаданному имени, не нашли, положили тесты в другой файл — и молча сломали `test_loader.py`. `grep` по имени функции ищет тех, кто патчит наши имена |
| один прогон за раз (`.git/preflight.lock`) | два параллельных `pytest` исчерпали дескрипторы: 72 «падения», все средовые (`OSError WinError 6/50` в тестах с subprocess). Полдня разбора регрессии, которой нет |
| весь набор + **вывод целиком в файл** | `pytest … \| tail -8` в фоне отбросил всё, кроме хвоста, и шестиминутный прогон пришлось повторять. Скрипт всегда пишет полный лог в `.git/preflight-logs/` |
| `ruff check` · `ruff format` · `mypy` | зеркалит CI, чтобы красное находилось до пуша, а не в матрице |

Режимы:

```bash
python scripts/preflight.py                # всё, включая полный pytest
python scripts/preflight.py --branch-only  # только гигиена ветки — ДО начала работы
python scripts/preflight.py --no-tests     # правки только в докáх
python scripts/preflight.py --force-lock   # перехватить протухшую блокировку
python scripts/preflight.py --install-hook # pre-push хук, отклоняющий непроверенный коммит
```

`--branch-only` дешёвый и запускается **до** работы, а не после: он отвечает на
вопрос «эту задачу уже кто-то делает?» тогда, когда ответ ещё что-то меняет.

### Штамп и pre-push хук

Удачный прогон пишет `.git/preflight-stamp.json` с **отпечатком содержимого**
рабочего дерева — отслеживаемые файлы плюс новые, ещё не добавленные в индекс.
Хук (`--install-hook`) сравнивает отпечаток с текущим и отклоняет пуш, если
уехать собирается **не то состояние, которое проверяли**.

Привязка к содержимому, а не к `HEAD`, — не тонкость, а исправленный дефект
первого же живого применения: прогон всегда идёт **до** коммита, поэтому штамп
на SHA обесценивался ближайшим `git commit`, и хук отклонял пуш ровно того
состояния, которое сам же и проверил. Гейт, который мешает при правильном
порядке действий, обходят на второй день.

Аварийный выход — `PREFLIGHT_SKIP=1 git push …`: он существует для срочного
фикса там, где прогон физически негде сделать, и остаётся осознанным решением
человека, а не значением по умолчанию.

## `check_pr_ready.py` — перед мержем

Инцидент: PR смержили, когда **9 проверок из 14 были `queued`/`in_progress`**.
Проверка звучала разумно — «нет `failure` и нет `pending` → мержим», — но сразу
после `git push` GitHub ещё не успевает создать check-runs, и REST отдаёт
**пустой список**. На пустоте это условие выполняется идеально.

Три правила, закодированные в скрипте:

1. **Пустой или неполный список проверок — «CI не стартовал», а не «зелено».**
   Поэтому смотрится не только `/commits/{sha}/check-runs`, но и
   `/actions/runs?head_sha=…`: пока прогон в `queued`/`in_progress`, часть
   джобов ещё не существует, и судить по ним нельзя.
2. **Набор сверяется с эталоном** — джобами тех прогонов последнего коммита
   `main`, чей workflow объявляет триггер `pull_request`. Эталон живой, а не
   константа в коде: список джобов меняется вместе с `ci.yml`, и зашитое число
   устарело бы молча. Фильтр по триггеру обязателен: на `main` есть прогоны от
   workflow с `issue_comment`/`workflow_dispatch`, которых на PR не бывает
   никогда, и без фильтра гейт краснел бы всегда — а гейт, который краснеет
   всегда, обходят.
3. **Только REST.** `gh pr view` / `gh pr checks` ходят через GraphQL, и поллинг
   в цикле выжигает квоту 5000/час до нуля — посреди работы `gh` просто
   перестаёт отвечать, со сбросом через полчаса. Опрашивать не чаще, чем раз в
   45–60 секунд.

```bash
python scripts/check_pr_ready.py 1100          # вердикт: 0 — можно мержить
python scripts/check_pr_ready.py 1100 --json   # то же машинно
```

Транспорт: `gh api` (локальное окно, где `gh` уже авторизован), иначе прямой
REST с `GH_TOKEN`/`GITHUB_TOKEN` из окружения.

## Очередь мержа: что за чем

Открытых PR обычно несколько, и они **не независимы**: каждый мерж в `main`
отбрасывает остальные назад.

Главный источник конфликтов убран — записи релиза теперь **файлами**
(`changelog.d/<slug>.<секция>.md`), а не строками в общем `CHANGELOG.md`. Причина
перехода: `merge=union` из `.gitattributes` спасает **только локально** —
проверено дважды, `git merge origin/main` сливал буфер без вмешательства ровно
тогда, когда GitHub уже помечал тот же PR `mergeable_state=dirty`. Полагаться на
union при мерже через GitHub нельзя, а два файла с разными именами не
конфликтуют по построению.

Отсюда диагностический признак, который иначе читается как «CI сломался»:

> **Конфликт = проверок нет вовсе.** Прогон на PR идёт по merge-коммиту; если
> слияние невозможно, GitHub его не строит, и check-runs не создаются. Пустой
> список проверок при `dirty` означает «сначала разведи конфликт», а не «CI не
> запустился».

Порядок:

1. **Первым — то, что чинит красный `main`.** Пока база красная, все остальные
   PR красные тоже, и их проверки ничего не говорят о них самих.
2. **Затем — PR, который держит общий файл.** Кто пересекается, показывает
   `python scripts/check_work_overlap.py`; мержится первым тот, чью правку
   остальным придётся учитывать.
3. **Остальные — по готовности** (`check_pr_ready.py` → «готов»).

**После каждого мержа оставшиеся PR обновляются из `main`** — `git fetch origin
main && git merge origin/main`, затем push (или кнопка «Update branch», если
ветка своя). Без этого они висят без проверок и выглядят «забытыми CI».

Практическое следствие: **снятие черновика перезапускает прогон с нуля** — все
проверки создаются заново, и ждать их приходится второй раз. Поэтому черновик
снимается **сразу после создания PR**, а не когда прогон уже позеленел;
«сниму перед мержем» звучит аккуратно, а стоит лишнего круга ожидания, за
который соседний мерж успевает сделать ваш PR `dirty`.

## Квота GitHub API: дорого не `gh`, а GraphQL

Прежнее правило называло команду — `gh pr view`/`gh pr checks` — и потому не
сработало, когда квоту выжгло другое. Замер в момент исчерпания:

```json
"core":    { "limit": 5000, "remaining": 4998, "used": 2 },
"graphql": { "limit": 5000, "remaining": 0,    "used": 10724 },
"search":  { "limit": 30,   "remaining": 30,   "used": 0 }
```

REST — **2 запроса из 5000**. Search — ноль. GraphQL — **10 724 при лимите
5000**, перерасход вдвое. При этом `gh pr view` не вызывался ни разу: в облачном
окне `gh` нет вовсе, и правило, написанное про него, читалось как «меня не
касается». Отсюда переформулировка по механизму:

- **Через GraphQL идёт почти всё, чем работает агент** — списки issue и PR,
  чтение issue/PR, поиск, правка PR. Признак — курсорная пагинация (`pageInfo`,
  `endCursor`) в контракте инструмента. Имя команды тут ни при чём.
- **Лимит GraphQL — 5000 *points* в час, а не 5000 запросов.** Один вызов,
  тянущий три десятка issue со всеми полями, стоит сотни. «Пять тысяч
  обращений» — иллюзия, до неё не доживают.
- **Кастомные поля стоят отдельно.** Семантический поиск issue подтягивает
  значения полей Projects на каждый результат; ошибка при исчерпании была
  буквально `failed to fetch issue field values`.
- **Гейты ходят через REST, и это правильно.** `check_pr_ready.py` через
  `gh api` — 2 запроса из 5000. Не «оптимизировать» его на GraphQL.

**Одни операции над PR идут по REST, другие — по GraphQL, и это видно на
практике.** При обнулённом GraphQL создание PR проходит, а снятие черновика —
нет. Практическое следствие: **создавать PR сразу не-черновиком**; тогда
GraphQL-вызов не нужен вовсе, и заодно не тратится круг ожидания на перезапуск
проверок (см. выше про снятие черновика).

### Практики экономии

- Не проверять дубли поиском на каждый заводимый issue: хватает **одного**
  списка открытых issue в начале работы, с полями `number, title`.
- Запрашивать минимальный набор полей — без `body` и `field_values` там, где они
  не нужны.
- Брать небольшие страницы.
- Не перечитывать в одной сессии то, что уже прочитано.

### Исчерпав квоту — остановиться, а не повторять

Счётчик продолжает расти после нуля: 10 724 против лимита 5000 — ровно этот
случай, вызовы шли дальше и дальше считались. Повтор не «пробует ещё раз», он
отодвигает сброс.

**Квота общая на аккаунт.** Работают три окна — расход складывается, и интервалы
опроса увеличиваются кратно числу окон.

### Диагностика — первым шагом, а не после часа догадок

```bash
gh api rate_limit --jq '.resources | {core, search, graphql}'   # локальное окно
```

В облачном окне `gh` нет — тот же ответ берётся напрямую:

```bash
curl -sS -H "Authorization: Bearer $GH_TOKEN" https://api.github.com/rate_limit
```

Три кошелька видно раздельно: остаток и время сброса. По времени сброса понятно
и то, когда началось окно, — то есть кто его тратил.

### Окно-наблюдатель за PR

Наблюдение в цикле — самый дорогой режим работы с API, и именно ему нужны явные
требования.

- **Событие вместо опроса.** Если среда даёт подписку на активность PR
  (`subscribe_pr_activity`), наблюдатель обязан использовать её: события
  приходят без единого запроса. В агентской сессии подписка включается
  автоматически при создании PR — падения CI и комментарии ревью приезжают
  сами. Опрос — резервный вариант, а не основной.
- **Опрос — только по REST**: `/repos/{owner}/{repo}/pulls`, `.../commits`,
  `.../status`. GraphQL в цикле запрещён.
- **Условные запросы (`ETag` / `If-None-Match`).** Ответ `304 Not Modified`
  **не расходует лимит**: пока в PR ничего не менялось, опрос бесплатен. У
  GraphQL такого механизма нет — ещё одна причина не водить его в цикл.
- **Дельта вместо полного обхода.** Список PR с сортировкой по `updated`;
  внутрь заходить только к тем, у кого `updated_at` изменился с прошлого
  прохода. Иначе шесть открытых PR дают 7+ вызовов за проход, а раз в минуту —
  под тысячу вызовов в час.
- **Интервал наблюдателя — минуты, а не секунды**, и он растёт с каждым
  дополнительным активным окном.

CI сюда не относится: там свой `GITHUB_TOKEN` с отдельным лимитом, и
единственный API-скрипт в workflow делает один вызов за прогон.

## Что гейты не ловят — и почему это записано здесь

Три инцидента той же сессии механической проверке не поддаются; они остаются
правилами, но названы явно, чтобы не выглядели «и так понятно»:

- **Пуш в ветку чужого PR.** Конфликт локалей выглядел тривиальным («оставить
  обе строки»), и правку внесли прямо в ветку соседнего окна. Гейт видит только
  совпадение имени ветки, а не намерение. Правило: **в чужую ветку не пушить** —
  сообщить владельцу, что и как разрешать.
- **Escape-последовательности через bash-heredoc.** `\n` внутри Python-строки,
  записанной heredoc'ом, дважды превращался в настоящий перевод строки →
  `SyntaxError: unterminated string literal`. Правило: код с экранированием
  писать **файлом**, а не heredoc'ом.
- **«Тест краснеет до фикса», доказанное откатом всего `src/`.** Тесты падали на
  `ImportError` — то есть доказано лишь «тест ссылается на новый код». Правило:
  краснота проверяется **полу-откатом** — новые имена оставить, убрать только
  поведение.

## Порядок работы целиком

```
1. python scripts/preflight.py --branch-only   # до работы: чужая ли это задача, свободно ли имя
2. … правки, тесты …
3. python scripts/preflight.py                 # перед коммитом: весь набор + линтеры + типы
4. git push -u origin <branch>                 # хук пропустит только проверенный коммит
5. python scripts/check_pr_ready.py <PR>       # перед мержем: набор полон, всё зелёное
```

Связанное: [`environments.md`](environments.md) — что из этого вообще выполнимо
в облачном окне, а что только на локальной машине;
[`../../CONTRIBUTING.md`](../../CONTRIBUTING.md) § «Когда дефект считается
исправленным» — критерий приёмки фикса.
