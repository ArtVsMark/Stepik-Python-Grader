# Факты проекта для соседних репозиториев

> **Контракт публикации.** Соседним проектам нужны наши числа. Раньше они
> считали их у себя; здесь описано, как получать их у нас — без клона,
> без токена и без знания нашего устройства.

## Зачем это заведено

Витрина [`ArtVsMark/ArtVsMark`](https://github.com/ArtVsMark/ArtVsMark) брала
числа так: клонировала грейдер **целиком** ради двух подсчётов по `tests/`,
разбирала наш `.github/workflows/ci.yml` регулярным выражением и оценивала
число проверок на PR **медианой по семи последним** смерженным PR.

Цена такого способа — не расход, а связанность. Знание о том, где лежат наши
тесты и как устроена наша матрица, жило в **чужом** репозитории: перенесём
каталог — у соседа молча изменится число, а не сломается сборка. Медиана же
существовала ровно потому, что снаружи точного ответа не видно, — тогда как
внутри он есть: тот же набор проверок считает `check_pr_ready.py` для
собственного мерж-гейта.

Приём тот же, что у [каталога правил](https://github.com/ArtVsMark/Engineering-Incidents-Playbook)
в его контракте потребления: **издатель считает, потребитель читает**.

## Где лежит

Ветка **`badges`**, файл `.github/badges/facts.json`. Собирает
`scripts/generate_facts.py` тем же шагом прогона, что и бейджи, и едет он тем
же копированием — новой трубы не потребовалось.

**Почему не в `main`.** Числа пересобираются на каждом пуше, то есть чаще, чем
идут изменения. Производное с такой частотой в общей ветке не хранят: оно
превращает каждое слияние в конфликт и красит ветку сдвигом числа, а не
поломкой. В `main` файла нет — он в `.gitignore`.

**Как читать.** Тем же способом, каким витрина уже читает наши бейджи, —
contents-API GitHub по ветке `badges`. Через `raw.githubusercontent.com`
запрос с заголовком `Authorization` отвечает `404`: токен для raw чужой, и
вместо содержимого приходит «нет такого файла».

## Поля

| Поле | Что это |
|---|---|
| `schema` | версия **формата этого файла** — не версия проекта и не его выпуск |
| `repo` | чьи это факты |
| `generated_at` | когда собраны |
| `commit` | состояние, по которому посчитано; ключа нет — git был недоступен |
| `tests.functions` | число `def test_` во всём дереве `tests/` |
| `tests.modules` | число файлов `test_*.py`; `conftest` и хелперы модулями не считаются |
| `python.supported` | версии из матрицы, блокирующие мерж |
| `python.experimental` | версии под `continue-on-error`; в правилах ветки их нет по устройству |
| `checks_per_pr.count` | сколько РАЗНЫХ проверок создаётся на pull request |
| `checks_per_pr.names` | их имена — эталонный набор, которым мерж-гейт сверяет полноту |
| `coverage_percent` | суммарное cross-OS покрытие числом; ключа нет — данные были неполны (см. ниже) |
| `rules.total` | сколько правил каталога заведено в нашем `.rules/bindings.json` |
| `rules.<чем держится>` | доли по механизму: `gate`, `pipeline`, `document`, `none`, а для неактивных — их статус (`not_applicable`, `rejected`) |

**Доли правил считаются, а не перечисляются.** Ключи `rules` выводятся из
самого `bindings.json` подсчётом: словарь механизмов ведёт каталог, и он
растёт — за две недели к четырём долям добавилась пятая. Жёсткий список в коде
отстал бы молча, показав старую картину как полную. По той же причине числа
берутся из своего файла, а не из сводки каталога (`badges/export/where.json`):
та — ответ каталога **о нас**, а здесь проект отвечает **о себе**, и у этих
ответов разные владельцы и разный срок жизни.

**`schema` называет, чего он версия, — и это не формальность.** Номера разного
назначения, названные одним словом, разъезжаются по чужим полям: у каталога
правил их четыре (формат выгрузки, формат сводки, версия ответа потребителя,
выпуск), и сосед уже записал один из них в поле другого — обе стороны при этом
остались формально валидными.

**Ключа нет — значит не измеряли.** `checks_per_pr` требует обращения к
площадке, и при отказе ключ **отсутствует**, а не выставляется нулём: ноль
читался бы как «проверок на PR не создаётся», то есть точной ложью. Тот же
приём, что у `portable` в контракте каталога правил.

**`tests.functions` — не число собранных тестов.** Считаются определения
`def test_`; параметризация умножает их при сборе, и прогон рапортует заметно
большее число. Оба числа честные, но отвечают на разные вопросы: сколько
написано против сколько выполняется.

**`coverage_percent` появляется только при полных данных.** Отчёт
`coverage.xml` пишется и после деградации (`coverage xml` выполняется в любом
случае), поэтому наличие файла признаком не является: судит о полноте прогон,
он же решает, звать ли `generate_facts.py` с `--coverage-xml`. Недосчитанное
число было бы не пробелом, а точной ложью — то же основание, по которому при
деградации не публикуется и комбинированный бейдж.

## Чего здесь нет

**Покрытие здесь было в списке «чего нет» — и перестало.** Довод звучал так:
оно уже публикуется бейджами в той же ветке, и второй источник тех же данных
заводить незачем. Довод оказался про **хранение**, а вопрос был про
**потребление**: значок показывает число человеку, а сравнивает его витрина, и
ей приходилось вычитывать цифру из поля `message` — то есть разбирать чужое
оформление ради содержания. Бейджи остались на месте, они никуда не делись:
это разные потребители одного числа.

**Обязательных проверок ветки** — они читаются у площадки любым, кто видит
репозиторий (`/repos/{repo}/rules/branches/main`), и посредник тут не нужен.
`checks_per_pr` отвечает на другой вопрос: сколько проверок вообще создаётся,
а не сколько из них блокируют мерж.
