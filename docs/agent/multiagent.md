# Мультиагентный режим: волнами по 5

Правила для **любой** массовой работы агентами, не только для аудитов: сквозные
правки документации или кода, генерация контента, разбор находок, миграции,
исследование в несколько срезов. В [`../../CLAUDE.md`](../../CLAUDE.md) — только
компактный триггер; канон здесь.

---

## Главное правило

**Волна = ровно 5 агентов. Одна волна = отдельный вызов Workflow.**

Не залпом — даже когда включён режим ultracode и «токены не ограничение». Правило
про **надёжность**, а не про экономию: большой залп сам себе создаёт отказ, и чем
он больше, тем дороже потеря.

```
❌ 40 агентов сразу  → перегрузка API (503/529 → Connection closed):
                       упало 13 из 32
❌ 29 агентов сразу  → лимит сессии + каскад 403 Failed to authenticate:
                       упало 20 из 29, 1.34M токенов ради 9 результатов
❌ 24 агента сразу   → остановлено вручную владельцем до первого результата
✅ 5 агентов → разбор → следующие 5
```

Почему именно отдельный вызов на волну, а не один скрипт с барьерами по 5: при
остановке такой скрипт уносит и невыполненные волны. Отдельный запуск даёт
чекпоинт и точку решения между волнами.

---

## Агенты возвращают данные — файлы правит хост

Агент **не редактирует файлы**. Он читает, анализирует и возвращает
структурированный результат через `agent(schema=...)`; применяет его
детерминированный код на стороне хоста.

Что это даёт:

- **нет гонок за файлы** — параллельные агенты не пишут в одно место;
- **результат проверяется до записи** — невалидное предложение просто не
  применяется;
- **потеря агента дешёвая** — упавший агент не оставляет полуправку в рабочем
  дереве.

Пример формата для сквозной правки текста: агент возвращает
`[{old_string, new_string, why}]`, хост проверяет уникальность каждого
`old_string` в файле и применяет; неуникальные и ненайденные — в отчёт, не в
файл.

## Разбор после КАЖДОЙ волны

Следующая волна запускается только после разбора предыдущей. По двум осям, и
вторая важнее первой.

**1. Механика.** Кто упал и почему. Добрать дельту до полного комплекта волны.

**2. Качество.** **Прочитать выборку реального результата** и сверить с
заданием: не пересказ ли это того, что уже было; нет ли запрещённой разметки; не
вода ли; верны ли факты. Считать одни успехи недостаточно — пять «успешных»
агентов способны выдать связный мусор, и на четырёх волнах это обнаруживается в
самом конце, когда испорчены уже сотни единиц контента.

Выборка не прошла — сначала правится промпт, только потом перезапуск.

## Рестарт только дельты

Собрать готовое из журнала → вычислить, чего реально нет → запустить точечно
недостающее. **Никогда** не перезапускать волну целиком ради пары упавших.

**`journal.jsonl` — источник истины, а не возврат Workflow.** Возврат показывает
`null` там, где в журнале лежит готовый результат: журнал append-only и переживает
падение. Сверяйся с журналом ПЕРЕД выводом «агент потерян» — на прошлых волнах
это спасло 11 готовых срезов и 103 карточки из 155.

## Дополнительно для аудитов

- **`file:line` + репро** у каждой находки — обязательно.
- **Адверсариальный верификатор** с установкой «опровергай по умолчанию»,
  отдельным агентом. На аудите v1.9.0 отсеял 7 находок из 32 как ложные.
- **Severity ставит верификатор**, а не автор находки (`corrected_severity`).
- **Критик полноты — последним.** Если после него дозапускались срезы, его вывод
  перечитывается заново.
- Результаты складываются в [`../audit/`](../audit/README.md) и уезжают в
  [`../archive/`](../archive/README.md), когда все находки закрыты или отклонены.

## Чек-лист перед запуском Workflow

```
[ ] В волне ровно 5 агентов (не 6, не 12)
[ ] Волна — отдельный вызов Workflow, без «барьеров по 5» внутри одного скрипта
[ ] У агентов есть schema; файлы они не правят — правит хост
[ ] Понятно, чем проверю качество выборки после волны
[ ] Знаю путь к journal.jsonl этого запуска
[ ] Прошлая волна разобрана по обеим осям
```
