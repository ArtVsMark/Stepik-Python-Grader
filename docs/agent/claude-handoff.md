# Очередь работ для Claude Code

> **Что это.** Порядок работ после крупного аудита: что за чем делать и почему
> именно в этом порядке. Заполняется, когда аудит выявил связанный пласт задач,
> который не выражается плоским списком issue (есть блокеры, «делать вместе»,
> «иначе фиксы недоказуемы»). Очищается, когда пласт разобран.
>
> **Чего здесь нет.** Отчётов «мы это сделали» — они в
> [`../CHANGELOG.md`](../../CHANGELOG.md). Критериев приёмки — они в самих GitHub
> issue. Списка открытых задач — он в `gh issue list` и устаревает за спринт,
> если продублировать сюда.

## Волна: входной слой вердикта (аудит 2026-08-10, эпик #915)

Порядок здесь задан **графом заражения**, а не тяжестью находок: стратегический
срез аудита показал, что девять `high` из шестнадцати опираются на состояние,
которое нигде не объявлено. Пока это так, любой фикс ниже по цепочке
недоказуем — прогон из другого каталога даёт другой ответ.

Подэпики и issue — в трекере под эпиком **#915**; здесь только порядок и
обоснование, которых в issue нет.

```
Ступень 1. Строгая загрузка набора кейсов — test_loader.py, mode_detector.py
  → прогонный корпус: пока вердикт неверен, эталон бессмыслен
  ⤳ снятие xfail в тестах формата 2

Ступень 2 (параллельно первой). Единый ключ задачи — history.py
  → «Прогресс», «Подучить», серия, бейджи — всё считает по этому ключу
  ✓ миграция схемы в одной транзакции: предпосылка, без неё замеры недостоверны
```

**Предпосылка снята: окружение прогона детерминировано** (#1009, #1011). Это
была первая ступень, и она стояла впереди не по тяжести — подтверждённых `high`
в ней не было, — а потому что репро остальных находок от неё зависело. Теперь
конфиг не подхватывается из чужих родительских каталогов, а вердикт из кэша
инвалидируется сменой условий исполнения, поэтому «починили ли мы загрузчик»
стало проверяемым утверждением. Escape-hatch (читать конфиг только из каталога
запуска) не понадобился: подъём ограничен маркером проекта, явный источник —
`--config`.

**Почему оставшийся порядок именно такой.**

- **Загрузчик первым из оставшегося:** девять подтверждённых `high` из
  шестнадцати — там, и теперь их репро воспроизводимо из любого каталога.
- **Ключ задачи ведётся параллельно:** общих файлов с загрузчиком нет, ребро
  только внутреннее — миграция схемы раньше всего, что считает агрегаты.
- **Вернувшиеся дефекты — не волна, а правило.** Их нельзя «сделать»: нужно
  закрывать каждую находку по грепу **всех** вызовов класса, а не одного места.
  Держится ревью, а не порядком в очереди. Свежий пример из закрытой ступени:
  третий вызов `GraderCache.get/put` жил вне `src/` — в стенде прогонного
  корпуса, и нашёлся только потому, что новый аргумент сделан обязательным.

**Вне цепочки, ведётся параллельно:** релиз и гейты CI, документы и витрины.
Общих файлов с ядром нет, блокировать нечего.

## Работы вне трекера

Не выражаются issue по природе:

- **архивация документа аудита — только когда закрыты ОБА эпика.** Основной
  собирает тяжёлые дефекты, эпик хвоста (#995) — остальные 870 находок по
  направлениям. Закрытие основного эпика **не является** основанием переносить
  `docs/audit/2026-08-10-full-roles.md` в `docs/archive/`: правило
  `docs/audit/README.md` требует, чтобы **каждая** находка была либо закрыта
  с номером PR, либо отклонена с причиной.

  Прецедент, ради которого это записано: аудит 2026-07-30 уехал в архив, когда
  закрылись все одиннадцать подэпиков его основного эпика. Ревизия четвёртой
  фазы вернулась к нему через полторы недели и нашла **десять живых дефектов**,
  числившихся исправленными, — в том числе `DIVE-02`, воспроизводящийся
  прогоном. Архив закрыл вопрос раньше, чем работа была сделана.

  Перед архивацией — проверить счётчиком: находок в документе без номера PR и
  без пометки об отклонении должно быть ноль.
- простановка номеров PR в документе аудита по мере закрытия находок — сейчас
  у 870 находок состояние «открыта» и ни одного номера;
- проверка каждого **нового** guard'а на пустом входе: класс «зелёный, когда
  проверять нечего» пойман в трёх местах и вернётся, если не проверять;
- следующий аудит обязан включить зоной **код, дописанный по находкам этого
  аудита**: ревизия показала, что именно он остаётся непроверенным.

Разбор пластов прошлого аудита (где ребро оправдалось, где нет) —
[`../archive/claude-handoff-2026-07-30.md`](../archive/claude-handoff-2026-07-30.md).

## Как заполнять после аудита

1. **Только связанные пласты.** Одна волна = одна причина держать порядок:
   общий файл, жёсткий блокер, «без этого фикс недоказуем». Плоский список
   независимых задач — в issue, не сюда.
2. **Формат волны:** заголовок с целью и релизом, под ним issue с пометкой типа
   ребра — `→` жёсткий блокер, `⤳` мягкий порядок (ради минимума переделок),
   `✓` предпосылка выполнена.
3. **Обоснование, а не пересказ issue.** Пишется то, чего в issue нет: почему
   этот порядок, что сломается при другом, где escape-hatch, если задача
   буксует.
4. **Проверки по фактическому коду.** Если аудит расходится с кодом (объём
   меньше заявленного, блокер уже снят) — фиксируй это здесь: план должен
   опираться на репозиторий, а не на текст issue.

## Как чистить по завершении

Волна разобрана — её запись **удаляется**, а не помечается «✅ выполнена».
Пометки о сделанном превращают доску очереди в журнал: именно так прежняя
редакция этого файла выросла до 336 строк отчётов о закрытых волнах. Если
разбор волны представляет исторический интерес, целиком перенеси её в
[`archive/`](../archive/README.md) отдельным файлом и оставь здесь пустое
состояние, как выше.

## Где выполнять: облачная сессия или локальная машина

Раздел постоянный — не удаляется вместе с очередью. Проверено фактами окружения
12.08.2026; если политика сети или образ изменятся, перепроверить и обновить.

**Можно делать в облачной сессии (почти всё):**

| Работа | Чем проверено |
|---|---|
| Код, тесты, `ruff`, `mypy`, покрытие | обычный прогон |
| **Linux-песочница** (`--sandbox`) | `bwrap` есть в `/usr/bin` — находки SBX получены прогоном |
| **Веб в реальном браузере** | Chromium в `/opt/pw-browsers`, Playwright из группы `e2e` |
| Python 3.12 и 3.13 | оба в системе; venv на 3.12 |
| GitHub: issue, PR, ревью, метки | MCP-инструменты |

**Только через CI, а не руками — и это нормально:**

Вторая и третья ОС. Матрица `ci.yml` — ubuntu + windows + macos × 3.12/3.13/3.14.
Правильная постановка задачи звучит не «прогнать песочницу на macOS», а
**«написать тест, который CI прогонит на macOS»**: сейчас `sandbox-linux` покрыт
отдельным job'ом, а паритетного набора для Windows и macOS нет. Пишется отсюда.
Python 3.14 в облачном образе отсутствует — тоже только через матрицу.

**Требует локальной машины владельца:**

| Работа | Почему |
|---|---|
| Скачивание задач, OAuth-флоу, `diagnostic_stepik` | `stepik.org` закрыт прокси (`CONNECT tunnel failed, 403`); с машины владельца отвечает `200` |
| Всё, что нужен **реальный** `secrets.json` | токен есть только у владельца, файл лежит рядом с проектом |
| GUI-лаунчер (`stepik-grader-gui`) | нет `DISPLAY`, `tkinter` не установлен — окно не открыть; локально `tkinter` 8.6 на месте |
| **Windows-специфика вживую** | Job-Objects-песочница, кодировка консоли, длинные пути: из облака это только матрица CI, а не наблюдение |
| **Python 3.14 руками** | в облачном образе его нет вовсе; локальный `.venv` — на 3.14 |

Пять сценариев из всего продукта. Если в окружении разрешить исходящие к
`stepik.org`, первые два уходят в облако; GUI, вторая ОС и 3.14 останутся
локальными.

**Чего, наоборот, нет на локальной машине владельца** (Windows): `bwrap` — то
есть Linux-песочница и находки `SBX` по ней проверяются только облаком или CI;
`watchfiles` (extra `[watch]`) не установлен, поэтому `--watch` там не
наблюдаем. Обратная асимметрия так же реальна, как прямая: «локально» не
значит «мощнее», значит «другое».

**Практический вывод для планирования.** Дели работу не по «сложности», а по
этой таблице: в облачное окно ставь всё, что не упирается в сеть Stepik, в
графическую оболочку и в конкретную ОС/версию языка, — это подавляющее
большинство. Локальное окно владельца дорого и редко, поэтому копи для него
только неизбежное и приходи с готовым списком проверок, а не с идеей
«посмотреть, что будет».

Свежий пример неоптимального дележа: подэпик детерминизма окружения прошёл в
локальном окне целиком, хотя ни одна его правка не упиралась ни в сеть Stepik,
ни в GUI, ни в конкретную ОС — чистый Python, тесты и прогон CLI. Работа
сделана верно, но потрачен дефицитный ресурс. Принадлежность окна проверяется
**до** начала задачи, а не после.

## Общие правила для любой задачи

Полностью — в [`../CLAUDE.md`](../../CLAUDE.md) и
[`../CONTRIBUTING.md`](../../CONTRIBUTING.md): ветвиться от свежего `main`, PR — в
`main`; Python 3.12+ union-типы; `from __future__ import annotations`; `__all__`
в новых модулях; не добавлять зависимости без явного указания; не ломать
`--serve`, `/api/grade` и DAG без циклов; `pytest` + `ruff` + `mypy` зелёные
перед PR; запись в `CHANGELOG.md [Unreleased]`.
