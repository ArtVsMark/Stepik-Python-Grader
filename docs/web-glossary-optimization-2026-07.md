## Часть I — Глоссарий: 832 незаполненные карточки

### 1.1 Фактическая база

Локальная база — `src/stepik_grader/glossary/data/*.json`, всего 1413 карточек:

- **581 `ready`** в 10 тематических файлах (`builtin.json` 75, `module.json` 214,
  `op.json` 104, `str.json` 41, `seq.json` 39, `mapset.json` 33, `exc.json` 22,
  `oop.json` 20, `iter.json` 19, `typing.json` 14) — импорт из Glossary-Python
  (issue #326). У всех заполнены `summary` (RU) и `examples`.
- **832 `draft`** в `drafts.json` — офлайн-генерация из stdlib-интроспекции
  (issue #328, `scripts/generate_draft_cards.py`, тег `autodraft`). У всех есть
  `id`/`title`/`kind`/`section`/`docs_url` (100 %), у большинства `body`
  (EN-докстринг, 805 шт.) и `syntax` (676 шт.). **Пусто у всех 832: `summary`
  (RU), `examples`, `subcat`.**

«Незаполненная карточка» = `status="draft"` с пустым `summary` — это дизайн
#328: «`summary` пуст — его вписывает редактор при промоции `draft` → `ready`»
([glossary.md § Черновики](glossary.md#черновики-из-официальной-документации-issue-328)).
То есть запрос владельца — довести отложенную редактуру до конца.

### 1.2 Эталон «заполненной» карточки

По аналогии с `ready`-карточками (пример — `exc.json::assert`):

| Поле | Планка |
|---|---|
| `summary` | RU-однострочник 1–3 предложения (как `hint` у `core/glossary.py`), без «водянистости» |
| `syntax` | Сигнатура/шаблон; у 156 драфтов пуст — дозаполнить |
| `examples` | Рабочий код-блок (список строк), минимум 3–5 строк с `# → результат`; стиль существующих |
| `subcat` | Из уже используемых подкатегорий раздела (см. `ready`-карточки той же `section`) |
| `tags` | Секционный тег вместо `autodraft` (например `exc`, `str`) |
| `status` | `ready` |
| `url` | **НЕ заполнять** — проставляется экспортом в Glossary-Python (design-only, #126-follow-up) |
| `body` | Дизайн-вопрос волны 1: у всех 581 `ready` он пуст, у драфтов — EN-докстринг; пилот решает «переводить/сокращать/оставлять» |

### 1.3 Триаж: что не наполнять

11 карточек с приватными префиксами (`_frozen_importlib._DeadlockError` и
т.п.) — служебные сущности, попавшие через рекурсивный обход иерархии
исключений (`stdlib_inventory`, [glossary.md § Инвентарь](glossary.md#инвентарь-официального-pythonstdlib-stdlib_inventory-issue-196)).
Новичку они не нужны: пометить тегом `internal` (не наполнять, скрыть из
витрины web-списка по тегу) и заодно отфильтровать приватные модули в
`generate_draft_cards.py`/инвентаре, чтобы не восстанавливались.

### 1.5 Процесс и механика

1. **Генерация черновика контента** (RU `summary`+`examples`) — полуавтоматически
   (Claude-сессия по волне), **ревью владельцем в PR** — карточки контентные,
   истина контента — этот репозиторий ([glossary.md § Источники истины](glossary.md#источники-истины-роли)).
2. **Промоция**: готовая карточка переносится из `drafts.json` в тематический
   файл своей секции (`drafts.json` остаётся = «ещё не готовое»). Проверить в
   пилоте, что `generate_draft_cards.py` идемпотентен относительно переноса
   (он не пересоздаёт существующие id по всей директории — так задокументировано,
   закрепить тестом).
3. **Прогресс** меряется без ручного счёта: количество карточек в `drafts.json`
   + отчёт `python -m stepik_grader.glossary.coverage`.
4. Примеры кода в `examples` — прогоняемы (пилот В1 решает, закреплять ли это
   smoke-тестом по образцу существующих тестов данных глоссария).

### 1.6 Синергия с Частью II

Пункт 2.д (полнота «Функций в коде») упирается в те же карточки: детектор
матчит найденные концепции по `id`/`aliases`/«хвосту id»
(`web/glossary_adapter.py:175-212`). Наполнение В1/В2 напрямую улучшает панель:
у draft-карточки в мини-карточке пустая подпись (`summary` = ""), у `ready` —
осмысленная строка.

### 2.а Sidebar: «Рабочее пространство» и мёртвые «Настройки» (→ W1)

**Сейчас.** «Рабочее пространство» — это просто подпись-заголовок над списком
разделов; «Настройки» — disabled-пункт, который ничего не делает
(`index.html:22-35`). Оба элемента не несут функции.

**Проблема.** Мёртвый пункт меню — классический анти-паттерн: пользователь
кликает, ничего не происходит, доверие к UI падает. Метка «Рабочее
пространство» ничего не группирует (других групп нет) и создаёт ложное
ожидание «рабочих пространств» (мультипроектности), которой в продукте нет.

**Решение.**
1. Метку «Рабочее пространство» убрать (разделам подпись не нужна).
2. Вместо disabled-заглушки — **минимальный рабочий раздел «Настройки»**:
   язык интерфейса уже поддержан бэкендом (`web/i18n.py`, `?lang=`), тема —
   дублировать тумблер topbar, «Недавние пути» (§ 2.в, вариант Б) и место под
   будущий тумблер истории из #348 (эпик #342 уже планирует «Тумблер записи
   истории в „Настройках"» — каркас нужен ему как посадочная площадка).
   Если каркас в момент реализации окажется пустым (язык решат не выносить) —
   допустимый fallback: просто удалить пункт до реального наполнения; держать
   disabled-заглушку — нельзя.

📊 *Продуктовый аналитик:* «Настройки» с одним пунктом — тоже плохо; каркас
оправдан только тем, что #348 уже везёт туда контент (тумблер истории).
🎨 *Дизайнер:* согласен; disabled-пункт в навигации хуже отсутствия пункта.

### 2.б История (→ W2)

**Сейчас.** Блок «История» в конфиг-панели: последние 10 прогонов в
`localStorage` (`grader_history`), клик восстанавливает путь+режим
(`app.js:1883-1930`); показывается во всех 4 режимах.

**Решение владельца:** не нужна во всех 4 режимах — **убрать блок целиком**
(разметка `index.html:118-119`, функции `addHistoryEntry`/`renderHistory`,
ключ `grader_history`).

**Важно про будущее.** «История прогонов» как продуктовая ценность возвращается
в эпике #342 на SQLite-фундаменте (#344) в виде раздела «Подучить» — то есть
удаляем localStorage-суррогат, а не идею. В issue сослаться на #342/#344,
чтобы удаление не выглядело противоречием roadmap.

### 2.в Недавние пути (→ W1)

**Сейчас.** Блок «Недавние пути» (8 путей, `grader_recent_paths`,
`app.js:1858-1881`) — постоянно занимает высоту конфиг-панели во всех режимах.

**Решение.** Убрать постоянный блок; сохранить функцию за нулевую высоту —
**вариант А (рекомендуемый): подсказки у поля пути** — фокус/клик по `#path`
раскрывает выпадающий список последних путей (нативный `datalist` или лёгкий
кастомный дропдаун в стиле палитры). Вариант Б: список в разделе «Настройки»
(владелец: «можно запихнуть где сейчас настройки»). А — на один клик короче и
живёт там, где путь и вводят; Б — приемлемый fallback, если А окажется шумным.

### 2.г Вкладка «Параметры» в режиме 2 — и вкладки конфиг-панели вообще (→ W3)

**Сейчас.** В режиме 1 вкладка «Параметры» скрыта, в режиме 2 — видна, но
серая/некликабельная (#331, `app.js:433-441`), в 3/4 — активна. Содержимое:
один селект «Повторов на тест-кейс» (bench) или профиль calls/run (microbench)
(`index.html:122-149`).

**Решение владельца:** в режиме 2 параметры не нужны. **Расширение (Дизайнер +
Разработчик):** вкладок в конфиг-панели после этого остаётся полторы — вкладка
из одного селекта не оправдывает себя. Убрать вкладки конфиг-панели целиком:
параметры режима 3/4 рендерить **инлайн в панели «Путь»** (селект под полем
пути, только в соответствующем режиме). Меньше состояний (`configTab`,
`setConfigTab`, aria-логика #331 удаляются), меньше кликов до параметра.

### 2.д «Функции в коде» находит не всё (→ W4)

**Сейчас.** Панель питается `POST /api/code-terms` →
`glossary_adapter.code_terms` → AST-сканер `scan_code_concepts`
(`glossary/detector.py:249-268`). Сканер видит только:

1. **Курируемые builtins** — `CODE_TERM_BUILTINS`, ~42 имени
   (`detector.py:63-95`). Вне набора: `frozenset`, `bytes`, `bytearray`,
   `hash`, `id`, `super`, `callable`, `slice`, `staticmethod`, `classmethod`,
   `property`, `vars`, `dir`, `eval`, `exec`, `oct`, `ascii`, `memoryview`… —
   при том, что `builtin.json` держит 75 ready-карточек, а инвентарь stdlib —
   полный список.
2. **Курируемые методы** — `_BUILTIN_METHODS`, ~66 имён только str/list/dict/set
   (`detector.py:101-170`). Вне набора: `removeprefix`/`removesuffix`,
   `expandtabs`, `translate`/`maketrans`, `isnumeric`/`isdecimal`/`isascii`,
   `casefold`-парные пропуски, set-`*_update`-семейство, все bytes-методы.
3. **Вызовы модулей** — только через `ast.Name`-корень
   (`detector.py:221-239`): `math.sqrt(x)` видит, а **`os.path.join(...)` —
   нет** (корень — вложенный `Attribute`): имя `join` уходит в метод-эвристику
   и матчится карточкой **`str.join`** — ложная карточка. Константы-атрибуты
   (`math.pi`) не видны вовсе (сканируются только `Call`).
4. **Конструкции** — только `match/case` (`visit_Match`,
   `detector.py:241-243`). Не распознаются: list/set/dict comprehension,
   генераторные выражения, `lambda`, срезы, f-строки, распаковка `*`/`**`,
   тернарный оператор, walrus, декораторы, `with`, `try/except` — при том,
   что `ready`-карточки под них в базе **есть** (`списочные-выражения-…`,
   `lambda`, `срезы-строк`, `f-строки`, `распаковка-…`, `walrus-operator`,
   `тернарный-оператор`, `декораторы`, `generator-function-yield`).

**Решение.**
1. Наборы builtins/методов **не хардкодить, а выводить из
   `stdlib_inventory`** (issue #196 уже собирает builtins + методы
   `str/list/dict/set/tuple/bytes/…`). `scan_code_concepts` уже принимает
   `notable_builtins=` — добавить симметричный параметр `methods=`; наборы
   собирает адаптер (`web/glossary_adapter.py`) с кешем по образцу
   `_CARDS_CACHE` (#339). Слои не ломаются: `detector.py` остаётся leaf,
   инвентарь — тоже leaf в том же пакете.
2. Починить `os.path.join`: разворачивать цепочку `Attribute` до корня-`Name`
   и матчить `module.attr.func` по импортам; метод-эвристика — только когда
   модульный матч не сработал.
3. Добавить construct-детекторы (comprehensions, lambda, срез, f-строка,
   распаковка, тернарный, walrus, декоратор, генераторное выражение) со
   стабильными concept-ключами; сопоставление с существующими карточками — через
   `aliases` (дозаполнить алиасы соответствующих `ready`-карточек — пересечение
   с Частью I).
4. Панель — с потолком карточек и приоритетом (сначала покрытые, как сейчас,
   `glossary_adapter.py:267`), чтобы «нашли всё» не превратилось в стену.

🧪 *Тестировщик:* нужен золотой тест-набор «эталонное решение → ожидаемые
концепции» (табличный тест на `scan_code_concepts`), отдельно кейс
`os.path.join` ≠ `str.join`, отдельно — chained `x.strip().split()`.

### 2.е Объединить «Детали» и «Лог» (→ W5)

**Сейчас.** «Детали» (`renderDetailPanel`, `app.js:1729-1767`): вердикт, stdin,
expected/actual/diff (WA), диагностика (RE/TLE), glossary-карточка, action
cards. «Лог» (`renderLogTab`, `app.js:366-378`): **тот же stdin** + сырой
stdout/stderr. Обе вкладки — про один и тот же выбранный кейс; «Лог» на ~80 %
дублирует «Детали» и оба зовут `getSelectedCase()`.

**Решение владельца** («сравнение полученных данных и данных, которые
получились» — и есть суть): **одна вкладка разбора кейса** вместо двух.
Ядро вкладки — сравнение: блок «Ожидалось / Получено» (для WA — рядом,
двухколоночно на широкой панели + diff), stdin сверху, диагностика (stderr,
exit code, timeout) — как сейчас, сырой вывод — коллапсируемая секция
«Сырой stdout/stderr» внизу (то единственное, что «Лог» давал сверх «Деталей»).
Вкладки результатов: «Таблица / Разбор» (имя финализируется в PR; «Детали» —
тоже ок). `state.resultTab`-значение `log` удаляется.

### 2.ж Вкладка «Эталон» и issue #55 (→ W6)

**Сейчас.** Вкладка «Эталон» рендерит `reference_source` из ответа

то есть вкладка всегда показывает заглушку «не реализовано (issue #55)».
Бэкенд при этом полностью готов: `grade_benchmark(reference=...)` +
`_apply_reference_ranking` с вердиктами `REFERENCE`/`FASTER`/`SIMILAR`/
`SLOWER`/`MUCH_SLOWER` (`web/viewmodels.py:471-613`) покрыт тестами; в режиме 1
есть disabled-кнопка «Найти эталонное решение» (#55).

**Решение владельца** (совпадает с заделом в коде): **вкладку «Эталон»
убрать**. Эталон — не отдельная сущность, а участник сравнения: после
реализации #55 импортированный файл (`task{N}_stepik_reference.py` — имя
«слегка другое, выделяющееся, но не противоречащее логике» — ровно как в #55)
попадает в папку и виден в таблицах 3/4 обычной строкой с выделенным вердиктом
`REFERENCE` (рендер вердиктов уже общий — `renderVerdict`). Кнопку
«Найти эталонное решение» при реализации #55 логичнее показывать в режимах
3/4 (сейчас она в file-picker режима 1 — `index.html:81-82`); просмотр кода
эталона = обычный просмотр файла решения. В W6 — только удаление вкладки и
заглушки; перенос кнопки — в #55 (там же решается её финальное место).

### 2.з «Функции в коде» в режиме 2 (→ W3)

**Сейчас.** Панель скрыта в 3/4 (#324), видна в 1/2 (`app.js:412`). Но в
режиме 2 file-picker скрыт (`app.js:402`), `selectedSolutionFile` не
выставляется, путь — папка ⇒ панель почти всегда пустует с подсказкой
«Начните вводить код…» (`loadCheckTerms`, `app.js:595-613`), а при множестве
файлов показывала бы «пересмесь всего» (владелец). **Решение:** показывать
только в режиме 1 (`hidden = m !== "file"`), ветку `{path}`-запроса для
режима 2 удалить. В песочнице панель остаётся как есть (#321).

### 2.и Действия в разборе кейса в режиме 2 (→ W5)

**Сейчас.** Action cards собираются бэкендом одинаково для режимов 1/2:
`run_again`, `copy_input`, `copy_output`, `explain_error`, `open_glossary`
(`viewmodels.py::_error_card_actions:153-170`).

**Решение владельца:** в режиме 2 оставить **только копирование входных и
выходных данных** (`copy_input`/`copy_output`). Контент разбора (diff,
диагностика, glossary-блок при RE) — остаётся: это не «действия», а сам разбор
(🧪 без diff/stderr сценарии J2/J3 в режиме 2 ослепнут — не сокращать).
`run_again` не выпиливается из системы — остаётся командой палитры (Ctrl+K)
и action card'ом режима 1. Механика: viewmodels принимает контекст режима или
фронтенд фильтрует `actions` по режиму — решить в PR (первое честнее к
контракту `actions[]`).

### 2.к Режимы 3/4: раскладка и структура таблиц (→ W7)

**Сейчас — раскладка.** `.split-pane` всегда двухколоночный `1fr 1fr`
([web-current.md § Layout](web-current.md#layout-split-pane-workspace)). В
режимах 3/4 левая колонка почти пуста (путь + 1-2 селекта: file-picker скрыт,
«Функции в коде» скрыты #324), а правая — самая широкая таблица приложения.
Половина экрана простаивает, таблица тесная.

**Сейчас — таблицы.** Web-таблица режима 3 **усечена относительно CLI**: CLI
печатает `File / Runs / Min / Median / Mean / Max / Std dev / Memory /
Relative / Verdict` (`core/reporter.py:148-163, 232-280`), web-режим 3 — только
`Файл / Runs / Min / Median / % / Вердикт / Память` (`renderBench`,
`app.js:1780-1783`), тогда как web-режим 4 показывает полный набор
(`renderMicrobench`, `app.js:1819-1825`). Отсюда ощущение владельца «результаты
отличаются от результатов грейдера… суммируются или что»: ничего не
суммируется — это (а) сокращённые колонки режима 3 и (б) разные KPI-плашки
сверху (`kpiGrid`: «Файлов/Медиана/Схожих» с разными подписями в 3 и 4).

**Решение.**
1. **Вертикальная раскладка для 3/4**: конфиг-блок (путь + параметр) компактной
   полосой сверху, панель результатов — во всю ширину под ним (владелец: «папка
   с решениями сверху, под ним результаты — больше места под результаты»).
   Реализация — модификатор класса `.split-pane--stacked` по режиму; режимы
   1/2 остаются двухколоночными (редактор кода оправдывает колонку).
2. **Единая структура таблиц 3/4 = структура CLI**: одинаковый набор и порядок
   колонок `Файл / Runs / Min / Median / Mean / Max / Std dev / Память /
   Relative / Вердикт`; различия только легальные — единицы (s vs µs) и
   подпись памяти `Memory` vs `Py-heap` (методика tracemalloc/RSS, issue #66).
   Данные для Mean/Max/Stdev режима 3 бэкенд уже считает
   (`run_benchmark` → `fmt_time(d["mean"])` и т.д.) — добавить в
   `grade_benchmark`-строки (`viewmodels.py:588-601`) и в рендер.
3. **KPI-плашки** унифицировать: одинаковые три плашки для 3/4
   («Решений / Лучшая медиана / Схожих»), с явными единицами.
