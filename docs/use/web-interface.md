# Веб-интерфейс: разделы и как ими пользоваться

> Что вы видите в браузере после `stepik-grader --serve` и что где нажимать.
> Как запустить сервер и лаунчер — [grader-workflow.md § Веб-интерфейс](grader-workflow.md#веб-интерфейс---serve).
> Контракты данных, сквозные сценарии и устройство фронтенда — для разработчика,
> в [dev/web-contracts.md](../dev/web-contracts.md).

Веб-интерфейс — **локальная оболочка поверх того же ядра, что и CLI**, а не
отдельный продукт. Он существует, чтобы:

1. **Снизить барьер входа.** Консольное меню — препятствие для новичка и для
   того, кто работает из IDE. В браузере то же самое: указал путь → увидел
   вердикты AC/WA/TLE/RE, diff, бенчмарк.
2. **Связать проверку с обучением.** Когда решение падает, рядом открывается
   карточка глоссария по типу ошибки — из **своей** базы, deep-link
   `#/glossary/<id>`, наружу не ссылаемся.

Часть возможностей есть **только здесь** и аналога в терминале не имеет:
песочница с пошаговым трейсом, редактор решения с сохранением, отправка решения
на Stepik, интерактивные разделы «Глоссарий», «Правила (PEP)», «Подучить» и
«Прогресс».

## Разделы и функциональные блоки

Оболочка делится на **семь разделов навигации** (sidebar): «Проверка
решений», «Загрузчик задач», «Глоссарий», «Правила (PEP)», «Подучить»,
«Прогресс», «Песочница».

| Блок | Раздел UI | Что делает | Источник данных |
|---|---|---|---|
| **Проверка решений** | Проверка решений | Прогон файла/папки на корректность (режимы 1/2), subprocess-бенчмарк (режим 3) и микро-бенчмарк timeit (режим 4); таблица вердиктов, diff при WA, error cards при RE/TLE. Панель **«Функции в коде»**: мини-карточки функций/методов/конструкций текущего решения (только режим 1, по коду редактора с debounce), клик → полная карточка глоссария. Наборы builtins/методов — из stdlib-инвентаря, плюс синтаксические конструкции и корректный разбор `os.path.join` (≠ `str.join`) | `grade_path()` / `grade_benchmark()` / `grade_microbench()` → `run_tests` / `run_benchmark` / `run_microbench_mode`; мини-карточки — `POST /api/code-terms` |
| **Downloader / Загрузка тестов** | Загрузчик задач (отдельный раздел) | По URL шага Stepik скачивает задачу, шаблоны и тест-кейсы в локальную папку, откуда сразу можно запустить проверку | `web/downloader_adapter.py::download_task()` — тонкий адаптер над `downloader.py::process_step_url` + `core/oauth_flow.py::try_create_session_without_browser` |
| **Глоссарий** | Глоссарий | Локальный knowledge-модуль: карточки терминов/исключений/функций в проекте, поиск, детектор недостающих конструкций, очередь пополнения | `GlossaryProvider`/store поверх `core/glossary.py`; `MissingConceptDetector` |
| **Песочница** | Песочница | Не проверка, а «запусти этот код с этим вводом»: редактор + поле stdin + вывод (stdout/stderr, код выхода, время). Статусы OK/RE/TLE/CANCELLED. Кнопка **«Пошагово»** открывает плеер трейса: ⏮◀▶⏭ + слайдер + ←→, подсветка активной строки в снимке кода, кадры стека с переменными (изменившиеся подсвечены), нарастающий вывод, красная строка + ссылка в глоссарий на шаге-исключении. Переключатель **«Таблица / Диаграмма»** рисует memory-graph в духе Python Tutor: кадры слева, узлы heap-объектов справа, SVG-стрелки переменная→объект (aliasing = две стрелки в один узел, вложенность = стрелки узел→узел). Панель **«Функции в коде»**: мини-карточки функций, найденных в коде (debounce), клик → полная карточка глоссария; при RE — error card с типом исключения и deep-link в глоссарий | `web/playground.py::run_playground()` (playground) и `core/tracer.py::trace_code()` (trace) поверх `core/runner.LocalRunner`; async через `POST /api/v1/runs` `mode="playground"`/`"trace"`; мини-карточки — `POST /api/code-terms` (`glossary_adapter.code_terms` над `scan_code_concepts`) |

| **Прогресс** | Прогресс | Витрина накопленного: KPI (решено задач, серия зачётов, прогонов, успешных кейсов), чипы достижений, разбор вердиктов и таблица задач с попытками и временем до первого зачёта. Считается по прогонам проверки (режимы 1/2) — сравнение вариантов серию не рвёт | `GET /api/progress` → `web/insights_adapter.progress_report()` поверх `core/progress_export` + `core/insights`; тот же движок, что у CLI `--export-progress` |

> **Разделы «Правила» и «Подучить».** «Правила (PEP)» —
> list+detail карточек правил (поиск, фильтр-чипы по тегам, deep-link
> `#/rules/<code>`, примеры «до/после»); «Подучить» — карточки частых ошибок со
> статусом затухания (🔥 активна / 🌤 угасает / ✅ архив) + ссылки на
> глоссарий/правила и бейдж активных в sidebar (deep-link `#/insights`).
> У каждого типа падения — понятное название вместо ключа (`output-format` →
> «Формат вывода»), строка «что делать» и ссылка в карточку глоссария; сам ключ
> остаётся в `title` подсказки, потому что по нему ищут в документации. Данные
> — `GET /api/rules` (`?q&tag`) / `/api/rules/{code}` / `GET /api/insights` (см.
> [api.md](../dev/api.md)) поверх `rules/` и `core/insights`. Те же
> инсайты в терминале — `--insights`/`--lint`. Единый hash-роутер
> (замена glossary-only, риск R6). Чипы «Стиль» прямо в результатах проверки
> (lint в web-grade) — отдельный follow-up.

Блоки связаны:

- из **error card** в «Проверке решений» есть переход **Open glossary**
  прямо на нужную карточку раздела «Глоссарий» (deep-link по `glossary_id`);
- **Downloader** — кнопка «Перейти к проверке» (по клику, не автоматически)
  подставляет скачанный путь в command bar «Проверки решений» и переключает
  раздел — скачал → сам нажимает ▶ (J0);
- **детектор недостающих концепций** глоссария читает решения/ошибки из
  «Проверки решений» и пополняет очередь карточек.

Обратной жёсткой связи нет — «Глоссарий» самодостаточен и может читаться
отдельно.

### Обратная связь (кнопка 💬 в topbar)

Кнопка живёт в topbar рядом с «?», а не в разделе sidebar: канал должен быть
виден из любого места, иначе о баге просто не сообщат.

Как работает: выбор типа обращения (🐞 Баг / 💡 Идея / 🧩 Задача проверяется
неправильно) → необязательное краткое описание → `POST /api/feedback` собирает
**черновик** (см. [api.md](../dev/api.md#post-apifeedback)) → блок «Показать,
что уйдёт в форму» показывает итоговые поля → кнопка ведёт на GitHub, где форма
уже заполнена, а Submit жмёт сам пользователь.

Что здесь гарантировано:

- **Ничего не отправляется из грейдера.** Токена нет, сервер только считает URL;
  кнопка — обычная ссылка (`<a target="_blank">`), а не fetch-отправка.
- **Предпросмотр обязателен.** Содержимое обращения видно до открытия браузера;
  поля, усечённые или выброшенные из-за лимита длины URL, объявляются строкой
  предупреждения, а не теряются молча.
- **Код решения не уходит.** В черновик попадают версия, ОС, Python, состояние
  `--sandbox`, локаль и — если грейдер запущен из git-клона — текущий коммит;
  без имени машины и без домашнего пути (свёрнут в `~`).
- Адреса GitHub в статике не хардкодятся: `href` ставит JS из ответа API —
  иначе нарушился бы инвариант «никаких внешних `href`/`src` в `index.html`».
- Вопросы уводятся в Discussions ссылкой в самой модалке — вопрос новичка не
  должен становиться issue.

Тот же канал в терминале — пункт «Сообщить о проблеме / предложить идею» в
интерактивном меню (см. [grader-workflow.md](grader-workflow.md)).

## Downloader / Загрузка тестов

Скачивание задачи и тест-кейсов из Stepik реализовано как отдельный раздел
«Загрузчик задач». CLI-путь
(`python -m stepik_grader.downloader`, см.
[grader-workflow.md § Шаг скачивания задачи](grader-workflow.md#шаг-скачивания-задачи))
остаётся неизменным и по-прежнему единственный способ выполнить первичную
OAuth-авторизацию — веб-раздел лишь показывает понятную ошибку, если
валидного токена нет.

**Где в UI.** Отдельный раздел «Загрузчик задач» (sidebar, `data-section=
"downloader"`, `<section id="view-downloader">`) — одна колонка из трёх
панелей: «Доступ к Stepik» (состояние авторизации + строка «Куда
скачивать»), «Скачать задачу» (поле URL + «▶ Скачать») и «Результат», которая
появляется только после скачивания. Порядок — по ходу дела: без доступа
скачивать нечем. По завершении — кнопка «Перейти к проверке» (по клику, не
автоматически) подставляет путь скачанной папки в поле пути раздела «Проверка
решений» и переключает раздел — цикл «скачал → сам нажимает ▶ проверки»
замыкается без копипаста (J0).

**Куда скачивать.** Корневая папка показывается **значением** из
`stepik_config.json` (а не пустым полем с плейсхолдером) и меняется по кнопке
«Изменить» → поле → «Сохранить»: `POST /api/downloader/config` пишет `root_dir`
в тот же файл, что читает CLI, поэтому значение действует и в следующий раз, и
в терминале. Если конфига нет — показывается дефолт `StepikTasks` с пометкой
«по умолчанию».

**Что показывает.** Итог загрузки (`DownloadedTask`): какие файлы созданы
(`task{N}_1.py`, `tests/`, `task.md`, `meta.json`), сколько тест-кейсов
извлечено и из какого источника (ZIP / HTML-таблица / GitHub-ссылка / ничего
не найдено — те же 4 приоритета, что в `downloader.py`).

**Границы (неинвазивность).** Web-слой (`web/downloader_adapter.py`) — тонкий
адаптер над публичными функциями `downloader.py`/`core/oauth_flow.py`; новой
логики скачивания в web нет, DAG без циклов сохраняется (`web →
downloader → core`).

**OAuth.** Браузерный OAuth-мастер первого запуска доступен прямо в web:
раздел «Загрузчик задач» проверяет токен (`GET /api/auth/status`)
и при его отсутствии показывает форму `client_id`/`client_secret` — кнопка
«Авторизоваться в браузере» запускает `POST /api/auth/start`, который пишет
`secrets.json` (0600) и проводит loopback-OAuth как async-job (`kind="auth"`,
опрос через `GET /api/v1/runs/{id}`). Так авторизоваться можно без ручного
создания `secrets.json` и без CLI.

**Три состояния панели доступа.** Мастер больше не показывается
всегда — он лишь одна из веток:

| Состояние | Что видно |
|---|---|
| `authorized` | Строка «Доступ активен · `<путь>`» + «Проверить» / «Настроить заново» |
| `no_token` (креды есть, токен истёк) | «Токен истёк» + одна кнопка «Авторизоваться заново» — креды берутся из файла, вводить их снова не нужно (`POST /api/auth/start` с пустым телом) |
| `no_secrets` (первый запуск) | Развилка «Настроить впервые» (мастер `client_id`/`client_secret`) / «У меня есть secrets.json» (поле пути + «Проверить файл») |

Ветка запоминается не флагом, а самим состоянием конфига: как только рабочий
`secrets.json` найден, при следующем заходе показывается компактная строка, а
не мастер. Путь к файлу — из `stepik_config.json` (`GET /api/downloader/config`,
`secrets_path`) — тот же источник, что и у скачивания: иначе панель могла бы
показывать «Доступ активен» при неработающем скачивании. Тонкий адаптер `web/auth_adapter.py` над
`core/oauth_flow` (DAG `web → core` без циклов); `webbrowser.open`
открывается на машине сервера — корректно только для локального `--serve`
(localhost, single-user), для удалённого сервера не применимо.
`try_create_session_without_browser` по-прежнему обслуживает уже-валидный
токен/обновление по `refresh_token` без похода в браузер.

**Non-goal.** Массовое/batch-скачивание курса целиком, планировщик
обновлений — вне рамок; один шаг за раз, как в CLI.

## Режимы проверки и микро-бенчмарк

CLI поддерживает **четыре** рабочих режима (плюс `0` — выход); WEB отражает
все четыре, включая корректность, subprocess-бенчмарк и микро-бенчмарк:

| Режим CLI | Название | Ядро | Раздел UI «Проверка решений» |
|---|---|---|---|
| 1 | Проверка одного файла | `run_tests` | режим **Корректность** (файл) |
| 2 | Проверка папки | `run_tests` | режим **Корректность** (папка) |
| 3 | Subprocess-бенчмарк | `run_benchmark` | режим **Бенчмарк** |
| 4 | Микро-бенчмарк (timeit) | `run_microbench_mode` | режим **Микро-бенчмарк** |

Переключатель режимов — ряд кнопок **«Режим 1…4»** (Один файл / Папка /
Bench / Microbench) в шапке раздела «Проверка решений». Микро-бенчмарк
(режим 4) меряет время через `timeit` внутри процесса и показывает колонки,
отличные от режима 3:

- метрики в **микросекундах** (`Min/Median/Mean/Max/Std dev, µs`),
  `Relative`, `Verdict` (`SIMILAR`/`SLOWER`/`MUCH SLOWER`);
- колонка памяти называется **`Py-heap`** (не `Memory`): для stdin-блоков —
  пик Python-heap через `tracemalloc`, для function-блоков — RSS;
- профили «calls per run» (fast/normal/thorough/deep/hard/custom) —
  параметр запуска (аналог `--number`).

**Реализация.** `grade_microbench()` + `_resolve_group_test_dir`
(`web/viewmodels.py`), роутинг `mode=microbench` (`server.py`,
`GET /api/grade?mode=microbench&number=`, см. [api.md](../dev/api.md)),
профиль-селектор и таблица результатов; оркестрация —
`core/grader_core.py::run_microbench_mode`, нижнеуровневый прогон —
`core/microbench_runner.py::run_microbench`. Non-goal: менять саму методику
timeit-замера — web лишь отображает результат существующего ядра.
Per-block detail-разбор (какой блок замерялся stdin/tracemalloc vs
function/RSS) остаётся design-only, см.
[web-design.md](../dev/design/web-design.md#per-block-detail-разбор-микробенча).

## Условие задачи в режиме 1

Кнопка **«📄 Условие задачи»** рядом с «Отправить в Stepik» открывает
модальное окно с текстом задания: хлебные крошки курс → секция → урок → шаг,
само условие и список файлов к задаче.

Кнопка живёт в блоке режима 1 и в режимах 2–4 не показывается: условие
относится к одной выбранной задаче, а не к папке решений. Пока задача не
выбрана — или условие для неё не скачано — кнопка неактивна, и подсказка
объясняет, почему. Пустое окно после нажатия человек читает как поломку,
поэтому этого случая нет.

Закрытие — крестиком, `Esc` или кликом мимо диалога; фокус возвращается на
кнопку. Длинное условие прокручивается **внутри** окна, страница под ним не
смещается; таблица примеров при необходимости прокручивается по горизонтали
сама, не растягивая диалог.

**Что показывается.** Тело условия приходит с сервера уже очищенным —
`GET /api/task/statement` пропускает его через whitelist тегов (см.
[api.md](../dev/api.md)). Картинки подставляются только из скачанных вложений;
внешние источники не подгружаются. Вложение, которое не приехало при
скачивании, помечено **словом**, а не только цветом: задача, ссылающаяся на
`files.txt`, иначе выглядит как ошибка в коде решения.

**Чего окно не делает.** Не редактирует условие, не кэширует его в браузере,
не открывает отдельную вкладку и не рендерит формулы LaTeX — они переносятся
как есть.

## Навигация по скачанным задачам

Над полем пути — переключатель **«Навигация / Путь»**. В режиме навигации
стрелки листают скачанные задачи, выпадающий список задаёт, **чем** шагает
стрелка (курс, глава или шаг), а `☰` раскрывает перечень со статусами.

**Поле пути никуда не делось** и остаётся равноправным: работа с произвольной
папкой вне скачанного курса — рабочий сценарий, и к тому же первый по времени
(сначала пробуют одну задачу, курс качают потом). Выбор режима запоминается.

**Порядок — из курса, а не из алфавита папок.** `task10` идёт после `task9`, а
не перед ним, и переименование папки порядок не ломает: он берётся из
иерархии в `meta.json`.

Шаги листаются сквозным потоком через границы глав — смена главы не теряется,
потому что видна в подписи под стрелками («Списки · Урок 3 · шаг 9 — Девятый»).
На краях диапазона стрелка становится неактивной **с подсказкой**: серая кнопка
без объяснения читается как «сломалось». Alt+←/→ делают то же, что стрелки
(голые стрелки заняты редактором кода).

Статусы в списке берутся из истории: «решено», «в работе», «не начата»; на
уровне главы — прогресс вида «5 из 12 решено». История opt-in, и при выключенной
все шаги показываются как «не начата» — навигация работает и без неё.

Выбор в панели заполняет поле пути; ручной ввод, наоборот, ставит панель на эту
задачу, а для папки вне курса честно говорит «вне скачанного курса». Источником
истины остаётся путь — панель лишь способ его выбрать.

## Глоссарий как локальный knowledge-модуль

Раздел «Глоссарий» — **не список внешних ссылок**. Внутри
Stepik-Python-Grader живёт полноценный локальный knowledge-модуль, который
хранит контент и обнаруживает пробелы. Внешний проект
[Glossary-Python](https://github.com/ArtVsMark/Glossary-Python) при этом
**сохраняется** как отдельный лёгкий one-page HTML-справочник для быстрого
доступа откуда угодно — он не заменяется, а получает контент через экспорт
(design-only, см. [web-design.md](../dev/design/web-design.md#экспортсинхронизация-глоссария-во-внешний-проект)).

**Составные части модуля:**

1. **Локальная база карточек** (`GlossaryProvider`/store). Карточки
   терминов/исключений/функций хранятся **в проекте** — JSON-файл(ы), при
   росте — SQLite. Расширяет компактный `core/glossary.py` (~28 исключений)
   полями `body`/`section`/`related`/`status` (см. контракт `GlossaryCard`).
   Источник истины для карточек — локальная база, а не удалённый сайт.
2. **Детектор недостающих концепций** (`MissingConceptDetector`). Сканирует
   решения (AST/имена), тексты ошибок и вердикты RE/WA и находит
   функции/конструкции/исключения, для которых **нет карточки** в локальной
   базе (например, встретился `functools.reduce`, `RecursionError` без
   карточки, конструкция `match/case`).
3. **Очередь пополнения** (backlog недостающих карточек). Обнаруженные
   пробелы складываются в локальную очередь `GlossaryMissingEntry` со
   статусом `new` — черновики для последующего наполнения (вручную или
   полуавтоматически). Это «TODO-лист глоссария», который растёт из реальной
   практики проверки решений.
4. **Связь с error cards и проверкой решений.** error card при RE/WA
   ссылается на карточку глоссария (`glossary_ids`), а если карточки нет —
   `MissingConceptDetector` регистрирует пробел в очереди. Так глоссарий
   пополняется именно теми терминами, на которых спотыкаются решения.
5. **UI раздела.** Комплектная база
   (~1349 ready-карточек; приватно-именованные автодрафты скрыты всегда)
   грузится по умолчанию (zero-config). Поверх списка — тулбар:
   поиск, сетка **раскрываемых семейств разделов** одного размера (Модули ·
   Типы данных · Синтаксис · Встроенные и исключения · Ввод-вывод и файлы ·
   Алгоритмы; плюс «Прочее», если появился неклассифицированный раздел). Клик по
   семейству фильтрует выдачу (`?group=`) и раскрывает его разделы со
   счётчиками — разнотипное не объединяется, «Списки» и «Кортежи» остаются
   раздельными кнопками внутри «Типов данных». Выбор раздела **сворачивает**
   панель (список из 30 модулей не занимает экран), а текущий фильтр виден
   «пилюлей» «Семейство › Раздел» с крестиком: повторный клик по семейству лишь
   разворачивает/сворачивает список и выбор не теряет, снимает фильтр только
   крестик. Семейства покрывают **все** разделы базы, поэтому селектов «Раздел»
   и «Тип» больше нет (`kind` дублировал навигацию: исключения = раздел
   «Исключения», конструкции = «Синтаксис»); селект «Статус» показывается только
   если в источнике есть не-ready карточки (в комплектной базе их нет). Остаётся
   сортировка (по релевантности / A–Я / по разделам / по версии) — грани
   комбинируются на бэке (`GET /api/glossary`, см.
   [api.md](../dev/api.md#get-apiglossary)); счётчик «Показано N из M». Карточка
   открывается по deep-link `#/glossary/<id>` (прямые ссылки; сюда же ведут
   error cards и мини-карточки «Функции в коде»). Полный вид карточки
   рендерит `syntax`, примеры, version-бейдж и ссылку на docs.python.org.

**Жизненный цикл карточки:** `new` (обнаружена детектором) → `draft`
(наполняется) → `ready` (готова к показу/экспорту) → `exported`
(выгружена во внешний глоссарий — экспорт сам ещё design-only, см. ниже).

**Двуязычные описания.** Текстовые поля `summary` и `body`
хранятся двуязычно — вложенным `{ru, en}` в JSON. Web-API (`/api/glossary`,
`/api/glossary/<id>`, `/api/code-terms`) отдаёт их **строкой** локали из
`?lang=` (тумблер `RU|EN` в topbar) с fallback на `ru`;
смена языка перезагружает список и открытую карточку без перезагрузки страницы.
Python-атрибуты `card.summary`/`card.body` остаются RU-строками (обратная
совместимость всех читателей), EN — `card.summary_en`/`card.body_en`;
локализация в API — `card.localized(field, lang)` / `card.to_api_dict(lang)`.

**Разделение ролей (важно):**

| | Локальный модуль (Stepik-Python-Grader) | Внешний Glossary-Python |
|---|---|---|
| Роль | Богатый learning/checking-глоссарий: база карточек, детектор пробелов, очередь, связь с проверкой | Лёгкий one-page HTML-справочник для быстрого доступа откуда угодно |
| Данные | Локальная JSON/SQLite-база в проекте | Статический HTML/GitHub Pages |
| Направление | Источник контента → экспорт наружу | Потребитель экспортированных карточек |
| Обновление | Растёт из реальной практики проверки решений | Обновляется экспортом из грейдера |

Внешний проект **не** заменяет локальный модуль и **не** редактируется из
грейдера напрямую (см. запрет в [`../CLAUDE.md`](../../CLAUDE.md) § «Связанный
проект») — только через экспорт/PR в самом Glossary-Python.

Односторонность распространяется и на ссылки: ни карточка, ни
подсказка при RE, ни UI не ведут на витрину — она копия этой базы и отстаёт от
неё, так что переход туда показал бы студенту устаревшую версию той же
карточки. Навигация всегда внутренняя (`#/glossary/<id>`).

**Истина контента vs истина полноты.** Важно не смешивать два разных вопроса:

- **Где хранится контент** — источник истины контента — сам
  **Stepik-Python-Grader** (локальная база карточек). Glossary-Python —
  downstream-витрина/цель экспорта, **никогда** не эталон.
- **Относительно чего меряется полнота (coverage)** — источник истины полноты —
  **официальный Python / stdlib**. «Чего не хватает» считается относительно
  официального языка и стандартной библиотеки, а не стороннего справочника.

Отсюда **два источника пробелов** очереди пополнения: *practice-driven* (из
решений/ошибок, детектор — J7 ниже) и *source-driven* (сканирование покрытия
stdlib, `glossary/stdlib_inventory.py`/`coverage.py`). Роли и источники
канонично сведены в
[glossary.md § Источники истины](../dev/glossary.md#источники-истины-роли).

## Навигация и UX-схема

```
┌──────────────────────────────────────────────────────────────────────┐
│ TOPBAR   🐍 Stepik Python Grader                      RU EN    🌓     │
├───────────────┬────────────────────────────────────────────────────────┤
│  SIDEBAR      │  MAIN (зависит от активного раздела)                    │
│  (вертикаль)  │                                                          │
│  • Проверка   │   — см. § Layout (split-pane) для «Проверки решений»;   │
│    решений    │     недавние пути — datalist-подсказки у поля пути      │
│  • Загрузчик  │   — «Глоссарий»/«Правила»: список карточек + панель      │
│  • Глоссарий  │   — «Загрузчик» / «Песочница»: свои split-pane           │
│  • Правила    │   — «Настройки»: статус истории; тема и язык —           │
│  • Подучить   │   — «Прогресс»: KPI, достижения и таблица задач           │
│  • Прогресс   │                                                          │
│  • Песочница  │                                                          │
│  ───────────  │                                                          │
│  • Настройки  │                                                          │
└───────────────┴────────────────────────────────────────────────────────┘
```

- **Topbar**: логотип, бейдж режима исполнения, тумблер языка `RU|EN` и
  тумблер темы (`🌓` системная / `☀️` светлая / `🌙` тёмная — подпись кнопки
  называет текущий режим). Переключателя разделов в topbar НЕТ —
  он в sidebar.
- **Sidebar**: вертикальный список разделов навигации («Проверка решений»,
  «Загрузчик задач», «Глоссарий», «Правила (PEP)», «Подучить», «Прогресс»,
  «Песочница») плюс
  отделённый чертой **рабочий** пункт «Настройки» (тема и язык — в topbar,
  здесь остался статус истории). Активный раздел подсвечен
  (`aria-current="page"`).
- **Недавние пути** — подсказки нативного `datalist` у поля пути раздела
  «Проверка решений»; постоянного блока «История» нет — продуктовая история
  живёт на SQLite в разделе «Подучить».

Навигация — «раздел → контекст → деталь»: выбор раздела в sidebar, выбор
объекта (путь / решение / карточка) в конфиг-панели или main, раскрытие
детали (тест-кейс / error card) inline. Deep-linking карточки глоссария через
URL-хэш `#/glossary/<id>` реализован. Раздел тоже адресуется — `#<раздел>`
(`#check`, `#sandbox`, …, тот же формат, что в ссылках sidebar): ссылкой на
раздел можно поделиться, а F5 возвращает туда же. Хэш раздела пишется через
`replaceState` (переключение раздела — смена вида, а не шаг истории), и хэш
карточки им не переписывается: он адресует точнее. Ранее задокументированный
`#/insights` продолжает работать. Общий deep-linking
состояния — см.
[web-design.md § Deep-linking через URL-хэш](../dev/design/web-design.md#deep-linking-через-url-хэш).

**Стартовый онбординг-экран.** При первом заходе поверх workspace
показывается модальный экран-приветствие: что это, как проверить решение и где
скачать задачу. Флаг «видел» персистентен на сервере (`onboarding_seen` —
`POST /api/v1/settings`, см. [api.md](../dev/api.md); `data-onboarding-seen` на `body`),
поэтому повторных показов нет: флаг пишет при закрытии галка «Не открывать это
окно автоматически при следующем запуске» (`#onboarding-dont-show`, по умолчанию
отмечена) — снять её, чтобы экран вернулся при следующем запуске. Открыть
вручную — кнопка «?» («Как пользоваться», `#onboarding-open`) в topbar.
Как и модалки, экран держит focus-trap, закрытие по `Escape` и возврат фокуса
на элемент-источник.

## Layout: split-pane workspace

Раздел «Проверка решений» — двухпанельное рабочее пространство (`.split-pane`,
`1fr 1fr`): слева конфиг-панель, справа панель результатов. В режимах 3/4
(bench/microbench) раскладка переключается на **вертикальный стек**
(`.split-pane--stacked`): конфиг компактной полосой сверху,
панель результатов — во всю ширину под ним.

```
┌─────────────┬───────────────────────────┬───────────────────────────┐
│  SIDEBAR    │  CONFIG PANEL             │  RESULT PANEL             │
│ (навигация) │  (без вкладок)            │  вкладки: Таблица / Разбор │
│             │  • путь + datalist        │  • Таблица решений         │
│             │    недавних путей         │    (passed / verdict / t)  │
│             │  • параметры 3/4 инлайн    │  • Разбор: Ожидалось/      │
│             │  • редактор кода (р.1)     │    Получено, diff, error   │
│             │  • «Функции в коде» (р.1)  │    card, glossary, ▸ сырой │
└─────────────┴───────────────────────────┴───────────────────────────┘
```

- **Sidebar** — глобальная навигация по разделам (не часть `.split-pane`).
- **Config panel** (левая колонка, **без вкладок**): путь с
  datalist-подсказками недавних путей, параметры режимов 3/4 инлайн под полем
  пути (repeats/микро-профиль), редактор кода и панель «Функции в коде» — только
  в режиме 1 (в режиме 2 путь — папка, панель пустует).
- **Result panel** (правая колонка) — вкладки «Таблица / **Разбор**».
  **«Разбор» — это вкладка, а не отдельная третья колонка**: ядро — сравнение
  «Ожидалось/Получено» (для WA двухколоночно) + diff, error card, glossary card;
  сырой stdout/stderr — коллапсируемая секция внизу. Action cards режима 2 —
  только копирование входа/выхода (`run_again` доступен главной кнопкой «Запустить»).
- Таблицы режимов 3/4 — единая структура как в CLI-репортере (Файл/Runs/Min/
  Median/Mean/Max/Std dev/Память/%/Вердикт). Упавшее решение даёт
  одну строку с сутью ошибки, полный traceback — свёрнутым блоком под таблицей.
- Вкладка «Разбор» в режимах 3/4 показывает **диаграмму сравнения решений**:
  полоса — медиана, тонкая линия — разброс min–max, общий масштаб
  для всех решений, «×N» — во сколько раз медленнее лучшего (по `relative`),
  эталон (`--import-reference`) отдельным цветом, упавшие решения — строкой «не
  участвуют». Выбирать кейс там нечего: строка таблицы в этих режимах —
  агрегат по решению, а не тест-кейс. Ширины ставит JS через CSSOM — строгий
  CSP запрещает инлайн-стили.
  В режимах 1/2 вкладка работает по-прежнему (разбор выбранного кейса).
- Разделитель панелей **не перетаскивается**; на узком экране панели
  схлопываются в вертикальный стек.

Раздел «Глоссарий» использует тот же `.split-pane` в варианте «список
карточек | панель карточки»; «Загрузчик задач» и «Песочница» — свои
двухпанельные раскладки.

## Доступность, клавиатура, тёмная тема

- **Тёмная тема.** Через `prefers-color-scheme` (CSS-переменные), плюс явный
  тумблер (topbar) с сохранением выбора (localStorage), дефолт «системная».
- **Клавиатура.**
  - `Enter` в поле пути — запуск.
  - `←`/`→` — шаги пошагового исполнения в песочнице.
  - `Tab`-навигация по интерактивным элементам; видимый focus-ring.
  - Хоткеи действий из реестра (`CommandAction.shortcut`) активны только в
    их контексте (`when`).
  - `Ctrl+K` больше нет — палитра команд удалена.
- **Доступность (a11y) — базовый уровень реализован.**
  - Семантическая разметка: таблицы результатов — настоящие `<table>` с
    `<th scope>`; вердикты дублируются текстом, не только цветом
    (`renderVerdict()` всегда вставляет строку вердикта в бейдж).
  - Панели/диалоги — с `role`/`aria-label`; модалка AI-согласия —
    `role="dialog"` с `aria-modal`.
  - **Объявление результатов.** Скрытый polite live-region
    `#result-announce` (`aria-live="polite"`) озвучивает одну строку-сводку
    исхода по ЗАВЕРШЕНИИ прогона («task_1.py — OK, 12 из 12» / «Бенчмарк
    завершён: N решений» / текст ошибки/отмены) — не на каждый прогресс-тик,
    иначе был бы шум. После завершения фокус переводится на панель
    результатов (`#restab-table[tabindex="-1"]`).
  - **Прогресс-бар** долгого прогона — `role="progressbar"` +
    `aria-valuemin/valuemax/valuenow` (неопределённый — `aria-valuetext`).
  - Контраст бейджей/вердиктов ≥ WCAG AA 4.5:1 в обеих темах: токен
    `--color-warning` в тёмной теме поднят до `#d98a5c` (прежний
    `#bb653b` давал ~3.5–4.4:1 для SLOWER на тёмных surface).

Полный a11y-аудит остаётся design-only, см.
[web-design.md § Полный a11y-аудит](../dev/design/web-design.md#полный-a11y-аудит).
