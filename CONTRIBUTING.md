# Contributing to Stepik-Python-Grader

Спасибо за интерес к проекту! Это руководство поможет быстро начать работу.

> Участвуя в проекте, вы соглашаетесь соблюдать
> [Кодекс поведения](CODE_OF_CONDUCT.md).

> **In English.** This guide is in Russian, but contributing does not require
> it. The short version: fork, branch off `main`, `python -m venv .venv` +
> `pip install -e ".[dev]"`, then run the same gates CI does —
> `pytest tests/ -x -q`, `ruff check .`, `ruff format --check .`,
> `mypy src/stepik_grader scripts`. Commit messages follow
> [Conventional Commits](https://www.conventionalcommits.org) with an English
> type/scope (`fix(cli): …`); the description and the `CHANGELOG.md` entry are
> written in Russian — the project's documentation language. Pull requests and
> issues in English are welcome. Conduct concerns:
> [Code of Conduct](CODE_OF_CONDUCT.md).

## Первый вклад за 15 минут

Короткий путь для новичка — от нуля до открытого PR:

1. **Выберите задачу.** Метки [`good first issue`](https://github.com/ArtVsMark/Stepik-Python-Grader/labels/good%20first%20issue)
   и [`help wanted`](https://github.com/ArtVsMark/Stepik-Python-Grader/labels/help%20wanted)
   — задачи с понятным объёмом. Вопросы/идеи — в
   [Discussions](https://github.com/ArtVsMark/Stepik-Python-Grader/discussions).
2. **Форк + ветка от свежего `main`** (`git checkout -b <type>/<slug>`,
   Conventional Commits — см. [§ Правила коммитов](#правила-коммитов-conventional-commits)).
3. **Установка** (5 минут): `python -m venv .venv`, затем активация —
   Windows: `.venv\Scripts\activate`, macOS/Linux:
   `source .venv/bin/activate` — и `pip install -e ".[dev]"`
   (см. [§ Установка](#установка)).
4. **Локальные гейты перед PR** (зеркалят CI): `python scripts/preflight.py` —
   одна команда вместо четырёх (`pytest tests/ -x -q` · `ruff check .` ·
   `ruff format --check .` · `mypy src/stepik_grader scripts`), плюс свежесть
   ветки и запись в `CHANGELOG.md`; вывод прогона целиком ложится в
   `.git/preflight-logs/` (см. [§ Запуск тестов](#запуск-тестов)).
5. **Одна запись файлом** — `changelog.d/<slug>.<секция>.md`, внутри строка
   текста (формат — [`changelog.d/README.md`](changelog.d/README.md)) + PR в
   `main` (черновик можно;
   см. [§ Процесс внесения изменений](#процесс-внесения-изменений)).

Не уверены, за что взяться, или хотите обсудить идею? Откройте
[Discussion](https://github.com/ArtVsMark/Stepik-Python-Grader/discussions) — это
ни к чему не обязывает.

## Метки при заведении issue

Каждый новый issue помечается для навигации (полный список — `gh label list`):

- **`area/*`** — область кода: `cli`, `web`, `glossary`, `docs`, `sandbox`,
  `core`, `rules`.
- **`difficulty/*`** — `easy` (локальное изменение, минимум контекста) ·
  `medium` (несколько модулей или неочевидная логика) · `hard` (архитектура,
  кросс-модульные инварианты).
- **`good first issue`** / **`help wanted`** — изолированные задачи с низким
  барьером входа; питают блок «Первый вклад за 15 минут» выше, поэтому ставятся
  только на реально посильное новичку.
- Плюс тип по смыслу: `enhancement`, `bug`, `tech-debt`, `security`,
  `documentation`, …

### `good first issue` заводится сразу на двух языках

Тело задачи с меткой **`good first issue`** содержит русскую версию и
английский перевод — обе, а не одну на выбор.

Почему именно эта метка, а не все подряд: у проекта есть намеренная
англоязычная витрина ([README.en.md](README.en.md), локаль `en` в CLI и вебе,
двуязычные подписи в issue-формах), и `good first issue` — единственный вход,
на который она приводит. Задача, доступная только по-русски, отсекает ровно ту
аудиторию, ради которой метка и существует: англоязычный читатель доходит до
списка задач и упирается в стену текста, которую не может прочесть.

Формат — русская версия, разделитель, английская:

```markdown
<русский текст задачи>

---

## In English

<английский перевод>
```

Заголовок `## In English` — не украшение, а якорь: по нему
[`scripts/check_good_first_issues_bilingual.py`](scripts/check_good_first_issues_bilingual.py)
находит английскую половину и предупреждает, если её нет или она осталась
русской. Проверка **не роняет CI** — это состояние трекера, а не дефект кода
(тот же принцип, что у бейджа пула задач).

Русская версия — источник истины; английская переводит её, а не живёт своей
жизнью. Расхождение по смыслу — ошибка перевода, а не два разных требования.

### Комплексный issue ведёт чек-лист находок

**Комплексный** — тот, что несёт не одну задачу, а список: эпик, подэпик, хвост
аудита, «десять находок одной темы». С **третьей** находки список нужно вести, а
не пересказывать: две задачи в теле ещё читаются глазами, дальше состояние
теряется.

Формат — одна находка, одна строка чек-листа:

```markdown
- [ ] `RUN-1-01` — пара кейса ищется по нормализованному номеру (`core/test_loader.py:204`)
- [x] `RUN-4-02` — вывод обрабатывается без границ: ложный WA (#НОМЕР-PR)
- [x] ~~`STR-5-06`~~ — отклонено: репро недостижим, решение без кейсов в рейтинг не попадает
```

Четыре правила, без которых форма не работает:

1. **Галочка ставится тем же заходом, что и мерж** закрывающего PR, а не пачкой
   «когда-нибудь потом». Отложенная отметка — это и есть расхождение issue с
   кодом.
2. **Отмеченная строка называет исход:** номер PR или причину отклонения.
   Галочка без исхода — утверждение «сделано» без доказательства, и следующий
   читатель всё равно пойдёт проверять по коду.
3. **Отклонённая находка тоже отмечается** — зачёркнутым ID и причиной. Иначе
   счётчик GitHub врёт: «12 из 15» там, где по трём строкам работы нет и не
   будет.
4. **Состояние живёт в одном месте — в самом issue.** Пока он открыт, реестры в
   документах его не дублируют: два источника означают один устаревший.

Две поправки на размер и форму:

- **Больше тридцати находок — чек-лист по группам** (файл, модуль, зона), а не
  по каждой строке: три сотни пунктов нечитаемы и правятся с конфликтами.
  Строка группы закрывается, когда закрыты все её ID; частично закрытая
  остаётся неотмеченной, а закрытые ID называются в ней явно.
- **У эпика с дочерними issue чек-лист не нужен** — прогресс уже считает сам
  GitHub. Дочерний issue заводится, когда у пункта свой цикл работы и свой PR;
  галочка — когда пункт закрывается строкой в чужом PR.

Закрывать комплексный issue можно, когда отмечена каждая строка. В закрывающем
комментарии — таблица «находка → PR или причина»: тело показывает прогресс,
комментарий фиксирует итог.

Прецедент, из которого выросло правило: подэпик про вернувшиеся дефекты
перечислял семь находок таблицей. Пять были закрыты, но узнать это удалось лишь
ревизией по коду через полторы недели; параллельно документ аудита вёл
собственный реестр закрытых находок, который отстал и начал числить закрытое
открытым.

Проверяет [`scripts/check_issue_checklists.py`](scripts/check_issue_checklists.py):
находит открытые issue с меткой `epic`/`audit` или заголовком «[Эпик]»,
«[Подэпик]», «[Хвост]» и предупреждает, если находки перечислены скопом или
галочка не называет исход. Проверка **не роняет CI** — это состояние трекера, а
не дефект кода (тот же принцип, что у двуязычных `good first issue`).

## Правила размещения файлов

> **Корень репозитория — не свалка. Только `src/stepik_grader/` и
> инфраструктура репозитория (src-layout).**

### В `src/stepik_grader/` остаются точки входа

| Файл / паттерн | Причина |
|---|---|
| `grader.py`, `cli/` | Точки входа — запускаются как `python -m stepik_grader.X` / `stepik-grader` (`cli/` — пакет, `__init__.py` facade + `options.py` leaf) |
| `config.py` | Project-level конфигурация; импортируется из `core/*` (перенос вызовет circular import) |
| `downloader.py`, `diagnostic_stepik.py` | Самостоятельные пользовательские утилиты |

### В корне репозитория остаются только

| Файл / паттерн | Причина |
|---|---|
| `conftest.py`, `pyproject.toml` | Инфраструктура тестирования и сборки |
| `*.md`, `*.txt`, `*.toml`, `*.json.example` | Документация и шаблоны конфигурации |

### В `src/stepik_grader/core/` — всё остальное

Любой новый **внутренний модуль** (библиотечный код, не запускаемый пользователем напрямую) создаётся в `core/`, а не рядом с точками входа.

**Правило одной строки:**
> Если файл не запускается пользователем напрямую и не является конфигурацией
> уровня проекта — его место в `core/`, а не рядом с точками входа.

### В `tests/` — все тесты

Файлы `test_*.py` и `*_test.py` — только в `tests/`. Никаких тестовых файлов в корне.

## Документация: README как витрина, `docs/` как база знаний

Правило: **README — входная витрина**, а не свалка
технической памяти. В README живут только:

- описание проекта и бейджи;
- быстрый старт и установка;
- 4 режима работы и основные CLI-флаги;
- ссылки на подробную документацию.

Большие технические разделы живут в [`docs/`](docs/README.md), разложенной по
четырём направлениям — **перечень файлов здесь не дублируется**, он в индексе
каждого направления:

| Направление | Что туда | Индекс |
|---|---|---|
| `docs/use/` | справка пользователю: установка, режимы, флаги, веб, конфигурация | [`docs/use/README.md`](docs/use/README.md) |
| `docs/dev/` | устройство кода: архитектура, контракты, API, ADR (+ `design/` — спроектированное без кода) | [`docs/dev/README.md`](docs/dev/README.md) |
| `docs/agent/` | служебное для Claude Code: роли, очередь работ | [`docs/agent/README.md`](docs/agent/README.md) |
| `docs/archive/` | всё историческое: история разработки, архив CHANGELOG, разовые аудиты | [`docs/archive/README.md`](docs/archive/README.md) |

**Куда добавлять новый раздел.** Спроси, кто читатель: пользователь → `use/`
(+ строчка в README, если это заметная возможность); разработчик → `dev/`;
инвариант ядра → `CLAUDE.md`. Не уверен между `use/` и `dev/` — реши по вопросу,
на который отвечает текст: «как этим пользоваться» или «как это внутри».

**Чего в активном документе быть не должно:** журнала работ. `use/` и `dev/`
описывают, как всё работает **сейчас**. «Что сделано» → `CHANGELOG.md`, «что
предстоит» → GitHub Issues, «как шло» → `docs/archive/`. Числа тестов, покрытия
и размера глоссария не вписываются в прозу — они живут в бейджах README.

### Ссылки на issue: где можно, где нет

| Где | Номер issue | Почему |
|---|---|---|
| `CHANGELOG.md`, `docs/archive/` | обязателен | это логи: номер = ссылка на PR, в котором изменение приехало |
| `docs/audit/` | уместен | находки аудита привязаны к задачам по определению |
| `docs/dev/adr/` | уместен в «Контексте» | ADR отвечает «почему решили так» — задача часть ответа |
| `docs/dev/design/` | только как **требование** | номер-идентификатор согласованного контракта или пронумерованного набора требований, на который ссылаются другие документы и код |
| `CLAUDE.md`, `docs/agent/` | минимум | указатели вроде roadmap-issue |
| **`docs/use/`, `docs/dev/*.md`, README, SECURITY, CONTRIBUTING** | **нет** | отвечают «как работает сейчас»; когда и в каком эпике появилось — не нужно |

Правило машинное: `check_issue_tail_policy` в
[`scripts/check_docs_guardrails.py`](scripts/check_docs_guardrails.py) держит
объясняющие документы на нуле, а зонам `design/` и `agent/` задаёт бюджет
(`_DESIGN_TAIL_BUDGET` / `_AGENT_TAIL_BUDGET`). Бюджеты **снижают** по мере
чистки и не повышают: рост означает, что журнал снова пополз в объясняющий текст.

Если номер кажется необходимым — перепиши фразу так, чтобы она объясняла
компромисс, а не датировала его. Было: «фиксированный словарь тегов вместо
predicate-DSL — упрощение (issue NNN)». Стало: «фиксированный словарь тегов
вместо predicate-DSL — сознательное упрощение».

Не давай README снова разрастаться — проверяй это при ревью PR, добавляющих
документацию.

**Line-budget и link-check.** Правило «README — витрина» защищено
машинно: CI-job `docs-guardrails` (`.github/workflows/ci.yml`) запускает
[`scripts/check_docs_guardrails.py`](scripts/check_docs_guardrails.py), который

- **падает, если `README.md` превышает 220 строк** (константа
  `README_LINE_BUDGET` в скрипте — единственный источник числа; при изменении
  править и здесь);
- **проверяет подписи ссылок:** если текст ссылки выглядит как путь
  (`[docs/use/configuration.md § …]`), он обязан совпадать с фактической целью —
  иначе читатель копирует путь из подписи и попадает в никуда;
- **проверяет локальные Markdown-ссылки** README ↔ `docs/` ↔ корневые `*.md`:
  относительный путь должен вести на существующий файл, а якорь
  (`file.md#заголовок`) — на реально существующий заголовок. Внешние
  ссылки (http/https/mailto) осознанно не проверяются, чтобы CI не был флаки.

Запуск локально перед PR, добавляющим/меняющим документацию:

```bash
python scripts/check_docs_guardrails.py     # exit 0 — ок, 1 — нарушение
```

### Инварианты workflow

[`scripts/check_workflow_guardrails.py`](scripts/check_workflow_guardrails.py)
проверяет то, что ломается молча и проявляется один раз — в момент релиза:
порядок `checkout` → `download-artifact` в job'е публикации (обратный уносит
скачанный `dist/`, и релиз выходит без файлов), отказ публиковать пустой
`dist/`, `twine check` над собранными артефактами, объявленные `permissions` и
наличие `ready_for_review` в триггере `pull_request` (без него PR-черновик не
получает проверок).

```bash
python scripts/check_workflow_guardrails.py  # exit 0 — ок, 1 — нарушение
```

**Правило для любого guard'а: пустой вход обязан быть красным.** Проверка,
которая молча пропускает пропавший файл или переименованный job, зеленеет ровно
тогда, когда всё сломано, — и отличить её от отсутствующей нельзя. Поэтому у
каждого guard'а есть тест «входа нет → ошибка», а не только «всё хорошо → ок».

### Две линии работ: кто ещё трогает эти файлы

Работа идёт из двух окон — облачной сессии и локальной машины, — и они не видят
друг друга. Цена невидимости измерена: за одну сессию дважды бралась в разбор
задача, часть которой уже была сделана в соседнем окне и ждала мержа, а общие
файлы (`CHANGELOG.md`, разделяемые тесты) расходились конфликтами, заметными
только в момент мержа.

```bash
python scripts/check_work_overlap.py                # пересечения моей работы с чужой
python scripts/check_work_overlap.py --all          # обзор: все живые ветки и их файлы
python scripts/check_work_overlap.py --install-hook # pre-push предупреждение
```

**Почему без файла-реестра.** Живой файл со списком «кто что взял» пришлось бы
держать в репозитории — то есть он сам стал бы источником тех же конфликтов,
ради устранения которых заводится, и потребовал бы правил протухания записей,
которые некому применять (окно закрылось — запись осталась). Живые ветки на
`origin` уже отвечают на оба вопроса точнее: PR не существует без ветки, а
`git diff` даёт не «что человек написал в реестре», а фактический список файлов.
Запись нечего затирать — ветка смержена, пересечение исчезло само.

**Что делать с предупреждением.** Оно не запрет: два PR часто законно правят
разные части одного файла (в `CHANGELOG.md` это норма). Сигнал важен, когда
пересечение содержательное — тогда стоит согласовать порядок мержа, иначе второй
PR будет разводить конфликт вручную. Скрипт всегда завершается нулём и пуш не
блокирует.

## Быстрый старт

### Требования

- Python 3.12+
- Windows / macOS / Linux
- `.venv` (рекомендуется)

### Установка

```bash
python -m venv .venv
.venv\Scripts\activate      # Windows
# source .venv/bin/activate # macOS/Linux

pip install -e ".[dev]"      # runtime (requests/psutil/rich) + pytest/ruff/mypy
                              # ОБЯЗАТЕЛЬНО editable (src-layout): без
                              # него пакет stepik_grader не импортируется, и
                              # консольная команда stepik-grader не появится на
                              # PATH. Также: cli.__version__ читается через
                              # importlib.metadata из package-метаданных
                              # — без editable install падает
                              # на fallback "0.0.0+unknown"
```

> Нет отдельного `requirements.txt`: единственный источник зависимостей —
> `pyproject.toml`.

> Версия динамическая — её вычисляет `setuptools-scm` из git-тегов, статического
> поля `version` в `pyproject.toml` нет и заводить его нельзя (см.
> [§ Версионирование](#версионирование)). Package-метаданные при этом не
> обновляются сами: после `git fetch --tags`, нового тега или переключения
> ветки перезапусти `pip install -e .`, иначе
> `stepik-grader --version` будет показывать версию с момента последней
> установки.
>
> Запуск без установки: `pytest` работает благодаря `sys.path.insert(0,
> "src")` в `conftest.py`, но `python -m stepik_grader.grader` и
> `stepik-grader` требуют `pip install -e .`.

### Запуск тестов

```bash
pytest tests/ -v
pytest tests/ -q -n auto      # параллельно (pytest-xdist из extra dev)
```

Параллельный прогон — способ не ждать: замер на Windows дал 2 мин 30 с против
11 мин 42 с последовательно. В `addopts` флага нет намеренно, и вот что важно
знать перед тем, как его добавить:

- два теста `TestGradeBenchmarkReference` в `tests/test_web.py` сравнивают
  **относительную скорость** решений. Под шестью воркерами процессор занят, и
  вердикт `SLOWER`/`FASTER` перестаёт совпадать с ожидаемым — красное там про
  нагрузку, а не про код. Перед PR прогоняйте набор последовательно
  (`python scripts/preflight.py`), параллельный — для быстрой обратной связи;
- guard `_no_writes_outside_tmp` следит и за домашним каталогом, поэтому чужой
  процесс, тронувший файл в `~` во время прогона, обвиняет случайный тест.
  Длинный прогон ловит это чаще короткого — имя файла из сообщения стоит
  сверить с тем, что происходило на машине.

### Тесты пишут только в `tmp_path`

Файл, созданный мимо `tmp_path`/`tmp_path_factory`, остаётся на настоящем диске
и возвращается чужим падением недели спустя. Прецедент: тест `--serve`
передавал в `cli.main` выдуманный путь `--root /some/dir`. Пока `--root` задавал
только корень раздачи, это никого не смущало; когда он стал ещё и корнем
настроек, резолвер начал по нему читать и писать — на диске появился
`C:\some\dir` с `.grader_settings.json`, и этот файл потом уронил сам тест:
`record_history` резолвился в `False` вместо ожидаемого `True`. Только на
машине, где каталог успел появиться, — в CI тест был зелёным.

Поэтому guard'а два, и они ловят разное:

```bash
pytest tests/ -q                        # фикстура _no_writes_outside_tmp: след на диске = падение виновника
python scripts/check_test_isolation.py  # абсолютный путь в argv теста, ещё до прогона (и на Linux, где следа не будет)
```

Заведомо несуществующий путь тоже строится от `tmp_path`
(`tmp_path / "no_such_file.py"`): ветка «файла нет» проверяется та же, а создать
снаружи нечего.

### Пропуски: почему их видно поимённо

Часть тестов не выполняется на любой отдельно взятой машине — это нормально:
три ОС-специфичных backend'а песочницы, опциональные extra (`ruff`,
`playwright`, `hypothesis`), отсутствие графического дисплея. Ненормально
другое — не знать, сколько тестов молчит: набор из тысяч тестов даёт
уверенность ровно до тех пор, пока пропуски объяснены.

```bash
pytest tests/ -rs                       # что пропущено ИМЕННО в этом прогоне
python scripts/skip_inventory.py        # где вообще заложены пропуски и объяснены ли
```

Первое отвечает про конкретный прогон (`SKIPPED [n] file:line: причина`),
второе — статический инвентарь всех `skip`/`skipif`/`xfail`/`importorskip` с
причинами и сводкой. **У каждого пропуска обязана быть причина**: пропуск без
неё неотличим от забытого теста, поэтому скрипт (и тест
`tests/test_skip_inventory.py`) на таком падает.

### Покрытие: почему бейджа два

Одного честного числа не существует: под `--sandbox` в `core/sandbox/` живут
три ОС-специфичных backend'а, и на любой одной машине два из трёх недостижимы
в принципе. Поэтому README держит два бейджа, и они меряют разное.

| Бейдж | Что меряет | Порог |
|---|---|---|
| `Coverage (ubuntu)` | прогон на одной ОС; backend'ы чужих ОС исключены из знаменателя (CI генерирует `.coveragerc.ci` поверх базового `omit`) | 85 |
| `Coverage (all OS combined)` | объединение прогонов ubuntu + windows + macos + Linux-песочницы, без исключений по ОС — каждый backend измерен там, где он работает | 90 |

Настоящее покрытие проекта — второе число. Первое существует ради локального
прогона: `pytest` у контрибьютора на одной ОС не должен ложно краснеть из-за
кода, который эта ОС физически не может выполнить. **Порог 85 в
`pyproject.toml` не поднимать** — он откалиброван именно под этот случай.

Если данные какого-то среза в CI не приехали (типично — flaky privileged-job
песочницы), бейдж не публикуется вовсе: устаревшая дата честнее неверного
числа. Причина при этом пишется в лог job'а отдельным предупреждением —
и «артефакт не приехал», и «артефакт пуст/битый» названы поимённо.

### E2E-тесты (Playwright, опционально)

Смок-тесты реального веб-UI (`--serve`) через headless Chromium — свыше 20
сценариев по всем разделам workspace (режимы 2/1 грейдинга и a11y-озвучка,
«Функции в коде», глоссарий с deep-link, песочница с пошаговым плеером и
memory-диаграммой, «Прогресс», AI-подсказка с consent-гейтом, локализация
RU/EN) плюс регрессионный тест на XSS в `app.js` (экранирование в `esc()`,
экранирование в `esc()`). Живут в
`tests/e2e/`, **не входят**
в `pytest tests/` (см. `norecursedirs` в `pyproject.toml`) — отдельный
`playwright` нужен только для них, это dev-extra, а не runtime-зависимость:

```bash
pip install -e ".[e2e]"        # playwright>=1.40, отдельно от [dev]
playwright install chromium    # скачать браузер (один раз)
pytest tests/e2e/ -v           # запустить e2e-сьют явно
```

### Pre-commit хуки

```bash
pip install pre-commit
pre-commit install
```

Хуки ruff берут его **из активного окружения** (`language: system`), а не ставят
свою копию. Поэтому `pre-commit install` делается в том же venv, где выполнен
`pip install -e ".[dev]"` — иначе хук не найдёт `ruff` и честно упадёт.

Так версия ruff задана ровно в одном месте — `[project.optional-dependencies]
dev` в `pyproject.toml`, с верхней границей. Прежде она жила ещё и в `rev:`
хука, синхронизировалась вручную и разъехалась: в CI встал ruff 0.16, а хук
правил код правилами 0.15, из-за чего локальное «всё чисто» ничего не
гарантировало. `scripts/check_ruff_pin.py` (шаг в CI) следит, чтобы второй
источник не завёлся снова.

Кроме ruff хуки прогоняют guardrail-скрипты проекта — те же, что и CI: полнота
локалей, UI-строки без хардкода, импорты ES-модулей веб-слоя, пины в workflow'ах,
изоляция тестов, единственный пин ruff, согласованность версии в доках и ссылки
в Markdown. Каждый привязан к своим файлам, поэтому правка одного модуля не
зовёт проверку локалей; все восемь вместе укладываются в несколько секунд.
Прежде они жили только в CI, и о нарушении контрибьютор узнавал после пуша —
кругом в 5–10 минут вместо секунды на коммите.

Границу ruff поднимать отдельным PR, прогнав `ruff format --check .` на всём
дереве: минорный релиз меняет и правила, и форматирование.

## Соглашения по коду

Обязательные инварианты — union-типы вместо `Optional`/`List`, `from __future__
import annotations` в новом файле, `pathlib` вместо `os.path`, `Path` в
путь-сигнатурах, `sys.executable` вместо строки `"python"`, `__all__` в новых
модулях, вывод через `_console`, никаких голых `except:` — живут в
[`CLAUDE.md § Стиль кода`](CLAUDE.md). Здесь только то, чего там нет:

- **Docstrings** публичных функций — краткий Google-style.
- Все импорты в начале файла; lazy import — лишь с явной причиной в комментарии
  (например, разрыв DAG-ребра).
- Константы модуля — в начале файла, до функций.
- Строгость `mypy` (`disallow_untyped_defs`, `disallow_incomplete_defs`,
  `check_untyped_defs`, `warn_return_any`, `ignore_missing_imports`) задана в
  `[tool.mypy]` — не ослабляйте её точечными `# type: ignore` без объяснения.

Паттерн имён файлов решений (`task.py`, `task1.py`, `task1_2.py`, `task_12.py`) —
в [`docs/use/configuration.md`](docs/use/configuration.md).

## Процесс внесения изменений

1. Создайте ветку: `git checkout -b feat/your-feature`
2. Внесите изменения с тестами
3. Обновите `CHANGELOG.md` — запись в **каждом** PR, без исключений для
   рефакторингов (одна строка на изменение). Пишите её в раздел
   `## Буфер (разобрать при релизе)` строкой вида `- Fixed: что изменилось
   (#PR)`, а не в `### Added`/`### Fixed` напрямую: так параллельные PR не
   дерутся за одно место в файле (git настроен сливать `CHANGELOG.md` обеими
   сторонами, см. `.gitattributes`). По секциям буфер разбирают при релизе.
   CI запись не проверяет: правило держится на ревью, поэтому пропуск замечают
   уже при релизе, когда восстанавливать её задним числом дороже всего
4. Прогоните `pytest tests/ -v`
5. Прогоните `ruff check .` и `ruff format --check .`
6. Прогоните `mypy src/stepik_grader scripts`
7. **Опционально:** `pre-commit run --all-files` — только если ставили
   `pre-commit` отдельно (в extra `[dev]` его нет и в CI он не запускается, см.
   [§ Pre-commit хуки](#pre-commit-хуки)); хуки прогоняют тот же ruff, что и
   шаг 5, плюс guardrail-скрипты, которые иначе краснеют уже после пуша
8. Создайте Pull Request в `main`

## Когда дефект считается исправленным

Правило родилось из ревизии: аудит 2026-08-10 проверил находки предыдущего
аудита по коду и нашёл **десять живых дефектов**, числившихся закрытыми. Все
десять принимались одинаково — по диффу, без запуска. Отсюда требования 1–3;
четвёртое добавляет двухоконный режим работы.

**1. Фикс проверяется на той же поверхности, где найден дефект.** Нашли
прогоном — закрывать прогоном; увидели в браузере — открыть браузер и убедиться;
поймали на чистой установке — проверить на чистой установке. Чтение собственного
диффа доказательством не считается: дифф показывает, что вы поменяли, а не что
поведение стало верным.

**2. Все вызовы класса, а не один.** Самый частый способ, которым находка
возвращается: фикс применён к одному месту из нескольких. Реальные примеры этого
проекта — `errors="replace"` добавили в `mode_detector.py`, но не в
`test_loader.py`; проверку согласия на AI закрыли в CLI, но не в вебе; обрезку
вывода сделали в ветке `WA`, но не в `[ERROR]`. Перед закрытием — `grep` по
шаблону дефекта и явный ответ: покрыты все места или почему остальные не дефект.

**3. Регрессионный тест, падающий на старом коде.** Без него дефект вернётся при
следующем рефакторинге и будет найден только очередным аудитом. Тест обязан
краснеть до фикса — проверьте это, а не предполагайте.

Проверять **полу-откатом**: новые имена (классы, функции, параметры) оставить,
убрать только поведение. Откат всего `src/` даёт красноту по `ImportError` — то
есть доказывает лишь «тест ссылается на новый код», а не «тест ловит дефект».
Живой случай: краснота проверялась полным откатом, и все тесты падали на
импорте новых имён — про поведение это не говорило ничего.

**4. Поверхность, недоступная в вашем окне, не закрывается «по коду».** Работа
идёт в двух окнах: облачная сессия со свежим клоном из git (секретов, живой сети
до Stepik и накопленной истории обучения там нет) и локальная машина, где продукт
работает как у пользователя. Если дефект живёт на поверхности второго окна —
скачивание задач, OAuth, реальная история и всё, что по ней считается, GUI-лаунчер,
не-Linux ОС, — фикс из облака остаётся **непроверенным**, как бы убедительно ни
читался дифф. Такой PR мержится, но issue закрывается только после прогона в том
окне, где поверхность настоящая; до тех пор в issue висит готовый список проверок:
команда, ожидаемый результат, что считать провалом. Раскладка окон и шаблон такого
списка — [`docs/agent/environments.md`](docs/agent/environments.md).

**Правка в `src/` проверяется ВСЕМ набором тестов, а не файлом рядом с ней.**
Выборка `-k` и «свой» тестовый файл показывают только то, о чём вы уже
подумали. Чужие тесты патчат наши имена
(`monkeypatch.setattr(module, "ClassName", fake)`), поэтому переименование или
подмена класса ломает их молча — и именно молча, потому что в изменённом
модуле всё зелёное. Живой случай: замена `HTTPServer` на `_OAuthHTTPServer`
уронила четыре теста в **другом** файле; автор правки прогнал только свой файл
и узнал о поломке из CI. Это тот же класс, что и пункт 2 выше, только с другой
стороны: там фикс не дошёл до всех вызовов, здесь — проверка не дошла до всех
зависимых.

**Читайте вывод проверок целиком, а не хвост.** `pytest`, `ruff` и `mypy`
печатают итог в разных местах: у `ruff` провал уходит выше последних строк, и
`tail -2` показывает бодрое `Success` от `mypy`, когда линтер уже красный.
Живой случай: PR ушёл в CI с девятью красными job'ами из-за `F401`, который
лежал в том же локальном выводе — просто выше того, куда смотрели. Проверяйте
код возврата или весь вывод; «зелёный, потому что посмотрели не туда» — тот же
класс, что и «зелёный, потому что проверять было нечего».

**Что писать в PR.** Не «исправлено», а как проверяли: команда, наблюдаемый
результат до и после. Если поверхность недоступна — скажите это прямо в PR и
опишите, что именно осталось непроверенным и в каком окне это доказывается.

Отклонить находку — нормальный исход, но он тоже фиксируется: в документе аудита
пишется причина. Молча удалённая находка возвращается следующим аудитом.

## Версионирование

**Это НЕ SemVer.** Своя схема: тег ставится только на границе MINOR (все теги
имеют вид `vX.Y.0`), PATCH — счётчик принятых изменений после тега, версия
пакета вычисляется из git-тегов через `setuptools-scm`, а `version` в
`pyproject.toml` править **нельзя** — статической строки там нет.

Полная политика — [`docs/dev/versioning.md`](docs/dev/versioning.md): следствия
схемы, release- vs dev-форма, когда тегировать, блокирующая ротация CHANGELOG
перед тегом, CI-защита от дрейфа.

## Известные ограничения

- Memory measurement через `psutil` может давать нулевые значения для очень быстрых процессов.
