# Гейты: перед пушем и перед мержем

Канон двух команд, которые заменяют «не забыть» на «проверено машиной»:

```bash
python scripts/preflight.py            # перед коммитом и пушем
python scripts/check_pr_ready.py 1100  # перед мержем PR
```

Документ отвечает на три вопроса: **зачем гейт вообще** (иначе он воспринимается
как лишний шаг и обходится), **что именно он проверяет** и **что делать, когда
он красный**. Компактный триггер — в [`../../CLAUDE.md`](../../CLAUDE.md);
детали не дублировать там.

---

## Почему не «ещё один пункт в чек-листе»

Разбор сессии 2026-08-13 дал одиннадцать инцидентов. Существенно
здесь то, что **девять из них — не незнание правила, а его пропуск**: правило
«прогонять ВЕСЬ набор» уже было в `CLAUDE.md`, когда профильная выборка молча
сломала чужой тест; правило «ветвиться от свежего main» — тоже, когда гейт
прогнали на устаревшей ветке и `main` покраснел после мержа.

Отсюда принцип, по которому здесь всё устроено:

> **Правило, которое надо вспомнить, соблюдается ровно до первой спешки.
> Правило, которое проверяет команда, соблюдается всегда.**

Поэтому текст чек-листа переписан в код, а не дополнен ещё одним пунктом.
Каждая проверка ниже названа вместе с инцидентом, из которого выросла: правило
без причины выглядит формальностью, и его первым обходят.

## `preflight.py` — перед пушем

| Проверка | Инцидент, из которого выросла |
|---|---|
| ветка не `main` | прямые коммиты в `main` запрещены контрактом |
| **ветка от свежего `origin/main`** | гейт прогнали на ветке, созданной до чужого мержа: локально 18 passed, на `main` красные все девять ubuntu-джобов. «Зелено на моей ветке» ≠ «зелено после мержа» |
| **имя ветки не занято** | дважды взята работа соседнего окна; во второй раз совпало и имя ветки — `push` отлетел «tip is behind», а правка чуть не уехала в чужой PR |
| пересечение файлов с чужими ветками | общие файлы расходятся конфликтами, и узнаётся это в момент мержа (`check_work_overlap.py`) |
| **запись о изменении** | требуется в каждом PR, но CI её наличие не проверяет — держалась на памяти и чек-листе. Принимается фрагмент `changelog.d/<slug>.<секция>.md` (основная форма) либо строка в `## Буфер` — чтобы ветки, начатые до перехода на фрагменты, не краснели на ровном месте |
| карта «кто ссылается на правку» | тестовый файл искали по угаданному имени, не нашли, положили тесты в другой файл — и молча сломали `test_loader.py`. `grep` по имени функции ищет тех, кто патчит наши имена |
| один прогон за раз (`.git/preflight.lock`) | два параллельных `pytest` исчерпали дескрипторы: 72 «падения», все средовые (`OSError WinError 6/50` в тестах с subprocess). Полдня разбора регрессии, которой нет |
| весь набор + **вывод целиком в файл** | `pytest … \| tail -8` в фоне отбросил всё, кроме хвоста, и шестиминутный прогон пришлось повторять. Скрипт всегда пишет полный лог в `.git/preflight-logs/` |
| `ruff check` · `ruff format` · `mypy` | зеркалит CI, чтобы красное находилось до пуша, а не в матрице |

Режимы:

```bash
python scripts/preflight.py                # всё, включая полный pytest
python scripts/preflight.py --branch-only  # только гигиена ветки — ДО начала работы
python scripts/preflight.py --no-tests     # правки только в докáх
python scripts/preflight.py --force-lock   # перехватить протухшую блокировку
python scripts/preflight.py --install-hook # pre-push хук, отклоняющий непроверенный коммит
```

`--branch-only` дешёвый и запускается **до** работы, а не после: он отвечает на
вопрос «эту задачу уже кто-то делает?» тогда, когда ответ ещё что-то меняет.

### Штамп и pre-push хук

Удачный прогон пишет `.git/preflight-stamp.json` с **отпечатком содержимого**
рабочего дерева — отслеживаемые файлы плюс новые, ещё не добавленные в индекс.
Хук (`--install-hook`) сравнивает отпечаток с текущим и отклоняет пуш, если
уехать собирается **не то состояние, которое проверяли**.

Привязка к содержимому, а не к `HEAD`, — не тонкость, а исправленный дефект
первого же живого применения: прогон всегда идёт **до** коммита, поэтому штамп
на SHA обесценивался ближайшим `git commit`, и хук отклонял пуш ровно того
состояния, которое сам же и проверил. Гейт, который мешает при правильном
порядке действий, обходят на второй день.

Аварийный выход — `PREFLIGHT_SKIP=1 git push …`: он существует для срочного
фикса там, где прогон физически негде сделать, и остаётся осознанным решением
человека, а не значением по умолчанию.

### Где лежат штамп, блокировка и логи

Пути выше (`.git/…`) верны для обычного клона. Точный каталог гейт спрашивает у
самого git, а не собирает из имени `.git`: в рабочем дереве `git worktree` по
этому имени лежит **файл** со строкой `gitdir: …`, а настоящий каталог — в
основном репозитории. Собранный путь там не просто вёл не туда — гейт **падал**
`FileExistsError` до первой проверки, потому что `mkdir(exist_ok=True)` прощает
существующий каталог, а не файл.

Штамп и логи — у каждого рабочего дерева свои (`git rev-parse --git-dir`):
штамп описывает содержимое конкретного дерева, и общий файл означал бы, что
прогон в одном окне обесценивает штамп другого. Блокировка, наоборот, одна на
репозиторий (`--git-common-dir`) — она защищает не дерево, а дескрипторы
машины, и два параллельных `pytest` роняют тесты с subprocess одинаково,
запущен ли второй прогон из основного каталога или из соседнего worktree.
Отчёт печатает абсолютные пути, так что искать их вручную не нужно.

## `check_pr_ready.py` — перед мержем

Инцидент: PR смержили, когда **9 проверок из 14 были `queued`/`in_progress`**.
Проверка звучала разумно — «нет `failure` и нет `pending` → мержим», — но сразу
после `git push` GitHub ещё не успевает создать check-runs, и REST отдаёт
**пустой список**. На пустоте это условие выполняется идеально.

Три правила, закодированные в скрипте:

1. **Пустой или неполный список проверок — «CI не стартовал», а не «зелено».**
   Поэтому смотрится не только `/commits/{sha}/check-runs`, но и
   `/actions/runs?head_sha=…`: пока прогон в `queued`/`in_progress`, часть
   джобов ещё не существует, и судить по ним нельзя.
2. **Набор сверяется с эталоном** — джобами тех прогонов последнего коммита
   `main`, чей workflow объявляет триггер `pull_request`. Эталон живой, а не
   константа в коде: список джобов меняется вместе с `ci.yml`, и зашитое число
   устарело бы молча. Фильтр по триггеру обязателен: на `main` есть прогоны от
   workflow с `issue_comment`/`workflow_dispatch`, которых на PR не бывает
   никогда, и без фильтра гейт краснел бы всегда — а гейт, который краснеет
   всегда, обходят.
3. **Только REST.** `gh pr view` / `gh pr checks` ходят через GraphQL, и поллинг
   в цикле выжигает квоту 5000/час до нуля — посреди работы `gh` просто
   перестаёт отвечать, со сбросом через полчаса. Опрашивать не чаще, чем раз в
   45–60 секунд.

```bash
python scripts/check_pr_ready.py 1100          # вердикт: 0 — можно мержить
python scripts/check_pr_ready.py 1100 --json   # то же машинно
```

Транспорт: `gh api` (локальное окно, где `gh` уже авторизован), иначе прямой
REST с `GH_TOKEN`/`GITHUB_TOKEN` из окружения.

## Очередь мержа: что за чем

Открытых PR обычно несколько, и они **не независимы**: каждый мерж в `main`
отбрасывает остальные назад.

Главный источник конфликтов убран — записи релиза теперь **файлами**
(`changelog.d/<slug>.<секция>.md`), а не строками в общем `CHANGELOG.md`. Причина
перехода: `merge=union` из `.gitattributes` спасает **только локально** —
проверено дважды, `git merge origin/main` сливал буфер без вмешательства ровно
тогда, когда GitHub уже помечал тот же PR `mergeable_state=dirty`. Полагаться на
union при мерже через GitHub нельзя, а два файла с разными именами не
конфликтуют по построению.

Отсюда диагностический признак, который иначе читается как «CI сломался»:

> **Конфликт = проверок нет вовсе.** Прогон на PR идёт по merge-коммиту; если
> слияние невозможно, GitHub его не строит, и check-runs не создаются. Пустой
> список проверок при `dirty` означает «сначала разведи конфликт», а не «CI не
> запустился».

Порядок:

1. **Первым — то, что чинит красный `main`.** Пока база красная, все остальные
   PR красные тоже, и их проверки ничего не говорят о них самих.
2. **Затем — PR, который держит общий файл.** Кто пересекается, показывает
   `python scripts/check_work_overlap.py`; мержится первым тот, чью правку
   остальным придётся учитывать.
3. **Остальные — по готовности** (`check_pr_ready.py` → «готов»).

Порядок не хранится, а **вычисляется**: `python scripts/gh_rest.py queue`
печатает очередь из состояния API — кто голова, кто сколько ждёт, кто с кем
делит файлы. Реестра (меток, табло, файла состояния) нет намеренно: хранимый
порядок разъезжается между окнами и протухает молча. Пункт 1 из API не выводится,
поэтому про красную `main` `queue` говорит отдельной строкой и оставляет выбор
человеку.

**Из `main` обновляется только голова очереди** — `git fetch origin main &&
git merge origin/main`, затем push (или `gh_rest.py update-branch`, или кнопка
«Update branch»). Остальные стоят неподвижно.

Почему не «обновить всех сразу», как было раньше: массовое обновление
**гарантирует**, что обновлённые PR устареют снова следующим же мержем. При N
готовых PR это N(N−1)/2 обновлений против N — при шести PR 21 холостой прогон
против 12 полезных. Стоящий в очереди PR выглядит «забытым CI» ровно потому, что
его очередь ещё не подошла; `check_pr_ready.py` в этом случае отвечает «ждать» и
называет, кто впереди.

Практическое следствие: **снятие черновика перезапускает прогон с нуля** — все
проверки создаются заново, и ждать их приходится второй раз. Поэтому черновик
снимается **сразу после создания PR**, а не когда прогон уже позеленел;
«сниму перед мержем» звучит аккуратно, а стоит лишнего круга ожидания, за
который соседний мерж успевает сделать ваш PR `dirty`.

## Квота GitHub API: дорого не `gh`, а GraphQL

Прежнее правило называло команду — `gh pr view`/`gh pr checks` — и потому не
сработало, когда квоту выжгло другое. Замер в момент исчерпания:

```json
"core":    { "limit": 5000, "remaining": 4998, "used": 2 },
"graphql": { "limit": 5000, "remaining": 0,    "used": 10724 },
"search":  { "limit": 30,   "remaining": 30,   "used": 0 }
```

REST — **2 запроса из 5000**. Search — ноль. GraphQL — **10 724 при лимите
5000**, перерасход вдвое. При этом `gh pr view` не вызывался ни разу: в облачном
окне `gh` нет вовсе, и правило, написанное про него, читалось как «меня не
касается». Отсюда переформулировка по механизму:

- **Через GraphQL идёт почти всё, чем работает агент** — списки issue и PR,
  чтение issue/PR, поиск, правка PR. Признак — курсорная пагинация (`pageInfo`,
  `endCursor`) в контракте инструмента. Имя команды тут ни при чём.
- **Лимит GraphQL — 5000 *points* в час, а не 5000 запросов.** Один вызов,
  тянущий три десятка issue со всеми полями, стоит сотни. «Пять тысяч
  обращений» — иллюзия, до неё не доживают.
- **Кастомные поля стоят отдельно.** Семантический поиск issue подтягивает
  значения полей Projects на каждый результат; ошибка при исчерпании была
  буквально `failed to fetch issue field values`.
- **Гейты ходят через REST, и это правильно.** `check_pr_ready.py` через
  `gh api` — 2 запроса из 5000. Не «оптимизировать» его на GraphQL.

**Одни операции над PR идут по REST, другие — по GraphQL, и это видно на
практике.** При обнулённом GraphQL создание PR проходит, а снятие черновика —
нет. Практическое следствие: **создавать PR сразу не-черновиком**; тогда
GraphQL-вызов не нужен вовсе, и заодно не тратится круг ожидания на перезапуск
проверок (см. выше про снятие черновика).

### Защита `main`: что именно включено

Вариант B реализован не галочками classic-защиты, а **ruleset**'ом
«main: зелёный CI на актуальном состоянии»:

| настройка | значение | зачем |
|---|---|---|
| обязательные проверки | 11 имён: `docs-guardrails`, `static`, `supply-chain`, `sandbox-linux`, `e2e`, `test` на трёх ОС × 3.12/3.13 | зелёный CI как условие мержа |
| «up to date» (`strict`) | включено | зелёный отвечает про актуальное состояние `main`, а не про вчерашнее |
| bypass | **пусто** | правило действует и на владельца — иначе оно снова держится на памяти |
| запрет удаления и force-push | включено | история `main` не переписывается |

Что из этого следует на практике:

- **До включения `auto-merge` был бесполезен и опасен.** Без обязательных
  проверок GitHub считает PR готовым мгновенно: два PR уехали в `main`, не
  дождавшись CI, — при том что канон предписывал включать auto-merge.
- **3.14 обязательной не сделана**: комбинации под `continue-on-error`, они не
  должны блокировать мерж.
- **Имена джобов входят в ruleset дословно.** Переименование комбинации матрицы
  в `ci.yml` (например, смена версии Python) обязано сопровождаться правкой
  ruleset: иначе PR будет вечно ждать проверку, которой больше не существует.
- **Бейджи это не ломает**, потому что они больше не коммитятся в `main` —
  публикация уехала в ветку `badges` (см. `CLAUDE.md § Метрики`). Обход для
  GitHub Actions личному репозиторию недоступен: `422 Actor GitHub Actions
  integration must be part of the ruleset source or owner organization`.

### Транспорт конвейера — `scripts/gh_rest.py`

Правило «ходить по REST» не работает, пока REST-доступ приходится каждый раз
собирать заново. Поэтому операции конвейера собраны в один модуль, и агентская сессия
работает с PR через него, а не через
MCP-инструменты:

```bash
python scripts/gh_rest.py pulls                # открытые PR: ветка, автор, черновик
python scripts/gh_rest.py checks <PR>          # проверки PR + занятость main
python scripts/gh_rest.py compare <PR>         # отстала ли ветка от базовой
python scripts/gh_rest.py update-branch <PR>   # подтянуть main в ветку PR
python scripts/gh_rest.py merge <PR>           # squash-мерж
python scripts/gh_rest.py issue <N>            # состояние issue, заголовок, метки
python scripts/gh_rest.py create-issue --title  # завести issue (--label, --body)
python scripts/gh_rest.py close-issue <N>      # закрыть с причиной (--reason)
python scripts/gh_rest.py label <N> --add|--remove   # метки
python scripts/gh_rest.py comment <N> "текст"  # комментарий к issue или PR
python scripts/gh_rest.py comments <N>         # прочитать обсуждение
python scripts/gh_rest.py runs --branch main   # прогоны ci.yml по ветке
python scripts/gh_rest.py run-jobs <RUN>       # job'ы прогона: что именно упало
python scripts/gh_rest.py cancel-run <RUN>     # отменить зависший — он держит очередь
python scripts/gh_rest.py rate                 # остаток квоты; сам её не тратит
```

Что важно знать до первого запуска:

- **`gh` CLI не нужен.** В облачной сессии его нет вовсе — запрос уходит на
  `urllib` с токеном из `GH_TOKEN`/`GITHUB_TOKEN`. В локальном окне, где
  переменных обычно не заведено, а `gh` авторизован через keyring, токен один
  раз спрашивается у `gh auth token`; сам этот вопрос квоту не тратит.
- **Исчерпанная квота — код возврата 2, а не 1.** «Ждать» и «сломалось» —
  разные исходы, и агент, читающий первое как второе, начинает повторять;
  счётчик попыток растёт и после нуля. Время сброса модуль печатает сам.
- **`ETag` включён для GET.** Ответ `304 Not Modified` GitHub в лимит не
  засчитывает вовсе, поэтому повторный опрос статусов дешевле первого.
- **`check_pr_ready.py` ходит тем же транспортом** — токен, распознавание
  квоты и условные запросы одинаковы у всего конвейера.
- **Работа с issue и прогонами — тоже по REST.** Закрыть, разметить,
  прокомментировать, посмотреть прогон и отменить зависший. Причина закрытия
  обязательна: «сделано» и «не будем делать» — разные исходы, а трекер, где всё
  закрыто без разбора, перестаёт отвечать на вопрос «что мы решили не делать».
- **PR создаём через MCP, а не этой обёрткой.** Авторство должно быть
  авторским: в облачной сессии токены проксированы — `GET /user` отвечает
  человеком, а **запись атрибутируется приложению**, и PR получает автора
  `claude[bot]`. Workflow код-ревью для таких PR не работает вовсе («Workflow
  initiated by non-human actor»), обязательная проверка `claude-review`
  краснеет, мерж-гейт встаёт. Заранее это не распознать, поэтому `create-pr`
  сверяет автора **по ответу** и отказывается с ненулевым кодом. Экономии на
  этом почти нет: PR создаётся однажды, а платит окно за повторный опрос
  статусов — его REST и забирает.
- **Логи job'а из облачной сессии не читаются.** Эндпоинт отдаёт редирект на
  хранилище, а тот хост закрыт egress-политикой (`403` от прокси). `run-jobs`
  показывает, ЧТО упало; за текстом падения — MCP-инструмент или браузер.
- **Чего в REST нет — остаётся за MCP.** Sub-issues и `auto-merge`
  (`enablePullRequestAutoMerge`) существуют только в GraphQL; это исключение, а
  не лазейка для остальной рутины.
- **Мержить из облачной сессии нельзя вовсе.** Не «нет прав у токена» и не
  «настройка репозитория» — ограничение **типа сессии**:

  ```
  403 {"message": "Merging into a protected base branch is not permitted
                   for this session type."}
  ```

  Значит подкоманда `merge` полезна в локальном окне, а из облака PR доводится
  до зелёного и передаётся человеку. Пробовать обход бессмысленно: ответ не
  зависит ни от квоты, ни от состояния PR.

  Отдельно стоит помнить, **как** этот отказ выглядел: модуль печатал «квота
  исчерпана — сброс в ?, через 0 мин 0 с», потому что отсутствующий
  `x-ratelimit-remaining` читался как ноль. Совет был ровно обратный нужному —
  ждать там, где ждать нечего. Признак подмены виден в самом тексте: время
  сброса «?» и нулевое ожидание означают, что заголовков лимита не было, то
  есть про лимит сервер ничего и не говорил.
- **Корпоративный TLS-прокси роняет транспорт на Python 3.13 — и это видно.**
  Флаг `VERIFY_X509_STRICT`, включённый там по умолчанию в
  `ssl.create_default_context()`, требует от CA-сертификата расширения
  `keyUsage` по RFC 5280, а у перехватывающих прокси его часто нет. Симптом
  коварен: при одном и том же бандле, том же OpenSSL и исправной сети на 3.11
  всё работает, на 3.13 приходит `certificate verify failed: CA cert does not
  include key usage extension`.

  Модуль такой отказ **распознаёт, объясняет и останавливается** — сам проверку
  не ослабляет. Ослабление осталось возможным, но включает его
  окружение: `GH_REST_RELAXED_CA=1`, с предупреждением на каждый запрос;
  что именно снимается и чем это грозит —
  [SECURITY.md § Транспорт агентских скриптов](../../SECURITY.md#транспорт-агентских-скриптов-scriptsgh_restpy).
  `SSL_CERT_FILE` здесь не лечит: бандл уже нужный, не проходит его оформление.

  Практический вывод для окна: гоняйте конвейер тем интерпретатором, где флаг
  выключен, — иначе первым же запросом получите отказ. Это дороже прежнего
  тихого повтора ровно на одно осознанное решение, и в том и смысл: отказ
  транспорта возвращает окно к MCP, то есть к GraphQL, а молчаливое ослабление
  проверки — цена, которую за это не платят.

### Практики экономии

- Не проверять дубли поиском на каждый заводимый issue: хватает **одного**
  списка открытых issue в начале работы, с полями `number, title`.
- Запрашивать минимальный набор полей — без `body` и `field_values` там, где они
  не нужны.
- Брать небольшие страницы.
- Не перечитывать в одной сессии то, что уже прочитано.

### Исчерпав квоту — остановиться, а не повторять

Счётчик продолжает расти после нуля: 10 724 против лимита 5000 — ровно этот
случай, вызовы шли дальше и дальше считались. Повтор не «пробует ещё раз», он
отодвигает сброс.

**Квота общая на аккаунт.** Работают три окна — расход складывается, и интервалы
опроса увеличиваются кратно числу окон.

### Диагностика — первым шагом, а не после часа догадок

```bash
gh api rate_limit --jq '.resources | {core, search, graphql}'   # локальное окно
```

В облачном окне `gh` нет — тот же ответ берётся напрямую:

```bash
curl -sS -H "Authorization: Bearer $GH_TOKEN" https://api.github.com/rate_limit
```

Три кошелька видно раздельно: остаток и время сброса. По времени сброса понятно
и то, когда началось окно, — то есть кто его тратил.

### Окно-наблюдатель за PR

Наблюдение в цикле — самый дорогой режим работы с API, и именно ему нужны явные
требования.

- **Событие вместо опроса.** Если среда даёт подписку на активность PR
  (`subscribe_pr_activity`), наблюдатель обязан использовать её: события
  приходят без единого запроса. В агентской сессии подписка включается
  автоматически при создании PR — падения CI и комментарии ревью приезжают
  сами. Опрос — резервный вариант, а не основной.
- **Опрос — только по REST**: `/repos/{owner}/{repo}/pulls`, `.../commits`,
  `.../status`. GraphQL в цикле запрещён.
- **Условные запросы (`ETag` / `If-None-Match`).** Ответ `304 Not Modified`
  **не расходует лимит**: пока в PR ничего не менялось, опрос бесплатен. У
  GraphQL такого механизма нет — ещё одна причина не водить его в цикл.
- **Дельта вместо полного обхода.** Список PR с сортировкой по `updated`;
  внутрь заходить только к тем, у кого `updated_at` изменился с прошлого
  прохода. Иначе шесть открытых PR дают 7+ вызовов за проход, а раз в минуту —
  под тысячу вызовов в час.
- **Интервал наблюдателя — минуты, а не секунды**, и он растёт с каждым
  дополнительным активным окном.

CI сюда не относится: там свой `GITHUB_TOKEN` с отдельным лимитом, и
единственный API-скрипт в workflow делает один вызов за прогон.

## Маршрут при исчерпании лимитов

Правило выше отвечает на вопрос «что не делать». Этот раздел — про «что делать
вместо», потому что 19 августа 2026 упор в лимит случился четырежды за день, и
каждый раз разбор начинался с нуля.

Ответ почти всегда один: **работать можно, и почти всем**. Останавливается не
работа, а публикация.

### Транспорт важнее объёма

| | REST (`core`) | GraphQL |
|---|---|---|
| Что считает лимит | **запросы** | **points** |
| Цена операции агента | 1 | ≈ 300 |
| Пятьдесят PR за день | доли квоты | три квоты |

Раньше рутина шла через `gh api` — то есть по REST, и пятьдесят PR в день
проходили незаметно. Облачная агентская сессия `gh` не имеет вовсе и по
инструкции окружения ходит через MCP, то есть по GraphQL. **Изменился не объём
работы и не проект — изменился транспорт.** Отсюда и модуль
`scripts/gh_rest.py` (см. выше), и разделение: конвейер по REST, а
MCP-инструменты — только для того, чего в REST нет.

> **Поправка к цифрам.** У токена этого проекта лимит `core` — **15 000**
> запросов в час, а не 5000: замер 19.08 показал `core: 14977/15000` при
> `graphql: 0/5000`. То есть запас REST втрое больше, чем можно предположить по
> документации для персональных токенов, — а исчерпывается всё равно GraphQL.

### `used` считает попытки, а не успехи

`used: 10 853` при лимите 5000 не значит «сделано десять тысяч операций». Это
5000 успешных плюс 5853 отказа `403`. **Сверх лимита работа не проходит** — она
отбивается, а счётчик всё равно растёт.

Практическое следствие важнее арифметики: агент в исчерпанной квоте не
«работает с руганью», он не работает вовсе и оставляет **полусделанные
состояния** — ветка запушена, PR не открыт; PR создан, метки не проставлены;
issue закрыт, комментарий не ушёл. Это хуже простоя, и поэтому останавливаемся.

### Граница проходит по линии «git против API»

| Работает при нулевой квоте | Требует API |
|---|---|
| читать и писать код, гонять тесты | создать PR |
| коммитить | читать статусы CI |
| **пушить ветки** (`git push` — git-протокол, не API) | мержить |
| сравнивать и мержить локально | issue, метки, ревью |

Проверено 19.08: при нулевом GraphQL окно спокойно сделало фикс, подтянуло
`main` и запушило ветку. Упёрлось бы только в открытие PR.

**Режим работы при исчерпании — копить ветки**, публиковать пачкой после сброса
или из локального окна. Не «сидеть и ждать».

### Что кончилось → куда идти

| Кончилось | Как узнать | Недоступно | Доступно |
|---|---|---|---|
| **GraphQL** (points/час) | `remaining: 0`; ошибка `failed to fetch issue field values`; пропала карточка PR в интерфейсе | чтение и списки issue/PR через MCP, `gh pr view`, `gh pr checks` | REST: `scripts/gh_rest.py`, `check_pr_ready.py`, `gh api`; браузер; git; вся локальная работа |
| **REST core** (запросы/час) | `403` на `gh api` | гейты и скрипты, ходящие в GitHub | браузер, git, локальный прогон, код |
| **Search** (30/мин) | `403` на поиске | поиск issue | обычные списки и всё остальное |
| **Очередь Actions** | прогоны висят `queued` или отменяются | быстрый CI | локальный `preflight.py`, ревью, документация |
| **Лимит сессии агента** | окно перестало отвечать | работа через агента | ревью в браузере, локальный прогон, Фаза L |

### Работы, не зависящие от лимитов GitHub

- код по заведённым issue и полный `python scripts/preflight.py`;
- `pytest tests/e2e/` с Playwright;
- документация, `changelog.d`, `HISTORY.md`;
- **ревью PR в браузере** — квота касается доступа по токену, человек в
  веб-интерфейсе не ограничен ничем;
- **локальная подготовка и прогон Фазы L** — там другое API, степиковское, и
  это работа, которую не может выполнить ни одно облачное окно.

### Хроника

Не летопись, а доказательная база к правилам выше: три строки на инцидент.

- **19.08.2026** — GraphQL четырежды в ноль (10 724 · 3 111 · 10 272 · 10 853
  при лимите 5000); REST за тот же день — десятки запросов из пятнадцати тысяч.
  Источники: сперва окно-наблюдатель в цикле опроса PR (снято), затем
  окно-исполнитель, ведущее конвейер мержей через MCP. Корень — транспорт, а не
  объём: у облачных сессий нет `gh`, и всё уходило по GraphQL. Решение —
  `scripts/gh_rest.py`.

## Что гейты не ловят — и почему это записано здесь

Три инцидента той же сессии механической проверке не поддаются; они остаются
правилами, но названы явно, чтобы не выглядели «и так понятно»:

- **Пуш в ветку чужого PR.** Конфликт локалей выглядел тривиальным («оставить
  обе строки»), и правку внесли прямо в ветку соседнего окна. Гейт видит только
  совпадение имени ветки, а не намерение. Правило: **в чужую ветку не пушить** —
  сообщить владельцу, что и как разрешать.
- **Escape-последовательности через bash-heredoc.** `\n` внутри Python-строки,
  записанной heredoc'ом, дважды превращался в настоящий перевод строки →
  `SyntaxError: unterminated string literal`. Правило: код с экранированием
  писать **файлом**, а не heredoc'ом.
- **«Тест краснеет до фикса», доказанное откатом всего `src/`.** Тесты падали на
  `ImportError` — то есть доказано лишь «тест ссылается на новый код». Правило:
  краснота проверяется **полу-откатом** — новые имена оставить, убрать только
  поведение.

## Порядок работы целиком

```
1. python scripts/preflight.py --branch-only   # до работы: чужая ли это задача, свободно ли имя
2. … правки, тесты …
3. python scripts/preflight.py                 # перед коммитом: весь набор + линтеры + типы
4. git push -u origin <branch>                 # хук пропустит только проверенный коммит
5. python scripts/check_pr_ready.py <PR>       # перед мержем: набор полон, всё зелёное
```

Связанное: [`environments.md`](environments.md) — что из этого вообще выполнимо
в облачном окне, а что только на локальной машине;
[`../../CONTRIBUTING.md`](../../CONTRIBUTING.md) § «Когда дефект считается
исправленным» — критерий приёмки фикса.
