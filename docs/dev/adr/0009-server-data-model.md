# ADR-0009 — Единая доменная модель + PostgreSQL как серверное хранилище

- **Статус:** Proposed
- **Дата:** 2026-07-16
- **Связанные issue:** #154 (PostgreSQL поверх SQLite), #155 (accounts/workspaces/courses), #151 (эпик server mode)
- **Связанный дизайн:** [server-data-model.md](../design/server-data-model.md),
  [server-mode.md](../design/server-mode.md)
- **Опирается на:** [ADR-0001](0001-server-mode.md) (направление server mode),
  инвариант «ядро — библиотека»

## Контекст

Локальная история прогонов — SQLite (`core/history.py`: `runs`/`case_results`/
`lint_violations`, `user_version`-миграции), однопользовательская, в файле.
Server mode ([ADR-0001](0001-server-mode.md)) хранит прогоны многих клиентов с
изоляцией ([#157.6](../design/server-mode.md#sandbox-и-сетевая-изоляция-issue-157)) в
разделяемой БД. Issue #154 требует согласовать SQLite и PostgreSQL **без
дублирования доменной модели**; #155 — спроектировать accounts/workspaces/
courses/tasks и права.

Риск, который надо снять решением: сервер легко скатывается к **второй,
параллельной** доменной модели (отдельные серверные типы прогона/кейса), что
раздваивает истину и ломает переносимость логики между локальным и серверным
режимами.

## Решение

1. **Доменная модель — одна; хранилищ — два бэкенда.** Доменные типы прогона —
   `CaseRecord`/`LintRecord` (**уже** в `core/history.py`) и `RunRecord`
   (**вводится**: сейчас поля прогона пишутся напрямую в `record_run()` без
   dataclass'а — этот дизайн делает тип явным). Они — единственная доменная
   модель; SQLite и PostgreSQL — её разные бэкенды за **абстракцией репозитория**
   в `core/` (аналогично тому, как `Runner` абстрагирует исполнение). Никаких
   «серверных» дубль-типов.
2. **PostgreSQL-схема — надмножество SQLite:** те же смысловые поля прогона/
   кейса/линта + tenancy-колонки (`workspace_id`/`user_id`/`task_id`/
   `test_set_id`) + нативные типы (`TIMESTAMPTZ`/`BIGINT IDENTITY`/`DOUBLE
   PRECISION`). Не параллельная модель. Детали — [server-data-model.md § PostgreSQL](../design/server-data-model.md#postgresql-схема-поверх-sqlite).
3. **Иерархия tenancy — `workspace` как граница изоляции.** Всё
   (`run`/`course`/`task`) принадлежит workspace; личный режим = workspace из
   одного user'а (N=1) — тот же код обслуживает локальный и серверный опыт.
4. **`test_set` версионируется, `run` ссылается на версию** — вердикты
   воспроизводимы (перегенерация тестов не переписывает историю задним числом).
5. **RBAC на уровне сервиса, не sandbox.** Роли owner/maintainer/member/viewer
   через membership; изолированный код прогона доступа к БД не имеет (сеть off).
   Проверка доступа: нет membership → 404 (не раскрывать чужие workspace).
6. **Локальная SQLite не меняется.** Абстракция репозитория оборачивает текущий
   путь **без смены поведения**; фаза 0 (single-user, файл) остаётся как есть.

Это решение **не** начинает реализацию: ни ORM, ни миграций, ни серверного кода;
абстракция репозитория и явный `RunRecord` тоже не пишутся в рамках этой
подготовки — это дизайн.

## Альтернативы

- **A. Отдельная серверная доменная модель поверх PostgreSQL.** Плюс: свобода
  серверной схемы. Минус: две истины, дублирование логики агрегации истории/
  insights, дрейф между локальным и серверным поведением. Отклонено — прямо
  нарушает критерий #154 «нет дублирования доменной модели».
- **B. Тянуть SQLite и на сервер (файл на клиента / SQLite-per-tenant).** Плюс:
  ноль новой БД. Минус: SQLite не рассчитан на конкурентную многоклиентскую
  запись и разделяемый доступ; изоляция/квоты/бэкапы кустарны. Отклонено для
  серверного масштаба (локально SQLite остаётся оптимальным).
- **C. Document-store (Mongo и т.п.) вместо PostgreSQL.** Минус: реляционные
  связи (workspace→course→task→run, membership-RBAC) естественнее в SQL; уже
  есть SQLite-реляционная модель для надстройки. Отклонено как немотивированный
  сдвиг парадигмы.
- **D. Единая доменная модель + PostgreSQL-надмножество + абстракция репозитория
  (выбрано).** Одна истина, серверная схема — расширение локальной, локальный
  режим не затронут; согласуется с инвариантом «ядро — библиотека».

## Последствия

**Положительные:**

- Одна доменная модель на оба режима — логика истории/insights переносима без
  дублирования (критерий #154 закрыт на уровне дизайна).
- Серверная схема имеет спецификацию (tenancy, версионирование test_set, RBAC),
  реализация фазы 3 стартует не с чистого листа.
- Локальный опыт не меняется (абстракция репозитория — обратимый шаг).

**Отрицательные / издержки:**

- Вводится ещё одна абстракция в `core/` (репозиторий истории) плюс явный
  `RunRecord` — небольшой оверхед; митигируется тем, что SQLite-бэкенд не меняет
  поведение (как `LocalRunner`).
- PostgreSQL как серверная зависимость появится только на фазе 3 — по явному
  решению, не сейчас (запрет зависимостей CLAUDE.md соблюдён: это дизайн).

**Нейтральные:**

- Миграционный инструмент серверной схемы (Alembic-класс) vs `user_version`
  локально — независимые дорожки версионирования; выбор инструмента — этап
  реализации.

## Миграция (фазы)

Не меняет карту [server-mode.md § Фазовая миграция](../design/server-mode.md#фазовая-миграция):
абстракция репозитория и PG-бэкенд относятся к **фазе 3** (API + хранилище),
локальная SQLite (фаза 0) не затрагивается. Полная стратегия —
[server-data-model.md § Стратегия миграции](../design/server-data-model.md#стратегия-миграции-sqlite--postgresql).
