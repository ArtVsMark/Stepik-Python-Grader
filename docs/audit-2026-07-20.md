# Полный мультиролевой аудит Stepik-Python-Grader

**Дата:** 2026-07-20 · **Версия:** v1.9.0 (тег на `403c50f`) · **Метод:** 14 параллельных ролевых срезов + адверсариальная верификация + 2 deep-dive + критик полноты

> **Стратегический контекст.** Владелец намерен **выжать максимум из локальной версии**, затем **навсегда** перейти на серверную. Поэтому каждая находка помечена `server_relevance`:
> `blocks-server` (блокирует пивот) · `carry-over` (нужно и там) · `local-only` (сгорит при пивоте) · `n-a`.

## 0. Методология и честность о прогоне

Аудит выполнен параллельными агентами, читавшими **реальный код** (не документацию). Каждая находка обязана содержать `file:line`. Найденные баги/уязвимости проходили **адверсариальную верификацию** отдельным агентом-скептиком с установкой «по умолчанию опровергай».

**Что пошло не так (важно для повторяемости).** Первый запуск стартовал ~40 агентов одновременно → перегрузка API (`503`/`529`, затем `Connection closed` / `Stream idle timeout`). Упало 13 агентов из 32. Ручной `stop+resume` усугубил: часть уже готовых срезов пере-запустилась и упала повторно.

**Что спасло данные.** `journal.jsonl` — append-only и хранит результаты **всех** прогонов. Возврат workflow показывал `null` там, где в журнале лежал готовый результат. Восстановление из журнала дало 11 срезов; недостающие 3 (обе роли 🔐 и продукт) добраны **точечно, 3 агентами** — и прошли без единой ошибки.

**Вывод для будущих аудитов — см. § 12.**

**Итоговая полнота:** 14/14 срезов · 89 находок · 32 верификации · 2 deep-dive · 1 критик.

## 1. Резюме

Проект инженерно **зрелый**: чистая абстракция `Runner`, стабильный контракт результата, ADR-дисциплина, CI-guard'ы на доки/локали/DAG, 1700+ тестов. Аудит это подтверждает — и именно поэтому находки сконцентрированы не в «грязном коде», а в **трёх системных местах**:

1. **Корректность вердиктов.** Обнаружен **сломанный function-mode**: ни одна форма входа не вызывает функцию решения правильно → рабочие решения получают **false WA или спонтанный RE**. Это подрывает саму цель продукта.
2. **Модель безопасности не готова к публичному контексту.** Локальная threat-model «запускай доверенный код» корректна для локалки, но при пивоте молча переносится туда, где она **неверна**: RCE-as-a-service, утечка секретов через окружение в macOS-sandbox, отсутствие сетевой изоляции на Windows.
3. **WEB статичен не из-за плохого кода, а из-за неиспользуемого фундамента.** Дизайн-система умеет анимировать (`--transition-interactive` в `app.css:95`), но во всём CSS **5 объявлений transition и 2 keyframes**. Интерфейс телепортируется вместо переходов.

## 3. Критические и высокие находки

### 3.1 `CORE-01` — Function-mode сломан: false WA и спонтанный RE
**`grader_core.py:306-322`** · high · carry-over

`_prepare_run_spec` выбирает обёртку по `_is_python_code_block(input_data)`, а **не по семантике теста**:
- вход с присваиванием (`a = 5`) → `_build_call_wrapper` (`wrapper_builder.py:86`), который исполняет блок и **никогда не вызывает функцию решения** → пустой вывод → **WA**;
- голые данные (`5\n10`) → `_build_function_wrapper` (`wrapper_builder.py:79-82`) → `KeyError`, т.к. параметры не заведены в locals → **RE**.

**Нет ни одной формы входа, при которой function-wrapper работает корректно.** Репро подтверждено агентом. Downloader (`downloader.py:236`) проставляет `function_name` для любого шаблона с функцией, а входы из HTML-таблиц Stepik — голые значения → путь RE.

> **Почему это #1.** Молчаливо неверный вердикт хуже краша: студент правит корректный код. Плюс это доказательство дыры в тестах — баг такого калибра дошёл до main, значит путь не покрыт (см. `T*`).

### 3.2 `ARCH-01` — Runner как процессный синглтон (confirmed high)
**`grader_core.py:186`** · high · blocks-server

`_RUNNER: Runner = LocalRunner()` + `set_runner()` мутируют module-global. Нет per-request политики изоляции: на сервере два одновременных запроса **делят один Runner**, и запрос «без sandbox» может исполниться в контексте, настроенном другим. Верификатор подтвердил и **оставил high**.

### 3.3 `PERF-01` — Вывод дочернего процесса без лимита
**`core/runner.py:400, :461-469`** · high · blocks-server

`_drain` копит чанки в list без предела; лимит `output_size` есть **только** у `SandboxRunner`. Решение с `while True: print('x')` набивает RAM хоста за секунды таймаута. Даже доверенный код с багом роняет процесс по OOM.

### 3.4 `SEC-CORE-01` — macOS-sandbox наследует весь `environ`
**`core/sandbox/_macos.py:135` → `_posix_common.py:92-116`** · high · blocks-server

`run_argv_with_limits` вызывается **без** `env=`, значит `subprocess.Popen(env=None)` наследует окружение родителя. Контраст: Linux чистит через `--clearenv` (`_linux.py:132-143`), Windows строит минимальный dict (`_windows.py:233-238`).

Под `--sandbox` решение читает `os.environ` и получает **BYOK AI-ключ** (`STEPIK_GRADER_AI_KEY`), а на сервере — весь env оператора. Запрет сети `(deny network*)` **не спасает**: `print(os.environ)` уходит в захватываемый stdout. `SECURITY.md:141-149` про env-переменные молчит — это **пропуск, а не задокументированный компромисс**.

### 3.5 `SEC-CORE-04` — Windows-sandbox без сети и строгой ФС
**`core/sandbox/_windows.py:35-49`** · high · blocks-server

Job Object ограничивает только память/CPU/число процессов. Сеть — не изолирована, абсолютные пути не блокируются. Задокументировано как компромисс MVP, но по сути означает: **Windows-backend непригоден для исполнения чужого кода на сервере**.

> **Раунд 2 (#648, Windows-часть, дельта):** пробел закреплён исполняемым escape-PoC `tests/test_w6_windows_sandbox_gaps.py` (характеризующие тесты: сетевой egress до локального listener'а, запись и чтение-эксфильтрация по абсолютному пути вне `run_dir` — все проходят). Тесты покраснеют при появлении ФС/сеть-изоляции → сигнал закрыть пробел. Escape-PoC для Linux (`bwrap`) и macOS (`sandbox-exec`) — остаются (нужны живые ОС).

### 3.6 `SEC-WEB-01` — RCE из браузера при серверном деплое
**`web/playground.py:47-77`, `server.py:1075`** · high · blocks-server

`run_server(sandbox=False)` по умолчанию; `/api/v1/runs` c `mode=playground` принимает `{code, stdin}` и исполняет активным Runner'ом. Локально это «свой код на loopback», но инвариант держится **только** на bind-loopback + CSRF-guard. При выносе на сервер — произвольное исполнение кода как сервис.

### 3.7 `PROD-02` — OAuth-барьер убивает активацию (critical)
**`installation.md:192-243`** · critical · blocks-server

Чтобы скачать задачу, **каждый студент** должен создать OAuth-приложение на Stepik (Confidential client, redirect_uri). Для аудитории «новички курса для начинающих» это непреодолимо. Ключевой дифференциатор (автоскачивание тест-кейсов) остаётся недоступен большинству.

> **Вывод:** не вкладываться в локальные обходы — это ровно тот барьер, который **снимает серверная версия** (централизованный OAuth, вход в один клик). Локально — честно продвигать generic-mode без OAuth.

## 6. Deep-dive A: серверная миграция

### Что переносится как есть
Абстракция `Runner` + `RunOutcome` (не завязаны на subprocess) · контракт результата `core/result.py` (стабилен, сериализуем) · доменная модель истории по ADR-0009 · фасад `web/grading.py` под охраной `test_import_dag` · async job-контракт (`queued|running|done|error|cancelled`) уже соответствует `server-mode.md`.

### Что НЕ переносится
`RunSpec.path` — путь на **локальной** ФС; содержимого решения в spec нет (wrapper/bench/trace пишутся во временный `.py` на диске раннера). Через сеть уедет путь, которого на удалённой стороне не существует. Плюс `_JOBS` dict, single-workspace без auth, cwd-относительные dotfiles.

### Рекомендации (10)

**Делать локально (pre-pivot lock):**
1. **L** — починить `CORE-01` (маршрутизация function-mode) — *до* пивота, иначе баг переедет
2. **M** — **сериализуемое ядро `RunSpec`: нести СОДЕРЖИМОЕ решения, а не FS-путь** ← самый важный замок перед пивотом
3. **M** — ввести `RunRecord` + абстракцию репозитория (ADR-0009), не меняя SQLite-поведение
4. **S** — провести microbench/tracer через публичный `run_spec()`/`active_runner()`, убрать прямой `_RUNNER`
5. **S** — `run_microbench_mode`: применить `_apply_run_mode_override`
6. **S** — `LocalRunner.run`: `try/finally`, гарантирующий `_kill_process_tree`
7. **S** — классификация исходов: RE с пустым stderr → `errors`; CANCELLED не считать ошибкой
8. **S** — минимальная ротация истории (только если локальная фаза долгая)

**НЕ делать локально (сгорит при пивоте):**
9. **XL** — durable-очередь, auth, Postgres, per-tenant persistence
10. **S** — тяжёлый web-UX (кроме дешёвых фиксов видимости) — см. разбор конфликта в §8

## 7. Deep-dive B: WEB — почему «неинтерактивный» и что делать

### Диагноз
> **Превосходный статический фундамент и нулевая динамика.**

Дизайн-токены (`app.css:48-114`) — зрелая система: палитра на oklch, флюидная типографика `clamp()`, и **объявленная** переменная `--transition-interactive: 180ms cubic-bezier(0.16,1,0.3,1)` (`app.css:95`). Но во всём CSS — **5 объявлений transition** (реально работают два) и **2 `@keyframes`** (shimmer скелетона + бегунок прогресса). **Больше не движется ничего.**

Конкретика:
1. **Переключение разделов — телепортация.** `setSection()` (`core.js:167-185`) дёргает `.hidden` в цикле. Ни fade, ни slide. Контент появляется скачком через `innerHTML=`. Каждый клик ощущается как перезагрузка страницы.
2. **Действия без отклика.** `copyToClipboard()` (`grade.js:57-61`) пишет в буфер и **глушит ошибку** `.catch(()=>{})` — ноль подтверждения.
3. **Ошибки летят в дальнюю панель.** `saveSolution()` пишет ошибку в `#out` — правую панель, которая на вкладке «Разбор» вообще скрыта.
4. **Прогон — чёрный ящик.** Polling каждые 600 мс без оптимистичного состояния: пауза до первого тика читается как зависание.

### План (13 рекомендаций)

**Дёшево и сразу (S):** тосты через существующий `.notice` · инлайн-ошибки у поля вместо `#out` · единый скелетон-примитив вместо трёх разных индикаторов · focus-trap в модалках · клавиатурные потоки (Ctrl+Enter запуск, Ctrl+S сохранить, 1–4 режимы)

**Средне (M):** motion-слой переходов разделов/вкладок (fade/slide + stagger) · **drag&drop `.py` + нативный файловый диалог** · оптимистичные апдейты (скелетон-строки сразу по клику) · инлайн-diff с посимвольной подсветкой и маркерами невидимых символов · live-грейдинг с debounce (opt-in)

**Крупно (L):** **трейс как анимация исполнения** — уникальный актив в стиле Python Tutor, сейчас статичен; авто-плей, плавные переходы кадров · геймифицированный дашборд «Прогресс» (count-up, стрик-полоса, кольца)

**На сервер (L):** SSE-стриминг вывода вместо polling

## 8. Разбор конфликта ролей: вкладываться ли в WEB перед пивотом?

**🏛 Архитектор:** не вкладываться — web-слой переписывается под multi-tenant, UX-работа сгорит.
**🎨 Дизайнер + 🚀 Визионер:** web — лицо продукта, и владелец прямо им недоволен.

**Разрешение (моё заключение).** Конфликт разрешается разделением **клиента и сервера**:

- **Фронтенд** (`static/*.js`, `app.css`, `index.html`) — это **клиент**, он переживает пивот: серверная версия будет отдавать примерно тот же SPA. Тосты, motion, drag&drop, инлайн-diff, клавиатура, скелетоны — **переносимы**, живут в статике и не зависят от того, локальный бэкенд или серверный.
- **Сгорает** только то, что вшито в локальный бэкенд: polling→SSE, single-workspace пути, локальный OAuth-мастер, `_JOBS`.

**Итог:** делать **client-side UX волной 2** (это дёшево, radикально меняет ощущение и не пропадёт), и **не трогать** backend-coupled вещи до сервера. Возражение Архитектора корректно ровно в части бэкенда.

## 12. Правила проведения аудитов (методология)

Выведено из сбоев этого прогона — **применять в следующих аудитах**:

1. **Дозирование.** Максимум **4–6 агентов одновременно**. 14 срезов = 3 волны, а не один залп. Медленнее, но не теряет данные.
2. **Волна = чекпоинт.** После каждой волны сохранять результат на диск; сбой волны N не трогает волны 1..N-1.
3. **Рестарт только дельты.** Никогда не перезапускать прогон целиком. Собрать из журнала готовое → вычислить, чего нет → запустить точечно недостающее. (Именно так добраны 3 среза — 0 ошибок.)
4. **Журнал — источник истины, а не возврат workflow.** Возврат может показать `null` там, где в `journal.jsonl` лежит результат. Всегда сверяться с журналом **перед** выводом «агент потерян».
5. **Объективность:** обязательный `file:line` + репро · адверсариальный верификатор с установкой «опровергай по умолчанию» · severity ставит **верификатор** (`corrected_severity`), не автор находки · обязательное поле `server_relevance`.
6. **Критик полноты — в конце и по факту.** Его вывод устаревает, если срезы дозапускались после него (как случилось здесь).
