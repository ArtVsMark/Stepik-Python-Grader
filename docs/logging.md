# Диагностический режим и лог-файл (дизайн)

> Дизайн-контракт диагностического логирования (issue #150). Описывает
> **целевое поведение**: когда пишется лог, что в него попадает, требования
> редакции секретов и политику opt-in/opt-out. Реализация в
> `downloader.py`/`stepik_client.py`/`oauth_flow.py` — follow-up issue; здесь
> фиксируются правила, которым эта реализация обязана следовать.
>
> Сегодня вывод идёт через `_console` (rich) с fallback на `print()`
> ([CLAUDE.md § Стиль](../CLAUDE.md)); диагностика Stepik пишет отчёты в
> `stepik_diagnostics/` (`diagnostic_stepik.py`). Отдельного структурированного
> лог-файла и уровня verbosity пока нет — этот документ задаёт их контракт.

## Зачем отдельный диагностический режим

Проблемы воспроизводятся у пользователя, а не у мейнтейнера: сеть, OAuth,
парсинг ответов Stepik, раскладка тест-кейсов. Нужен способ получить
подробный след **по явному запросу**, не засоряя обычный вывод и не рискуя
утечкой токена. Диагностический режим — это управляемая многословность плюс
опциональный лог-файл.

## Уровни и активация (opt-in)

**По умолчанию — тихо.** Обычный запуск пишет только пользовательский вывод
через `_console`; диагностический лог **выключен** (opt-in), файл не создаётся.

Целевые способы включения (любой из):

| Способ | Область | Пример |
|---|---|---|
| Флаг CLI | один запуск | `--diagnostic` / `--verbose` |
| Переменная окружения | сессия/CI | `STEPIK_GRADER_LOG=debug` |
| Диагностическая утилита | разбор API/токена | `python -m stepik_grader.diagnostic_stepik` |

Уровни: `warning` (дефолт видимого вывода) → `info` → `debug` (полный след:
URL-запросы без секретов, шаги парсинга, пути файлов). Повышение уровня — только
явным opt-in; понижать/выключать (`opt-out`) можно тем же флагом/переменной
(напр. `STEPIK_GRADER_LOG=off`).

## Лог-файл

- **Путь по умолчанию:** внутри диагностического каталога
  (`stepik_diagnostics/`, уже используется `diagnostic_stepik.py`) —
  напр. `stepik_diagnostics/grader.log`. Каталог держится в `.gitignore`
  (как `errors.txt`, `.grader_cache/` — см.
  [project-structure.md](project-structure.md)).
- **Создаётся только при включённом диагностическом режиме** (opt-in). Без
  него файл не появляется — «чистый» запуск не оставляет следов на диске.
- **Формат:** строки с меткой времени и уровнем; человекочитаемо, без
  обязательного JSON (тяжёлых зависимостей не вводить —
  [CLAUDE.md](../CLAUDE.md)). Ротация/размер — деталь реализации follow-up.
- **Не коммитить.** Лог-файл и `stepik_diagnostics/` — локальные артефакты;
  вставлять их в issue/PR можно только после проверки на секреты (см. ниже).

## Редакция секретов (обязательно)

Диагностический лог — самая частая точка утечки токена. Требования **жёсткие**
(в скоупе [SECURITY.md](../SECURITY.md#обращение-с-секретами)):

1. **Никогда не логировать** содержимое `secrets.json`, `access_token`,
   `refresh_token`, `client_secret`, заголовок `Authorization`/`Bearer ...`.
2. **Редактировать при выводе, а не полагаться на «не передавать».** Значения
   токенов заменяются на `***redacted***` (или маскируются до последних 4
   символов) в любом сообщении — включая эхо URL, заголовков и тел ответов
   Stepik. Редакция применяется на уровне логгера, до записи в файл/консоль.
3. **URL с query-параметрами токена** санитизируются (вырезать
   `access_token=`/`code=`).
4. **Отчёты диагностики** (`stepik_diagnostics/*.json`, `save_json` в
   `diagnostic_stepik.py`) подпадают под те же правила — не сохранять токен в
   payload.
5. **Тест на редакцию** — часть реализации follow-up: unit-проверка, что
   известные секрет-поля не попадают в лог-строки.

Утечка токена в лог/отчёт/кэш прямо перечислена в скоупе безопасности
([SECURITY.md § Область](../SECURITY.md#область-scope)) — редакция закрывает
именно её.

## Связь с follow-up реализацией

Диагностика касается сетевого/OAuth-слоя; правила выше — контракт для будущих
issue по:

- **`core/stepik_client.py`** — логирование HTTP-запросов/ответов Stepik на
  `debug` с санитизацией URL/заголовков.
- **`core/oauth_flow.py`** — шаги авторизации без утечки `client_secret`/токена.
- **`downloader.py`** — след разбора URL шага, раскладки файлов, извлечения
  тест-кейсов (какой из 4 источников сработал — ZIP/HTML/GitHub/ничего).
- **`diagnostic_stepik.py`** — уже пишет отчёты в `stepik_diagnostics/`;
  привести к общему логгеру и правилам редакции.

Единый логгер должен оставаться совместимым с `_console`-fallback (rich
опционален) и **не** добавлять зависимостей. Вывод бизнес-модулей — по-прежнему
через `_console`, а не голый `print()` ([CLAUDE.md](../CLAUDE.md)).

## Non-goals

- Не вводить внешние logging-фреймворки/агрегаторы (stdlib `logging`
  достаточно).
- Не логировать по умолчанию (privacy/скорость) — только opt-in.
- Не менять пользовательский вывод обычного (не диагностического) запуска.
