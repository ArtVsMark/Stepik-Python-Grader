# Серверный трек: что делать и в каком порядке

> **Статус: не построено.** Документ отвечает на вопрос «**что** и **в каком
> порядке**», когда решение о серверном пивоте будет принято. На вопрос «**как**
> это устроено» отвечают [server-mode.md](server-mode.md) (фазы 0–4, Runner-слой,
> контракт API), [server-sandbox-design.md](server-sandbox-design.md),
> [server-data-model.md](server-data-model.md) и ADR-0001 / 0008 / 0009.
>
> Документ их **не переоткрывает**: где блок повторяет принятое решение, он его
> подтверждает и ссылается.

Отдельные issue по серверу **не заводятся** до решения о пивоте — направление
держит roadmap-issue проекта, а состояние трека живёт здесь.

## Откуда это взялось

Цели собраны двумя волнами и сведены из комментариев roadmap-issue, где их нельзя было ни
отревьюить в PR, ни найти поиском по `docs/`, ни изменить атомарно.

| Волна | Что дала |
|---|---|
| Аудит 2026-07-30 | 78 долгосрочных целей → 11 тематических блоков; 8 отклонено как «на самом деле не серверные», дубликаты схлопнуты |
| Аудит 2026-08-10 | 4 пункта пополнения: канарейка дрейфа API, каталог задач, переопределяемый `API_HOST`, агрегация данных об использовании |

**О числе 78.** Столько целей дала волна аудита *до* обработки. В блоках ниже их
**55**: автор сведения схлопнул дубликаты (например, «публичный профиль прогресса
по ссылке» и «публичная ссылка-профиль прогресса» — одна цель, сформулированная
двумя ролями) и вынес 8 в раздел отклонённых. Числа расходятся законно, и здесь
это сказано вслух, чтобы следующая сверка не искала пятнадцать потерянных строк.

## Фазы и зависимости

Блоки фазы «фундамент» независимы друг от друга и готовятся параллельно; всё
остальное на них опирается.

# 🧱 Фундамент — без этого сервера нет

## 1. Контейнерная изоляция недоверенного кода

*Аудит 2026-07-30. Зависит от: — (базис; опирается на готовый протокол `core/runner.py`)*

Локальные backend'ы дают гарантию по слабейшему звену (Windows — без сети и ФС,
macOS — psutil-поллинг), а opt-in `--sandbox` перестаёт быть выбором
пользователя, когда код чужой. Нужен один Linux-исполнитель за протоколом
Runner: namespaces + cgroups v2 + seccomp, сеть-off пустым netns, квоты и kill
как свойство job'а, плюс корпус escape-атак. Дизайн закрыт **ADR-0008** —
подтверждаем, не переоткрываем.

| Цель | Почему не локально |
|---|---|
| Контейнерный sandbox-backend для недоверенного кода | Threat model локального инструмента — код, который пользователь и так собирался запустить у себя; жёсткая изоляция там опциональна и местами вредна (под `--sandbox` недоступен пошаговый трейс). Обязательной она становится только там, где исполняется код постороннего |
| Обязательная контейнерная изоляция с квотами | Локально пользователь запускает СВОЙ код и уже имеет все свои права — изоляция там страховка от опечатки, а не от злоумышленника |
| Контейнерный sandbox с cgroups-квотами вместо трёх ОС-backend'ов | Требовать от школьника Docker ради проверки своего кода несоразмерно (CLAUDE.md запрещает Docker как обязательную зависимость) |
| Один контейнерный исполнитель вместо трёх ОС-специфичных | Локально ОС выбирает пользователь, и грейдер обязан работать на всех трёх; единый рантайм возможен там, где ОС контролируем мы |
| Квоты и отмена как свойство job'а (cgroup v2), а не потока-родителя | Per-run cgroup с `memory.peak` и надёжным kill всей группы требует делегированных привилегий, которых у локального запуска нет |
| Систематическое escape-тестирование против недоверенного кода | Пока код исполняет автор этого же кода, «побег» не угроза; она появляется, когда чужой код идёт на общей инфраструктуре |

## 2. Идентичность и мультиарендность

*Аудит 2026-07-30. Зависит от: — (базис для всего, что делит ресурсы между людьми)*

Периметр держится на допущении «один владелец на loopback»: эвристики
Host/Origin/Sec-Fetch-Site с намеренным fail-open, сырые пути ФС в
HTTP-контракте, артефакты от `Path.cwd()`. Заменяется сессиями и учётками,
адресацией задач по идентификатору и workspace, принадлежащим аккаунту. Сюда же
снимается critical-находка PROD-02: одно Confidential-приложение сервиса вместо
OAuth на каждого студента.

| Цель | Почему не локально |
|---|---|
| Аутентификация и сессии вместо localhost-эвристик | На одной машине аутентифицировать некого: единственный пользователь — владелец процесса |
| Заменить эвристики заголовков на настоящую аутентификацию сессии | Требует модели сессии/пользователя и хранения учётных данных, которых у локального single-user инструмента нет |
| Убрать сырые пути ФС из HTTP-контракта: адресация по идентификатору | На многопользовательском сервере сырой путь от клиента недопустим в принципе |
| Мультитенантные пути данных вместо производных от `Path.cwd()` | Локально cwd — корректная модель «моей папки с задачами»; разделение нужно, когда данные нескольких людей в одном хранилище |
| Централизованный вход через Stepik — одно OAuth-приложение сервиса | Confidential-клиент существует только там, где есть серверная сторона, способная хранить `client_secret` |

## 3. Ядро под многопользовательский рантайм

*Аудит 2026-07-30. Зависит от: — (подготовку можно вести на локальной версии; даёт точку подключения блоку изоляции)*

Механизм исполнения — процессный синглтон `_RUNNER`, лимиты вморожены в
константы на импорте, отмена — `threading.Event`, несериализуемый по природе.
Серверу нужен выбор Runner'а и квот на каждый запрос через контекст вызова,
cancellation-токен как внепроцессный контракт (id прогона + endpoint отзыва) и
граница «ядро-библиотека vs приложение», чтобы воркер-образ не тянул CLI, rich и
статику (**ADR-0001**).

| Цель | Почему не локально |
|---|---|
| Per-request Runner и конфигурация вместо process-global синглтонов | На одной машине один пользователь запускает один режим — глобальный Runner не наблюдаем как проблема |
| Per-request выбор Runner вместо процессного `_RUNNER` | Смысл появляется там, где в одном процессе живёт код взаимно недоверяющих пользователей с разными квотами |
| Отмена и квоты как внепроцессный контракт, а не `threading.Event` | Внепроцессный токен нужен, когда исполнитель живёт в другом процессе/контейнере/на другой машине |
| Явное расщепление на библиотеку-ядро и серверное приложение | Локально монолитный импорт стоит десятки миллисекунд один раз за сессию — оптимизировать нечего |

## 4. Durable-очередь прогонов

*Аудит 2026-07-30. Зависит от: блоков 1, 2, 3*

Реестр job'ов — module-level dict под Lock с ленивым TTL, пул —
ThreadPoolExecutor на 2 воркера, back-pressure — один глобальный счётчик
`max_active_runs` с 429; модель честно помечена как MVP. Серверу нужны внешняя
очередь и статусы, видимые всем воркерам и переживающие рестарт, справедливое
деление CPU/памяти/прогонов между арендаторами и приоритеты. Модель данных —
**ADR-0009**.

| Цель | Почему не локально |
|---|---|
| Вынос реестра job'ов и результатов из памяти процесса | Локально процесс один: словарь в памяти и есть источник истины |
| Персистентная очередь вместо module-level dict + ThreadPoolExecutor | Локально перезапуск — осознанное действие пользователя, который тут же перезапустит прогон |
| Сервисный уровень надёжности: очередь, приоритеты, наблюдаемость | Для одного человека двух воркеров и словаря достаточно, а внешняя очередь — лишний процесс на ноутбуке |
| Квоты и приоритеты на пользователя поверх back-pressure | Разделение бюджета между аккаунтами не имеет предмета на однопользовательской машине |

## 5. Централизованное хранилище учебных данных

*Аудит 2026-07-30. Зависит от: блока 2*

История, настройки и согласия живут файлами в рабочей папке — верный локальный
ответ, но прогресс и стрик разъезжаются между машинами. Серверный бэкенд встаёт
той же поверхностью `HistoryRepository` (**ADR-0009**): изоляция строк по
пользователю, профиль поверх устройств, сроки хранения, экспорт и подтверждаемое
удаление. Отдельно — миграции на копии боевых данных.

| Цель | Почему не локально |
|---|---|
| История и insights как централизованное хранилище с изоляцией по пользователю | Локально файл-на-пользователя — правильный ответ: ноль конфигурации, ноль сети, данные не покидают машину |
| Кросс-девайс синхронизация истории и настроек обучения | Синхронизация требует идентичности, серверного хранилища и разрешения конфликтов между устройствами |
| Синхронизация настроек интерфейса между устройствами | Профиль поверх нескольких устройств требует общего адреса, которого локально не существует |
| Регрессионное тестирование миграций на реальном объёме | У локальной SQLite нет ни объёма, ни требования доступности во время миграции |
| Политика удержания и удаления учебных данных | Erasure/retention доказуемы там, где есть учётная запись, бэкапы и репликация |

## 6. Эксплуатационная зрелость

*Аудит 2026-07-30. Зависит от: блоков 4, 2*

Собственного логгера у web-слоя нет, `log_message` заглушён целиком: локально
журналом служит окно терминала. Сервису нужны `request_id`, корреляция и метрики
латентности, нагрузочный профиль очереди (честность планировщика, деградация под
насыщением, TTL при притоке), регулярные e2e-journey против живого стенда с
алертами и канареечным откатом, сроки реакции на уязвимости и advisory.

| Цель | Почему не локально |
|---|---|
| Структурированное логирование и трассировка HTTP-запросов | На локальной машине окно терминала и есть журнал |
| Нагрузочное и конкурентное тестирование очереди при мультитенантности | Один пользователь физически не создаёт конкуренцию за пул; тест мерил бы производительность ноутбука |
| Синтетический мониторинг и канареечные прогоны против живого стенда | Локальный инструмент не работает между запусками: нет ни аптайма, ни выпуска для отката |
| Публичный процесс раскрытия уязвимостей с временем ответа и advisory | SLA и advisory имеют смысл, когда есть эксплуатируемая инсталляция и чужие данные |

## 7. Публичный HTTP-контракт

*Аудит 2026-07-30. Зависит от: блоков 2, 4*

Локально клиент и сервер едут одним `git pull`, поэтому форма ответов не
зафиксирована ни схемой, ни снапшотом, а `/api/` и `/api/v1/` соседствуют с
DEPRECATED без срока снятия. При независимых клиентах нужны спека как источник
истины вместо рукописного `api.md`, snapshot-схемы, матрица «старый клиент ×
новый сервер» и окно депрекации с `Sunset`. Тот же контракт открывает эндпоинт
для агентных IDE.

| Цель | Почему не локально |
|---|---|
| Контрактное тестирование публичного API с версионированием | Локально клиент и сервер обновляются одним `git pull` — рассинхрона версий не бывает |
| OpenAPI как источник истины вместо рукописного `api.md` | Ценность спеки появляется, когда клиенты внешние и обновляются независимо |
| Политика версионирования и депрекации (`/api/` vs `/api/v1/`) | Ломающее изменение локально стоит ноль — клиент едет в том же пакете |
| Публичный MCP/HTTP-эндпоинт как второй канал для внешних агентов | Локально MCP требует от школьника поднять хост и sandbox |

## 8. Публичный веб-периметр

*Аудит 2026-07-30. Зависит от: блоков 1, 4*

На `127.0.0.1` невозможно всё, что делает проект видимым снаружи: клик из курса
или статьи в первый зелёный прогон без `pipx`, оценка интерфейса до установки,
органический трафик по карточкам ошибок, срез документации на каждый тег с
поиском и RU/EN вместо доков `main` у пользователя старого релиза, сигнал о том,
где бросают чтение. Нужны домен, стабильные URL и приём чужого кода.

| Цель | Почему не локально |
|---|---|
| Демо «попробовать за 30 секунд» без установки | Требует исполнения чужого кода на нашей стороне — контейнерный sandbox с квотами |
| SEO-витрина глоссария на собственном домене | Локальный офлайн-глоссарий доступен только владельцу машины |
| Публичная демо-витрина интерфейса без установки | Нужен размещённый рантайм с изоляцией чужого кода |
| Версионированный сайт документации с RU/EN и поиском | Нужен хостинг, сборка на каждый тег и постоянный URL |
| Обратная связь по документации: что читают перед отказом | Требует сбора событий чтения на стороне сайта |

## 9. Адресуемые артефакты

*Аудит 2026-07-30. Зависит от: блоков 2, 5*

Поделиться результатом можно копипастой из stdout, скриншотом или файлом
`grader-progress`, который мгновенно устаревает и не подтверждает авторства.
Серверный снапшот прогона с постоянным URL и моделью доступа превращает грейдер
в инструмент обратной связи с ментором, а профиль по ссылке — в верифицируемое
«покажу другу / приложу к заявке», обновляемое новыми прогонами.

| Цель | Почему не локально |
|---|---|
| Публичный профиль прогресса по ссылке вместо файла | Нужен стабильный URL, права доступа и обновление содержимого при новых прогонах |
| Публичная ссылка-профиль с подписью «данные не подделаны» | Локальный файл принципиально не верифицируем |
| Ссылка на разбор прогона для преподавателя или ментора | У сервера на `127.0.0.1` адресуемости наружу нет |
| Разбор провала по постоянной ссылке вместо копипасты терминала | Постоянный адрес требует хранения прогона вне машины студента |

## 10. Учебный социальный слой

*Аудит 2026-07-30. Зависит от: блоков 2, 5, 1, 9*

Обмен агрегатами класса файлами — суррогат, а главный дифференциатор (честное
сравнение решений в режимах 3/4) упирается в то, что сравнивать можно только
свои. Общее хранилище даёт срез по группе, типовые падения когорты, позицию среди
своих и сопоставимый бенчмарк на едином исполнителе. Одновременно возникает
обработка данных третьих лиц: роли, согласия, минимизация, защита от накрутки.

| Цель | Почему не локально |
|---|---|
| Кабинет преподавателя: агрегаты по группе и сравнение с когортой | Нужны аккаунты, роли и хранение чужих прогонов; «медленнее 70% группы» невозможно без чужих замеров |
| Когорты преподавателя: прогресс группы поверх локальных прогонов | Агрегация по нескольким людям требует общего хранилища и разграничения доступа |
| Кросс-пользовательское сравнение решений по бенчмарку | Сопоставимость времени требует одинакового окружения — единого исполнителя, а не чужих ноутбуков |
| Лига группы и peer-сравнение: «как её решили другие» | Нужны чужие прогоны, агрегация без раскрытия кода и защита от накрутки |
| Работа с чужим кодом: лидерборды и импорт эталонов сообщества | Локальный `--sandbox` рассчитан на доверенный код и на Windows не даёт сетевой изоляции |
| Роль преподавателя и этика доступа к чужим прогонам | Локально владелец данных и пользователь совпадают |

## 11. Данные популяции

*Аудит 2026-07-30. Зависит от: блоков 2, 5*

Инструмент считает активацию, TTFG и стрик, но данные по дизайну не покидают
машину — приоритеты ставятся вслепую, а порядок блоков после провала задан
наугад. Согласованный обезличенный сбор даёт воронку по когортам, ранжирование
реально проваливаемых концептов и публичные отчёты. Тот же контур снимает барьер
BYOK: наш ключ, общий кеш падений, квоты и аудит (вариант D из **ADR-0003**).

| Цель | Почему не локально |
|---|---|
| Продуктовая аналитика воронки: активация, TTFG, удержание по когортам | Воронка — свойство популяции, её нельзя вычислить на машине с одним аккаунтом |
| Анонимная агрегированная статистика типовых ошибок | Локальная SQLite видит одну машину и по определению нерепрезентативна |
| Ежегодный отчёт «типовые ошибки студентов Поколения Python» | Агрегат по многим пользователям возможен только при явном opt-in и серверном приёме |
| Агрегированная opt-in телеметрия падений как источник приоритетов | Локальный инструмент по определению видит только себя |
| Подсказки, ранжированные по тому, что реально помогло другим | Нужна агрегация исходов многих студентов по одной задаче |
| Централизованный AI-канал с квотами вместо BYOK | ADR-0003 отверг вариант D как несовместимый с локальной безсерверной поставкой |
| Серверный AI-прокси с общим кешем, квотами и обезличиванием | Требует нашего ключа, rate-limit и биллинга на стороне сервиса |
| Централизованный BYOK и аудит обращений к AI-провайдеру | Требуются секрет-менеджмент вне пользовательского env и неизменяемый аудит-лог |

# Пополнение из аудита 2026-08-10

Аудит работал **по локальной версии** (70 срезов, 489 находок), как и задано
стратегическим контекстом «выжать максимум из локальной, затем перейти на
серверную». Отдельных серверных находок он поэтому не дал — но стратегическая
волна выявила четыре следствия, которые локально не решаются.

Ранее сведённые блоки остаются в силе без изменений: это дополнение, а не замена.

### 🐤 Канарейка дрейфа Stepik API (`STR-3-02`)

Все тесты сетевого слоя работают на моках, поэтому **зелёный CI ничего не
говорит о работоспособности с живым Stepik**: изменение схемы ответа обнаружит не
проверка, а пользователь. Локально канарейку держать негде — нужен регулярный
прогон против живого API по расписанию. Смежное: `STR-3-03` — смена формы ответа
сейчас маскируется под «шаг не найден» вместо честного «формат изменился».

### 📚 Каталог задач вместо локального мастера (`STR-3-05`)

Каталог задачи может создать **только загрузчик со Stepik** — офлайн-способа
завести задачу нет. Локальная часть решения — мастер «создать задачу из своих
файлов» (заведена в локальной части того же аудита). Серверная часть — общий каталог готовых задач,
из которого их берут без Stepik вообще; это и есть предпосылка независимости от
платформы.

### 🔧 Переопределяемый `API_HOST` (`STR-3-06`)

Адрес API зашит константой, а `diagnostic_stepik` импортирует значение, а не
модуль. Переопределяемый хост нужен и для тестового стенда (в том числе для
канарейки выше), и для развёртывания против собственного зеркала.

### 📊 Агрегация данных об использовании (`STR-4-05`, `STR-4-02`)

Локально возможен только opt-in журнал: он есть, но **не отвечает на вопрос, ради
которого заведён** — нет таксономии причин падения, нет временной оси, а
веб-прогоны в него вообще не попадают (`STR-4-01`, чинится локально). Всё, что
требует агрегации **по нескольким пользователям**, серверное по определению.

# Отклонено как «на самом деле не серверное»

Эти цели заявлялись как долгосрочные, но реализуются локально — они учтены в
локальной части аудита. Отклонённая находка фиксируется, а не удаляется: молча
выброшенная вернётся следующим аудитом.

| Цель | Почему отклонена |
|---|---|
| Курируемая витрина задач для новых контрибьюторов с автоподбором | Бот поверх GitHub API (Actions/внешний воркер); продуктового сервера не требует |
