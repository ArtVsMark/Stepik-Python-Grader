# Мультиагентный режим: волнами по 5

Правила для **любой** массовой работы агентами, не только для аудитов: сквозные
правки документации или кода, генерация контента, разбор находок, миграции,
исследование в несколько срезов. В [`../../CLAUDE.md`](../../CLAUDE.md) — только
компактный триггер; канон здесь.

---

## Главное правило

**Волна = ровно 5 агентов. Одна волна = отдельный вызов Workflow.**

Не залпом — даже когда включён режим ultracode и «токены не ограничение». Правило
про **надёжность**, а не про экономию: большой залп сам себе создаёт отказ, и чем
он больше, тем дороже потеря.

```
❌ 40 агентов сразу  → перегрузка API (503/529 → Connection closed):
                       упало 13 из 32
❌ 29 агентов сразу  → лимит сессии + каскад 403 Failed to authenticate:
                       упало 20 из 29, 1.34M токенов ради 9 результатов
❌ 24 агента сразу   → остановлено вручную владельцем до первого результата
❌ 5 агентов, но роль целиком одному агенту → Connection closed **на выдаче**
                       ответа: упало 5 из 5 дважды (884k и 503k токенов в ноль)
✅ 5 агентов → разбор → следующие 5
```

Пять — потолок волны, но не гарантия: волна из пяти агентов гибнет целиком, если
каждому поручена слишком большая зона (см. § Роль дробится на 2–3 агента).

Почему именно отдельный вызов на волну, а не один скрипт с барьерами по 5: при
остановке такой скрипт уносит и невыполненные волны. Отдельный запуск даёт
чекпоинт и точку решения между волнами.

---

## Роль дробится на 2–3 агента

**Роль целиком одному агенту не даётся.** Минимум **2 подсреза, лучше 3**, с
непересекающимися списками файлов.

Агент умирает не от сложности задачи, а от **размера**: большого входного
контекста (обход всего дерева) и большого одиночного ответа. Структурированный
вывод на десяток находок рвётся прямо **на выдаче** — `Connection closed
mid-response`. В журнале при этом только `started`: агент отработал (транскрипт
на сотни килобайт) и потерял всё в последний момент.

**Дробление режет контекст агента, но не глубину роли — оно её увеличивает.**
Лимит стоит на подсрезе, а не на роли: 3 подсреза × 4–7 находок = 12–21 находка
против прежних 4–14 у одного агента. Условия, при которых это работает:

- **зоны подсрезов не пересекаются**, а в объединении покрывают роль целиком —
  полнота роли есть объединение зон, а не выборка из них;
- **у каждого подсреза свой явный список файлов**, и вместе они исчерпывают
  предметную область роли (остаток «прочее» — признак, что дробили по аспектам,
  а не по объектам);
- **дедуплицирует хост**: пересечения по `file:line` схлопываются при сборке,
  поэтому лучше небольшой нахлёст зон, чем дырка между ними;
- **общий контекст роли — в общей части промпта** (профиль, запреты, критерии),
  чтобы подсрезы судили по одной планке и результат оставался сопоставимым.

Дробить — по **объектам**, а не по «аспектам»:

```
📝 docs   → docs/use/ + README  ·  docs/dev/ + ADR  ·  CLAUDE.md/CONTRIBUTING/SECURITY
🎨 дизайн → web (HTML/CSS/JS)   ·  CLI-вывод + локали
🔐 безоп. → web-периметр        ·  core/sandbox  ·  данные и этика
```

Правила того же корня — без них дробление не спасает:

- **Лимит объёма ответа прямо в схеме:** `minItems`/`maxItems` на массивах,
  `maxLength` на **каждом** строковом поле. Без него агент пишет простыню и
  обрывается на ней.
- **Бюджет обращений к инструментам** в промпте (~25) вместо обхода всего дерева.
- **Никаких бинарных файлов** (`.png`, `.gif`, `.woff2`) в зоне агента: `Read`
  картинки переполняет контекст, и агент встаёт намертво (180 с × 6 попыток без
  прогресса — реальный случай). Нужна оценка визуала — отдельный агент, у
  которого нет другой работы.
- **Явный перечень файлов зоны** в промпте вместо «твоя зона — документация».

Дробление не отменяет правило волны: в волне по-прежнему **ровно 5 агентов**,
просто 13 ролей укладываются не в 3 волны, а в 5–6.

### Прогонному агенту — не больше трёх пунктов плана

У читающего агента размер меряется файлами, у **прогонного** — шагами сценария, и
второе коварнее: каждый шаг тянет за собой десятки команд. На аудите 2026-08-10
прогонным агентам выдали по пять пунктов («собери колесо, подними чистое
окружение, прогони сорок раз, сверь отчёты, проверь очистку») — транскрипты
выросли до 390 КБ, а три агента из пяти не дошли до выдачи. Те же сценарии,
разложенные по **три пункта на агента**, дали 5 из 5 без потерь и 27 находок.

```
❌ один агент = сценарий целиком (5 пунктов)   → 2 из 5 дошли
✅ сценарий = 2 агента по 3 пункта             → 5 из 5, находок больше
```

Бюджет инструментов прогонному агенту — **~35 вызовов** (против ~25 читающему):
команд у него больше, а файлов он читает меньше.

## Агенты возвращают данные — файлы правит хост

Агент **не редактирует файлы**. Он читает, анализирует и возвращает
структурированный результат через `agent(schema=...)`; применяет его
детерминированный код на стороне хоста.

Что это даёт:

- **нет гонок за файлы** — параллельные агенты не пишут в одно место;
- **результат проверяется до записи** — невалидное предложение просто не
  применяется;
- **потеря агента дешёвая** — упавший агент не оставляет полуправку в рабочем
  дереве.

Пример формата для сквозной правки текста: агент возвращает
`[{old_string, new_string, why}]`, хост проверяет уникальность каждого
`old_string` в файле и применяет; неуникальные и ненайденные — в отчёт, не в
файл.

## Прогонным агентам — запреты окружения прямо в промпте

Агент, который запускает продукт, обязательно упрётся в защиту, если его не
предупредить. На аудите 2026-08-10 два агента были остановлены на середине: один
создавал во временном каталоге фиктивный `secrets.json`, другой делал
`export HOME=/tmp/...`. Оба запрета справедливы, но агенты о них не знали и
потеряли всю работу.

В промпт **каждого** прогонного агента — блок запретов:

```
- НЕ создавать файлы с именем secrets.json, даже фиктивные и во временном каталоге;
  поведение с секретами проверять на ОТСУТСТВУЮЩЕМ и на БИТОМ файле под другим именем
- НЕ переопределять HOME и другие переменные, меняющие домашний каталог;
  изоляция — рабочим каталогом (mktemp -d) и параметрами самого продукта
- НЕ писать в репозиторий: ни файлов, ни git-операций, только чтение
- Ничего интерактивного без stdin; каждой команде — timeout
- Поднял сервер — убей по pid в конце
```

Последний пункт не формальность: после первой прогонной волны в корне репозитория
осталось 13 мусорных файлов — ровно то, что произойдёт и у пользователя,
запускающего проверку из папки своего проекта.

## Разбор после КАЖДОЙ волны

Следующая волна запускается только после разбора предыдущей. По двум осям, и
вторая важнее первой.

**1. Механика.** Кто упал и почему. Добрать дельту до полного комплекта волны.

**2. Качество.** **Прочитать выборку реального результата** и сверить с
заданием: не пересказ ли это того, что уже было; нет ли запрещённой разметки; не
вода ли; верны ли факты. Считать одни успехи недостаточно — пять «успешных»
агентов способны выдать связный мусор, и на четырёх волнах это обнаруживается в
самом конце, когда испорчены уже сотни единиц контента.

Выборка не прошла — сначала правится промпт, только потом перезапуск.

## Рестарт только дельты

Собрать готовое из журнала → вычислить, чего реально нет → запустить точечно
недостающее. **Никогда** не перезапускать волну целиком ради пары упавших.

**`journal.jsonl` — источник истины, а не возврат Workflow.** Возврат показывает
`null` там, где в журнале лежит готовый результат: журнал append-only и переживает
падение. Сверяйся с журналом ПЕРЕД выводом «агент потерян» — на прошлых волнах
это спасло 11 готовых срезов и 103 карточки из 155.

**Дельта запускается тем же скриптом с `resumeFromRunId`.** Агенты с неизменёнными
`(prompt, opts)` возвращаются из кэша мгновенно, живьём идут только упавшие —
переписывать скрипт под «оставшихся» не нужно и вредно: теряется сопоставимость.

**«Упал» и «остановлен защитой» — разные вещи.** Различить их можно только по
`agent-*.jsonl`: отклонение выглядит как `tool_result` с текстом «The user doesn't
want to proceed with this tool use», за которым идёт «Request interrupted». Это не
дефект агента и не повод менять зону — это сигнал, что в промпте не хватает
запретов окружения (см. § Прогонным агентам). Лечится промптом, а не перезапуском.

## Темп: считать лимит сессии, а не гнать подряд

Длинная многоволновая работа упирается не в качество, а в **лимит сессии**, и
упирается всегда посреди волны: агенты падают с «You've hit your session limit»,
а их работа теряется целиком. На аудите 2026-08-10 это случилось дважды — 2 агента
в одной волне и 4 в другой.

Арифметика, по которой выбирается интервал между стартами:

- волна из 5 агентов стоит примерно **550k токенов субагентов** — это **9–10%**
  пятичасового окна лимита;
- значит в окно помещается **8–9 волн** с учётом расхода хоста на разборы,
  документ и issue;
- отсюда рабочий цикл — **40 минут от старта до старта** (волна идёт ~20 минут,
  остальное пауза).

```
30 минут  → 10 волн, ~95% лимита  → упрёшься в стену посреди волны
40 минут  → 7–8 волн, ~85%        → оптимум: запас есть, простоя нет
60 минут  → 5 волн, ~47%          → половина окна сгорает впустую, срок вдвое
```

**Проверка перед каждым стартом**, а не слепое расписание: пауза нужна, если
`(время до сброса ÷ длительность волны) × 9% > остаток лимита`. Если остатка
хватает — запускать сразу, ждать незачем.

Паузу ставить **фоновой задачей** (`sleep` в background), а не ожиданием в
диалоге: по её завершении приходит уведомление, и волна стартует сама.

### Остаток лимита: мерить, а не угадывать

Доступа к счётчику окна у агента **нет** — ни файла, ни инструмента. Но обе
составляющие расхода измеримы: и хост, и каждый субагент пишут в свой
`.jsonl` запись `usage` на каждый запрос. Отсюда единая метрика:

```
эквивалент = input + 0.1×cache_read + 1.25×cache_creation + 5×output
```

Складываются транскрипт хоста (`~/.claude/projects/<проект>/<сессия>.jsonl`) и
все `subagents/**/agent-*.jsonl`, с фильтром по времени начала окна. На
аудите 2026-08-10 потолок окна вышел **≈30.6 млн эквивалентных токенов**; две
контрольные точки владельца (73% и 81%) легли в модель с расхождением меньше
половины пункта.

Два следствия, из-за которых метрика и понадобилась:

- **Идущая волна видна сразу.** Субагенты пишут транскрипт в реальном времени,
  поэтому расход считается по ходу, а не постфактум из отчёта Workflow. Прежний
  способ (сумма `subagent_tokens` завершённых волн) занижал остаток на всю
  текущую волну — то есть ровно в момент, когда решение о старте и принимается.
- **Расход хоста не постоянен.** Он зависит от того, сколько раз владелец
  вмешался и **насколько длинным был контекст** в этот момент: обмен при
  раздутом контексте стоит втрое дороже, чем после сжатия (74k против 28k
  эквивалента на запрос). Фиксированной «базы хоста» не существует, её надо
  мерить. Для справки: доля хоста за окно аудита — 14–15% против 68–75% на
  субагентов, то есть участие владельца дёшево и сдерживать его незачем.

**Пороги по остатку** (шаг тем мельче, чем ближе стена — чтобы между замерами
не оставалось крупных прыжков вслепую):

```
≥15%   → полная волна из 5 агентов
8–15%  → максимум 2 агента, замер сразу после
5–8%   → один агент, замер сразу после
<5%    → пауза до сброса окна
```

Порог паузы держать низким: недельный лимит расходуется целиком, простой окна —
потерянная работа. Упереться в стену не катастрофа (см. следующий раздел), а вот
закрыть окно с четвертью неиспользованного запаса — чистый убыток.

### Агент, списанный на лимите попыток, работу НЕ потерял

`StructuredOutput retry cap exceeded` в отчёте Workflow означает, что **валидатор
отверг ответ**, а не что агент не справился. Валидатор не сообщает агенту, какое
именно поле нарушено, поэтому тот повторяет почти тот же ответ до исчерпания
попыток. На аудите 2026-08-10 так «погиб» стратегический агент, чей `fix`
оказался длиной 307 символов при `maxLength: 300` — вся его работа была готова.

Порядок действий: **сначала транскрипт, потом перезапуск.** Последний
`StructuredOutput` лежит в `agent-*.jsonl` целиком — его достаточно прочитать,
обрезать нарушающее поле и занести в накопитель хостом. Перезапуск волны ради
уже сделанной работы — двойная трата окна.

Отсюда же правило к схемам: **`maxLength` ставить с запасом** (+20% к
ожидаемому). Лишние символы не стоят ничего, потерянный агент — стоит волны.

### Обрезать текст молча нельзя — только с маркером обрыва

Обратная сторона того же лимита: если applier укладывает длинное поле в таблицу,
**обрезанный текст выглядит как полный**. Читатель не отличает «автор так
написал» от «здесь потеряно полфразы», и документ становится непроверяемым.

Прецедент: реестр отклонённых находок в
[docs/archive/audit-2026-07-30-full-roles.md](../archive/audit-2026-07-30-full-roles.md)
§ 6 — десять строк, у которых обе текстовые колонки обрываются посреди слова.
Ревизия следующего аудита (REV-5-01) потребовала «починить реестр», но чинить
оказалось нечего: обрезка была уже в первой ревизии файла, полного текста не
существует нигде. Работа десяти верификаторов сохранилась наполовину, и
перепроверить отклонения по документу больше нельзя — только по коду.

Правило: **обрезал — поставь `…` и число отброшенных символов** (тот же формат,
что у отчёта грейдера, — «… ещё N симв.»). Ещё лучше — не обрезать: положить
длинное поле отдельной строкой под таблицей, а в ячейке оставить ссылку.

## Дополнительно для аудитов

- **`file:line` + репро** у каждой находки — обязательно.
- **Адверсариальный верификатор** с установкой «опровергай по умолчанию»,
  отдельным агентом. На аудите v1.9.0 отсеял 7 находок из 32 как ложные.
- **Severity ставит верификатор**, а не автор находки (`corrected_severity`) —
  **но шкалу для него надо откалибровать примерами**. Без калибровки установка
  «опровергай» сдвигает вниз всю шкалу разом, а не отсеивает слабое: на аудите
  v1.10.0 верификаторы поправили severity у 141 находки из 192 (73%), почти все
  вниз, и подтверждённые (`CONFIRMED`) дефекты вроде «скачивание падает
  `ValueError`» оседали в `low`. Приоритет тогда приходится ставить по
  **риск-группам критика**, а не по механическому severity. В промпт скептика —
  три примера: что в этом проекте high, что medium, что low.
- **Прогон важнее чтения — и планируется от ПОВЕРХНОСТЕЙ, а не от файлов.**
  Подробности ниже отдельным разделом: правило «доля прогонных срезов» трижды
  подряд оказывалось недостаточным, потому что срезы планировались от того, что
  агенту удобно открыть, а не от того, чем пользуется человек.
- **Повторный аудит по тому же коду — с правилом новизны.** Второму проходу на вход
  подаётся файл находок первого и запрет: уже найденное находкой не считается, его
  можно только **углубить** (новое следствие, новый путь воспроизведения, реальный
  вывод команды вместо предположения) либо отбросить. Без этого правила второй
  аудит на 60% переоткрывает первый и стоит впустую целое окно лимита.
- **Критик полноты — последним.** Если после него дозапускались срезы, его вывод
  перечитывается заново.
- **У многофазного аудита критик проверяет МЕТОД своей фазы, а не проект.**
  Отдельная волна критиков в конце каждой фазы получает на вход накопитель и
  отвечает: какая доля находок фазы действительно новая, что фаза не проверила,
  где заявленный метод оказался мнимым. На аудите 2026-08-10 такая волна
  показала, что прогонная фаза покрыла треть исполнимой поверхности (меню и
  браузер не запускались ни разу), шла в одном окружении из девяти в
  CI-матрице и **не проверила ни одной находки предыдущей фазы** — при том, что
  ради этого фаза и затевалась.
- **В отчёт идёт подтверждённая severity, а не авторская.** Разрыв велик:
  на том же аудите авторы заявили 83 `high`, верификация оставила 16. Пока
  вердиктов нет, любые «сколько у нас high» — заявки, и называть их итогом
  нельзя. Сверять число находок с числом вердиктов перед каждым выводом.
- **Остаток окна добирать читающей волной ТЕКУЩЕЙ фазы, а не следующей.**
  Дешёвые читающие агенты есть в любой фазе (стратегия по накопителю, критики,
  сверка документов). Соблазн взять их из фазы вперёд ломает порядок: фаза
  остаётся недоделанной, а её критик уже отработал по неполным данным.
- **Пути в задании агенту сверять с `ls`, а не брать из документации.** На
  аудите 2026-08-10 два среза получили в списке файлов `src/stepik_grader/cli.py`,
  которого не существует: путь был взят из `CLAUDE.md`, где он указан ошибочно.
  Неверный документ уводит агентов ровно того аудита, который его и проверяет.
- Результаты складываются в [`../audit/`](../audit/README.md) и уезжают в
  [`../archive/`](../archive/README.md), когда все находки закрыты или отклонены.

### Аудит планируется от поверхностей продукта, а не от файлов

Правило «доля прогонных срезов» вводилось трижды и трижды не сработало. Причина
одна и та же: срезы планировались **от того, что агенту удобно открыть** —
модули, точки входа CLI, эндпоинты, — а не от того, чем пользуется человек.
Итог аудита 2026-08-10: прогонная фаза покрыла треть исполнимой поверхности,
интерактивное меню не вызывалось ни разу, **браузер не открывался вообще** — при
том, что веб является основной поверхностью продукта. Тот же дефект метода
ревизия нашла и у предыдущего аудита: прогон планировался от пунктов CLI-меню,
поэтому режим микробенча не запускался ни в одном из них.

**Первый шаг планирования — инвентарь поверхностей, а не список файлов.**
Выписывается всё, с чем человек фактически взаимодействует, и у каждой строки
обязан появиться прогонный срез:

```
Поверхность    Что проверяется                                           Где выполнимо
CLI            меню целиком (каждый пункт) · каждый флаг · коды возврата  облако
Веб            каждая вкладка В БРАУЗЕРЕ · тема · локаль · узкий экран    облако
Установка      чистая установка из пакета · без сети · чужой pyproject    облако
Данные         пустое · накопленное · повреждённое состояние              облако
Изоляция       песочница на своей ОС                                      облако
Платформы      вторая ОС · другие версии языка · без опциональных пакетов  только CI
Внешний API    живая сеть · реальный токен · графическая оболочка         только локально
```

Поверхность без прогонного среза — **не «пропустили», а слепая зона**, и её надо
назвать в документе явно, а не обнаружить постфактум критиком.

**Среда проставляется в тот же момент, что и срез.** Иначе поверхность выпадает
молча: агент не смог запустить, никому не сказал, и это всплывает у критика в
конце фазы. Три категории:

- **облако** — подавляющее большинство. В сессии есть песочница (`bwrap`), браузер
  (Chromium + Playwright), несколько версий Python, весь инструментарий тестов;
- **только CI** — вторая и третья ОС, версии языка вне образа. Задача ставится не
  «прогнать на macOS», а **«написать тест, который матрица прогонит на macOS»**;
- **только локально** — что упирается в закрытую сеть, реальный токен, реальные
  данные пользователя или графическую оболочку. Такие срезы **агентам облачной
  волны не отдаются вообще**: они собираются в отдельный список проверок для
  второго окна — с готовыми командами и ожидаемым результатом, а не с
  предложением «посмотреть, что будет».

Разница между средами — **не в мощности, а в доступе к настоящему**. Облачное
окно работает со свежим клоном из git и синтетическими фикстурами: секретов,
живой сети до Stepik и накопленной истории обучения там нет по устройству, а не
по недосмотру. Локальное окно — единственное место, где продукт запускается «как
у пользователя»: настоящий `secrets.json`, реальные задачи курса, месяцы
накопленных прогонов. Практический вывод для планирования аудита: **облако
проверяет узлы, локальное окно — цепочку**. Сквозной сценарий (скачал задачу →
решил → проверил → история записалась → «Прогресс» показал верное → «Подучить»
дал рекомендацию) в облаке честно не воспроизводится ни при каком старании
агента, и планировать его туда — заведомо ложный зелёный.

Раскладка окон, проверенные факты окружения, шаблон задачи для локального окна и
команды перепроверки — [`environments.md`](environments.md). Перед аудитом
сверять заново: образ и политика сети меняются.

**Порядок фаз в двухоконном аудите — там же, § Как проводить аудит в двух окнах.**
Коротко: локальное окно входит в аудит **дважды и коротко**, а не повторяет
облачные фазы. Сначала **фаза 0** — слепок реальности (формы накопленной истории,
реальные имена папок задач, окружение владельца), из которого строятся фикстуры
облачных волн: фикстура по настоящим объёмам ловит то, что синтетическая
пропускает. Потом весь массовый аудит в облаке, по ходу которого копится список
для локального окна — **с первой волны, а не в конце**. И в конце **фаза L** —
исполнение этого списка: сквозной сценарий, накопленные гипотезы,
[`local-sweep.md`](local-sweep.md) по реальной базе. Находка на локальной
поверхности, полученная в облаке на фикстуре, — **гипотеза**, а не находка:
severity она получает после подтверждения.

**Роль не заканчивается чтением.** Если предмет роли наблюдаем в работающем
продукте, у роли обязан быть прогонный подсрез: читающий подсрез без прогонного
не принимается. 🧪 запускает проверку решений во всех режимах, 🎨 смотрит вёрстку
в браузере, 🧠 открывает карточки глазами, 📊 сперва создаёт историю прогонами,
потом сверяет показанное с фактом, 🔐 пробует нарушить границу, а не рассуждает о
ней. Роли, чей предмет вне работающего продукта (📣 рост, 📢 реклама, 🚀 визионер),
остаются читающими — это единственное исключение, и оно фиксируется в плане.

**Веб проверяется в браузере, а не запросами.** `curl` подтверждает, что эндпоинт
отвечает, и ничего не говорит о том, что видит человек. Из 4875 строк фронтенда
чтение и запросы дали 2 находки, один браузерный прогон — 33, треть из них
недостижима чтением в принципе: пример в карточке распадается на плитки, плашка
перекрывает таблицу и глотает клики, переключатель схлопывается в 6 px.

Рецепт, проверенный на этом проекте (Playwright в опциональной группе `e2e`,
Chromium предустановлен, версии не совпадают — путь указывается явно):

```python
from playwright.sync_api import sync_playwright
EXE = '/opt/pw-browsers/chromium-<версия>/chrome-linux/chrome'
errs = []
with sync_playwright() as p:
    b = p.chromium.launch(executable_path=EXE)
    pg = b.new_page()
    pg.on('console', lambda m: errs.append(m.text) if m.type == 'error' else None)
    pg.on('pageerror', lambda e: errs.append(str(e)))
    pg.on('response', lambda r: errs.append((r.status, r.url)) if r.status >= 400 else None)
    pg.goto('http://127.0.0.1:<свой порт>/', wait_until='networkidle')
```

Ошибка в консоли, необработанный `pageerror` или 4xx при штатном действии — это
находка сама по себе, даже если внешне ничего не сломалось.

**Фикстуру готовит хост, а не агент.** Набор данных для прогона (задача с
тест-кейсами, верное решение, заведомо неверное, медленное) создаётся один раз до
волны и передаётся путём. Иначе каждый агент тратит половину бюджета инструментов
на подготовку и делает её по-своему — результаты перестают быть сопоставимыми.
Каждому агенту — **свой порт и свой рабочий каталог**, иначе они мешают друг другу.

**Фазы различаются методом, а не темой.** Одна тема, пройденная пять раз одним
способом, даёт пять раз одно и то же. Рабочая последовательность аудита
2026-08-10, по одной фазе на метод:

```
1. чтение кода            широкий охват, дёшево, находит структурное      8 high / 489
2. запуск продукта        дорого, узко, находит неверный вердикт          7 high / 224
3. документы как система  сверка пар: документ против кода и документа    0 high / 127
4. ревизия прошлого       что числится закрытым, но живо                  1 high /  58
5. браузер                то, что ломается только в рендере               4 medium / 34
```

Плотность тяжёлых дефектов у прогона впятеро выше, чем у чтения (8.3% против
1.6%). Документационная фаза не даёт `high` — и это её честная граница, а не
провал: расхождение README с кодом не портит вердикт грейдера.
