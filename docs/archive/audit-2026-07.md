### Сводный вердикт

Проект в **отличной инженерной форме**: дисциплина процессов (Conventional
Commits, CHANGELOG в каждом PR, CI-матрица на 3 ОС, guardrail-скрипты,
динамическая версия) на уровне зрелых open-source библиотек. Архитектурный
DAG соблюдён, God-object'ов нет, тесты содержательные (ratio 1.3:1).

Три системные темы, которые стоит признать и планомерно закрывать:

1. **«Двойники»** — параллельно живут две системы исполнения
   (`executor.py` legacy и `runner.py`), два i18n (JSON-локали и
   захардкоженный словарь CLI), **два глоссария** (компактный
   `core/glossary.py` на ~29 исключений для CLI и JSON-база на 1413
   карточек, которую CLI не видит), три стратегии URL карточек. Это цена
   быстрых итераций; пора консолидировать.
2. **Аналитика эфемерна** — результаты прогонов нигде не персистятся:
   web-история живёт в localStorage браузера (10 записей), job'ы — в памяти
   с TTL 15 мин, `.grader_stats.jsonl` хранит только тальи вердиктов и
   web-слоем не используется. Именно поэтому разделы «частые ошибки»
   сегодня построить не на чем — нужна история (эпик #130).
3. **Точечный дрейф документации** — 4 места в корневых доках и 6 в
   web-доках (детали в § 7); особенно: CLAUDE.md сам себе противоречит про
   sandbox (инвариант «Нет sandbox» против собственной сноски про
   `--sandbox`/#266).

## 1. 🏛️ Архитектор

**Слои (фактические, сверено с docs/architecture.md):**

```
CLI (cli/*, grader.py-фасад)          WEB (web/server.py, stdlib http.server)
        │                                     │
        ▼                                     ▼
core/grader_core ── core/reporter      web/viewmodels · runs · adapters
        │                                     │ (in-memory jobs, TTL 15 мин)
        ▼                                     ▼
   Runner Protocol ──► LocalRunner ──► subprocess
        │                └─ opt-in SandboxRunner (linux/macos/windows backends)
        ▼
core/result (контракт) · normalizers · cache · stats     ← leaf-слой
glossary/ (JSON, 1413 карточек) ◄─ web/glossary_adapter
core/glossary.py (компакт, ~29 исключений) ◄─ core/reporter (CLI)
```

**Сильно:** циклов импортов нет (проверено grep'ом); leaf-модули чисты;
`Runner` Protocol (#140) — готовая точка подмены исполнения для будущего
сервера; прецедент opt-in extras (`[watch]`, `[e2e]`) — правильный механизм
для опциональных подсистем; sandbox не деградирует молча
(`SandboxUnavailableError`, `core/sandbox/__init__.py:41`).

**Риски (по убыванию важности):**

- **R1. `--sandbox` не действует на `--serve`.** Ветка `--serve`
  возвращается из `cli/__init__.py:597-602` **до** вызова `set_runner()`
  (`:611-620`) — код из web-редактора и песочницы всегда исполняется
  `LocalRunner`'ом с полными правами пользователя, даже если человек явно
  попросил sandbox. Это документировано как «нет sandbox в web»
  (`web/server.py:14-16`), но с точки зрения UX — тихое игнорирование
  явного флага безопасности. Либо честная ошибка «--sandbox с --serve не
  поддерживается», либо проброс раннера.
- **R2. Глобальное мутабельное состояние.** `_RUNNER`
  (`grader_core.py:193/203`, без лока), кэш конфига, `_LANG`; плюс
  **замороженные при импорте алиасы** `TIMEOUT_SECONDS/ENCODING/...`
  (`grader_core.py:125-130`) — изменение `CONFIG` после импорта не
  действует. Для многопоточного web-слоя это мины замедленного действия.
- **R3. Файловые записи без блокировок.** Ротация статистики —
  read-modify-write (`core/stats.py:52-57`), очередь глоссария «прочитай
  весь файл и перепиши» (`glossary/json_provider.py:232-247`) — параллельные
  web-запросы могут терять записи. До SQLite (WAL) — хотя бы `threading.Lock`
  на процессном уровне.
- **R4. Двойники** (см. сводный вердикт): выделю **два глоссария** — CLI
  показывает подсказки только из компактной карты (`reporter.py:349`),
   1413 JSON-карточек ему недоступны; третий вид карточек («правила»)
  усилит рассинхрон, если не свести источники.
- **R5. Фасады фиксируют приватные имена**: `grader.py` (wildcard
  реэкспорт + ~30 приватных имён) и реэкспорты `cli/__init__.py:54-79`
  ради monkeypatch-тестов — скрытая поверхность обратной совместимости.
- **R6. Монолит `app.js` (2358 строк)** vanilla-JS с ручной конкатенацией
  HTML: для текущих 4 разделов — на пределе управляемости; каждый новый
  раздел дописывает захардкоженный `setSection()` (`app.js:303-321`) и
  hash-роутер, который знает только глоссарий (`:2094`). Нужен общий
  реестр разделов/маршрутов до добавления новых.
- **R7. Персистентности нет вообще** (см. § сводный вердикт, п. 2) — для
  задуманных «частых ошибок» это блокер №1; правильно, что эпик #130 уже
  заведён.

**Стратегическая рекомендация:** перед новыми фичами — микрорелиз гигиены
(R1-R3 + дрейф доков + релиз v1.8.0), затем фундамент #130, затем разделы
«Правила»/«Подучить» (§ 9). Порядок важен: карточки без истории — пустышка,
история без затухания — свалка.

## 3. 🐍 Core Python Dev

**Похвала.** Образцовое современное упакование: PEP 621 + PEP 639
(SPDX-license), PEP 561 (`py.typed`), динамическая версия setuptools-scm,
union-типы вместо `Optional`, `Protocol` + `@runtime_checkable`, dataclass'ы
с `field(default_factory=...)`, `sys.executable` для subprocess. Голых
`except:` — ноль; широкие `except Exception` — точечно и с `noqa: BLE001`.

**Замечания:**

- `core.grader_core` в TYPE_CHECKING (`reporter.py:22`) — см. § 2 п. 1;
  это единственное место, где типизация фактически «дырявая».
- `os.path.relpath` → `Path.relative_to(other, walk_up=True)` — прямой
  идиоматичный аналог, доступен с 3.12 (проект и так требует 3.12+).
- Для будущей PEP-проверки **не пишите свой чекер на tokenize/ast**:
  в stdlib нет PEP 8-линтера, а самописный чекер = переписать pycodestyle
  с вечной поддержкой. Правильный путь — **opt-in extra** по прецеденту
  `[watch]`/`[e2e]`: `lint = ["ruff>=0.15"]`. Ruff уже доверен проекту
  (dev-зависимость), это один бинарный wheel без транзитивных зависимостей,
  выдаёт машиночитаемый JSON (`ruff check --output-format json`) и покрывает
  коды pycodestyle (E/W), pyflakes (F) и далее. Нет extra — раздел «Правила»
  честно скрыт с подсказкой «pip install stepik-python-grader[lint]».
- Для истории ошибок **`sqlite3` из stdlib — идеален** и не нарушает
  инвариант «3 runtime-зависимости»: WAL-журнал решает проблему
  конкурентных записей CLI+web (R3), `PRAGMA user_version` — простейшие
  миграции, `executescript` — схема одним файлом. Никакого ORM не нужно.
- Педагогическая деталь: карточки правил должны учить **духу** PEP 8
  («A Foolish Consistency is the Hobgoblin of Little Minds») — каждое
  правило объясняет «почему», а не только «что нельзя».

**Состояние.** 1308 passed / 22 skipped; матрица ubuntu/windows/macos ×

**Дыры и риски:**

- **`app.js` (2358 строк) — фактически вне измерения покрытия**: клиентскую
  логику проверяют только e2e-смоуки (4 сценария) вне дефолтного прогона.
  Самое слабое место тестовой стратегии.
- **Sleep-поллинг** в тестах web/runs/playground:
  `test_web_playground.py:113` («дать воркеру стартовать», 0.2 с),
  `test_runs.py:37/66/140/162/244`, `test_web.py:1378/1470/1486/1634` —
  тайминг-зависимы, кандидаты во flaky на медленных CI-агентах. Лечится
  ожиданием события/условия с дедлайном (паттерн уже есть в e2e:
  `wait_for_selector`).
- **Property-based тестов нет** (hypothesis) — а нормализаторы вывода,
  парсеры тест-форматов и сравнение float-ов прямо просятся.
- **Заморозки времени нет** (freezegun/инъектируемые часы) — единственный
  прецедент «времени» это TTL-оффсеты. **Вывод для дизайна затухания
  (§ 9): считать затухание по номерам прогонов, а не по календарю** —
  тогда весь механизм тестируется чистыми функциями без часов.

**Тестируемость новых фич — что уже готово:** прецеденты персистентности
`test_cache.py` (218 строк: roundtrip, битый файл, инвалидация) и
`test_stats.py` (append, агрегация, пропуск битых строк, ротация через
monkeypatch `_MAX_BYTES`) + повсеместная инъекция пути. SQLite-слой обязан
принимать `db_path` параметром — и тестируется на `tmp_path` без моков.

**Обязательные тест-кейсы для § 9:** битая/чужая БД (graceful, не ронять
грейдинг — принцип stats/cache); конкурентная запись CLI+web (WAL);

## 5. 📊 Продуктовый аналитик

**JTBD сейчас:** «Когда я решаю задачу Stepik локально, я хочу мгновенно
прогнать её по тестам, чтобы сдать с первой попытки». Закрыт хорошо
(режимы 1-4, web, песочница).

**JTBD, который открывают фичи 1-5:** «Когда мои решения падают или
работают медленно, я хочу понять, **какие ошибки я повторяю**, чтобы
перестать их делать». Сегодня инсайт умирает в момент закрытия вкладки
(localStorage, 10 записей) — обучающей петли нет. Раздел «Подучить» — это
**петля удержания**: причина вернуться в инструмент между задачами.

**Метрики успеха (локальные, приватные — телеметрии в проекте нет
по философии, и это правильно):** доля прогонов с повторной ошибкой того же
класса; время до первого зелёного прогона (TTFG) по задаче; число активных
карточек «Подучить» и скорость их затухания (= прогресс ученика); долю WA
из-за формата вывода (гипотеза: лидер) — всё это считается SQL-запросами по
локальной истории и показывается самому пользователю.

**Предостережения:**

- Карточка должна появляться **в момент боли** — рядом с упавшим тестом
  (мини-карточка в результатах, § 9.5), а раздел «Подучить» — агрегатом.
  Отдельный раздел без врезки в результаты работать не будет (баннерная
  слепота).
- **PEP-педантизм отпугивает новичков.** Порядок подачи: сначала «тесты
  зелёные?», потом «а теперь сделаем красиво». Lint-нарушения не должны
  влиять на вердикт и не должны кричать красным (§ 6 Дизайнер согласен).
- Затухание (п. 5 хотелок) — продуктово главное: карточка, которая гаснет,
  даёт чувство прогресса; карточка, которая висит вечно, — чувство вины.
  Показывать «исправлено N правил за месяц» (архив побед).

## 9. Дизайн фич 1-6: «Правила/PEP» + «Подучить» на SQLite (совместное решение ролей)

Маппинг хотелок владельца на план: (1) раздел «Правила/PEP» → § 9.4;
(2) раздел «Подучить/частые ошибки» → § 9.5; (3) сбор падений в базу →
§ 9.2-9.3; (4) PEP-проверка с мини-карточками → § 9.4; (5) затухание →
§ 9.3; (6) SQL → да, SQLite (эпик #130 уже открыт — фичи ложатся в него и
поверх него).

### 9.1 Принципы

- **Никакой телеметрии** — база локальная, в рабочей папке, в .gitignore.
- **Lint не влияет на вердикт** — информационный канал (продукт+дизайн).
- **Затухание по прогонам, а не по календарю** — тестируемость (QA).
- **Graceful degradation** — нет ruff → раздел «Правила» скрыт с
  подсказкой; битая БД → грейдинг работает, как с битым кэшем.
- **Переиспользуем паттерны глоссария** — модель карточки, JSON-провайдер,
  mtime-кеш, фасетные фильтры, бейджи, hash-роуты.

### 9.2 Хранилище: `.grader_history.db` (SQLite, stdlib)

Новый leaf-модуль `core/history.py` (по образцу cache/stats: DI пути,
best-effort, `__all__`): `PRAGMA journal_mode=WAL` (конкурентные CLI+web
записи), `PRAGMA user_version` для миграций, `PRAGMA foreign_keys=ON`.

```sql
CREATE TABLE runs (
    id            INTEGER PRIMARY KEY,
    ts_utc        TEXT    NOT NULL,   -- ISO-8601 UTC
    mode          INTEGER NOT NULL,   -- 1..4
    source        TEXT    NOT NULL,   -- 'cli' | 'web'
    task_key      TEXT    NOT NULL,   -- отн. путь папки задачи ('' если нет)
    solution_name TEXT,
    solution_hash TEXT,               -- sha256 кода
    duration_s    REAL
);
CREATE TABLE case_results (
    run_id       INTEGER NOT NULL REFERENCES runs(id) ON DELETE CASCADE,
    case_no      INTEGER NOT NULL,
    verdict      TEXT    NOT NULL,    -- AC|WA|RE|TLE|CANCELLED|SANDBOX_VIOLATION
    time_ms      REAL,
    error_class  TEXT,                -- имя исключения для RE ('IndexError')
    failure_kind TEXT,                -- таксономия § 9.3
    PRIMARY KEY (run_id, case_no)
);
CREATE TABLE lint_violations (
    run_id    INTEGER NOT NULL REFERENCES runs(id) ON DELETE CASCADE,
    rule_code TEXT    NOT NULL,       -- 'E501', 'W291', 'F841', ...
    line_no   INTEGER NOT NULL,
    message   TEXT
);
CREATE INDEX idx_runs_task   ON runs(task_key, id);
CREATE INDEX idx_cases_kind  ON case_results(failure_kind);
CREATE INDEX idx_lint_rule   ON lint_violations(rule_code);
```

Все данные для записи **уже существуют** в момент вызова
`stats.record_run()` (cli/commands.py:152/223/290/431): per-case
`verdict/time/error/diff` — в `result["cases"]`, имя исключения достаёт
`glossary.lookup_from_error()`. Схема БД = «то же, но не выброшено».
Включение: CLI — opt-in (`--history`, issue #134 «по умолчанию без БД»);
web — включено по умолчанию с тумблером в настройках (см. § 11 п. 3).
`.grader_stats.jsonl` не трогаем (не мигрируем, не ломаем) — сводка
`--stats-summary` продолжает работать; позже можно свести.

### 9.3 Таксономия падений и затухание

`failure_kind` вычисляется чистой функцией классификации при записи:

| kind | Правило | Источник данных |
|---|---|---|
| `output-format` | WA, diff только в trailing-пробелах/пустых строках/регистре | diff + normalizers |
| `wrong-answer` | остальные WA | verdict |
| `runtime-error:<Класс>` | RE | последняя строка stderr (как lookup_from_error) |
| `timeout` | TLE | verdict |
| `slow` | режимы 3/4: SLOWER/MUCH_SLOWER | BenchStats |

**Ключ карточки «Подучить»** = `failure_kind` (для падений) или
`rule_code` (для lint). **Статус** — чистая функция от истории последних
прогонов (окно N=10, порог активности T=2, чистая серия K=3;
конфигурируемо в `[tool.stepik-grader]`):

```
активна:  ключ встречался в ≥T из последних N прогонов
угасает:  была активна, последние 1..K-1 прогонов чистые
архив:    ≥K чистых прогонов подряд (пропадает из «Подучить» — п. 5 хотелок,
          остаётся в «архиве побед»)
```

Считается SQL-запросом + `classify_status(история: list[bool]) -> Status` —
без часов, без хранимого состояния, тестируется таблично (QA § 4).

### 9.4 Раздел «Правила» и lint-интеграция (пп. 1 и 4)

- **Данные**: пакет `rules/` по образцу `glossary/`: `models.py`
  (`RuleCard`: id=код правила, title, summary, body-Markdown, `pep_url`,
  severity, tags, examples bad/good), `json_provider.py`,
  `data/pep8_ru.json` (стартовый набор: ~30 самых частых E/W/F-кодов),
  общая утилита mtime-кеша (вынести из glossary_adapter, не копипастить).
- **Чекер**: `core/lint.py` — subprocess `ruff check --output-format json
  --select E,W,F <file>` при наличии ruff (opt-in extra `[lint]`);
  граммотный fallback: ruff нет → `LintUnavailable`, UI скрывает блок.
  Свой AST-чекер не пишем (§ 3).
- **UI**: раздел «Правила» = клон списка/деталей глоссария (list + detail +
  фильтры по тегам + `#/rules/<code>`); в результатах проверки — блок
  «Стиль» с чипами-кодами (§ 6), клик → карточка. Частое правило
  автоматически видно в «Подучить» (§ 9.3 — тот же механизм, ключ
  `rule_code`), это и есть п. 4→2 хотелок.
- **CLI**: `--lint` флаг в режимах 1/2 — блок после результатов (через
  `_console`).

### 9.5 Раздел «Подучить» (пп. 2, 3, 5)

- `GET /api/insights` → карточки: ключ, статус, счётчики (падений/прогонов),
  «затухание ▰▰▱», ссылки на карточку глоссария (для `runtime-error:*` —
  по классу исключения, база уже связана: `related_errors` в GlossaryCard)
  или правила (для lint-ключей), последние задачи, где встречалось.
- Web-раздел «Подучить» с бейджем активных карточек в sidebar; CLI —
  `stepik-grader insights` (терминальная сводка тех же данных).
- Пустые состояния и тон — § 6.

### 9.6 Этапы и критерии приёмки

- **Э0 (фундамент, закрывает часть эпика #130):** `core/history.py` +
  схема v1 + запись из commands.py + `.gitignore` + тесты
  (tmp_path, WAL-конкуренция, битая БД, миграция). БД не обязателен для
  CLI по умолчанию (#134).
- **Э1 (Правила):** rules/ + core/lint.py + extra `[lint]` + web-раздел +
  чипы в результатах + CLI `--lint`. AC: без ruff всё работает как раньше;
  карточка открывается по клику на код; 30 карточек в базе.
- **Э2 (Подучить):** таксономия + запись lint_violations + statuses +
  /api/insights + раздел + CLI insights. AC: ошибка, исправленная K прогонов
  подряд, исчезает из активных (п. 5 хотелок) и появляется в архиве;
  сценарный тест «3 падения → карточка → 3 чистых → архив».
- **Э3 (полировка):** экспорт прогресса, покрытие правил (аналог
  glossary coverage: все коды ruff vs наша база карточек), spaced-повторение.

**Не-цели:** телеметрия/сеть; блокировка вердикта линтером; серверная БД
(PostgreSQL — только как эволюция схемы, issue #154); автофиксы кода.
