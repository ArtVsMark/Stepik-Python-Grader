# ADR-0008 — Класс sandbox-backend для server mode

- **Статус:** Proposed
- **Дата:** 2026-07-16
- **Связанные issue:** #153 (этот ADR + дизайн), #157 (требования sandbox), #151 (эпик server mode)
- **Связанный дизайн:** [server-sandbox-design.md](../server-sandbox-design.md),
  [server-mode.md § Sandbox и сетевая изоляция](../server-mode.md#sandbox-и-сетевая-изоляция-issue-157)
- **Дополняет:** [ADR-0001](0001-server-mode.md) (направление server mode —
  сознательно оставил выбор механизма открытым; этот ADR сужает его до *класса*
  backend, всё ещё не начиная реализацию)
- **Отличать от:** [ADR-0007](0007-sandbox-backends.md) — тот про **локальный
  opt-in `--sandbox`** (три нативных backend'а по ОС, issue #266); этот — про
  **серверный** backend для недоверенного кода многих клиентов

## Контекст

[ADR-0001](0001-server-mode.md) зафиксировал направление на server mode через
абстракцию `Runner` и сознательно **не** выбирал механизм изоляции («Docker/
nsjail/VM — этап реализации»). [server-mode.md § #157](../server-mode.md#sandbox-и-сетевая-изоляция-issue-157)
перечислил **обязательные требования** к `SandboxRunner` в server mode (сеть
off, эфемерные tmp-каталоги, жёсткие квоты, изоляция клиентов), но не то, каким
классом технологий они закрываются.

Issue #153 просит следующий шаг дизайна: **спроектировать SandboxRunner с
контейнерами и resource limits** — то есть сузить пространство решений до
конкретного класса backend, чтобы будущая реализация (фаза 2-server,
[server-mode.md § Фазовая миграция](../server-mode.md#фазовая-миграция)) не
начиналась с чистого листа. Это по-прежнему **дизайн**: ни зависимостей, ни
демонов, ни кода сервера (запрет [CLAUDE.md](../../CLAUDE.md), Non-goals
server-mode.md).

Локальный MVP `--sandbox` ([ADR-0007](0007-sandbox-backends.md), issue #266,
`core/sandbox/`) уже закрывает часть требований на одной машине (bubblewrap/
`sandbox-exec`/Job Objects), но **не** мультитенантный сетевой сервер: без
аутентификации, очереди, per-client изоляции и (на Windows) сетевой изоляции.

## Решение

1. **Класс backend для server mode — контейнер уровня ОС на Linux-хосте**
   (namespaces + cgroups v2 + seccomp), а **не** микро-VM по умолчанию и **не**
   расширение локального per-process `--sandbox` на сеть. Обоснование и
   сравнение — [server-sandbox-design.md](../server-sandbox-design.md).
2. **Жёсткие лимиты — через cgroups v2** (`memory.max`, `cpu.max`, `pids.max`),
   а не через POSIX `resource`-лимиты (последние — best-effort, обходятся и не
   дают per-tenant учёта). Это закрывает требование #157.3 «реальный лимит
   памяти, а не best-effort».
3. **Сеть off — через сетевой namespace без интерфейсов** (`unshare(CLONE_NEWNET)`
   без `veth`), не через firewall-правила. Закрывает #157.1.
4. **Профиль по умолчанию — rootless** (user namespaces), с явно
   задокументированным fallback на privileged-контейнер там, где хост запрещает
   unprivileged userns (тот же класс ограничения, что вскрыт в CI, issue #420).
5. **Backend остаётся за абстракцией `Runner`.** Конкретный рантайм (runc/crun/
   youki, gVisor как усиление, Firecracker для сильной мультитенантности) —
   **параметр развёртывания**, не жёсткая зависимость кода: `SandboxRunner`
   говорит с OCI-совместимым рантаймом через тонкий адаптер. Выбор конкретного
   рантайма и его установка — этап реализации/деплоя, не этот ADR.
6. **Windows/macOS-хосты для server mode с недоверенным кодом не
   поддерживаются** — сетевой namespace-изоляции там нет (см. server-mode.md);
   server mode — Linux-only, локальный `--sandbox` на них остаётся как есть.

Это решение **не** начинает реализацию: `SandboxRunner`-класс в `core/sandbox/`
для server mode не пишется, зависимости не добавляются. ADR сужает пространство
решений и даёт будущей реализации спецификацию, а не откладывает выбор целиком.

## Альтернативы

- **A. Микро-VM (Firecracker/Cloud Hypervisor) по умолчанию.** Плюс: сильнейшая
  изоляция (отдельное ядро), гейт против kernel-эскалации. Минус: тяжелее
  (образ ядра/rootfs на прогон, ~100–200 мс старт), сложнее эксплуатация, KVM на
  хосте обязателен. Отклонено **как дефолт**, но оставлено как рекомендованное
  **усиление** для публичной мультитенантности (фаза 4) — см. дизайн-документ.
- **B. Расширить локальный per-process `--sandbox` (bubblewrap, ADR-0007) на
  сеть и выставить наружу.** Плюс: переиспользует готовый `core/sandbox/`.
  Минус: bwrap per-process не даёт per-tenant cgroup-учёта, очереди и
  мультитенантной изоляции; на Windows нет сетевой изоляции вовсе. Отклонено: не
  масштабируется до сервера, размывает границу «локальный opt-in» vs «серверная
  изоляция».
- **C. gVisor (`runsc`) по умолчанию.** Плюс: перехват syscalls в user-space —
  сильнее обычного контейнера, легче микро-VM. Минус: заметный оверхед на
  syscall-heavy код (влияет на bench-вердикты — конфликт с назначением
  грейдера), не все syscalls поддержаны. Отклонено **как дефолт**, оставлено
  опцией усиления, где скорость не критична.
- **D. Docker Engine как обязательная зависимость.** Отклонено: тяжёлый демон
  против запретов CLAUDE.md; привязка к одному рантайму. Вместо этого — тонкий
  адаптер к OCI-рантайму (см. решение 5), Docker становится *одним из* возможных
  деплой-вариантов, а не требованием.
- **E. Контейнер ОС-уровня, rootless, cgroups v2 + netns + seccomp (выбрано).**
  Баланс изоляции, веса старта и эксплуатационной простоты; закрывает все
  требования #157 на Linux; не привязан к конкретному рантайму; допускает
  усиление (gVisor/микро-VM) как параметр деплоя без переписывания.

## Последствия

**Положительные:**

- Будущая реализация фазы 2-server имеет спецификацию класса backend и механик
  лимитов, а не открытый вопрос.
- Требования #157 отображены на конкретные примитивы Linux (cgroups v2/netns/
  seccomp) — проверяемо и без привязки к вендору.
- Возможность усиления (gVisor/микро-VM) сохранена как параметр деплоя.

**Отрицательные / издержки:**

- Server mode фиксируется как **Linux-only** для недоверенного кода — Windows/
  macOS-хосты вне поддержки (это и так следовало из server-mode.md, теперь
  явно).
- Rootless-профиль требует unprivileged user namespaces на хосте; где их нет —
  нужен privileged fallback (та же оговорка, что в CI #420).

**Нейтральные:**

- Конкретный OCI-рантайм и оркестрация (очередь, автоскейл) остаются решением
  деплоя — этот ADR их не выбирает.

## Миграция (фазы)

Не меняет фазовую карту [server-mode.md](../server-mode.md#фазовая-миграция):
решение применяется на **фазе 2-server** (реализация `SandboxRunner` для
сервера) и далее. Фазы 0–1 (локальный CLI/`--serve`, Runner-абстракция) и
локальный `--sandbox` MVP (ADR-0007, #266) не затрагиваются.
