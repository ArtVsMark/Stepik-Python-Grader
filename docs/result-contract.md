# Контракт результата проверки (CLI / Web / API)

> Документ-контракт (issue #116). Фиксирует **форму данных**, которую ядро
> отдаёт про один тест-кейс и про решение целиком, чтобы CLI, веб-оболочка
> (`--serve`) и будущий API/сервер (см. [server-mode.md](server-mode.md))
> опирались на один стабильный набор полей, а не переизобретали его.
>
> Это **контракт**, не описание реализации: имена полей и семантика вердиктов
> здесь канонические. Продуктовые ViewModel'и веб-слоя (`ResultViewModel`,
> `ErrorCard`) — надстройки над этим контрактом, канонично описаны в
> [web-current.md § Контракты данных](web-current.md#контракты-данных) и здесь не
> дублируются. Форматы тест-кейсов и таблица вердиктов — в
> [configuration.md](configuration.md#формат-тест-кейсов).

## Уровни контракта

Проверка возвращает данные на трёх уровнях. Каждый последующий агрегирует
предыдущий:

| Уровень | Что описывает | Кто строит | Форма сегодня |
|---|---|---|---|
| **Case result** | Один тест-кейс на одном решении | `core.grader_core.run_single_test` | `CaseResult` (TypedDict) |
| **Solution result** | Одно решение на всех кейсах (агрегат) | `run_tests` / `run_benchmark` | `dict[str, Any]` |
| **Run result** | Прогон пути (файл/папка) — набор решений | адаптер (`cli.py`, `web.grade_path`) | `dict` / `ResultViewModel` |

Case-уровень формализован как `CaseResult` (`TypedDict`,
`core.result`, issue #442): mypy проверяет ключи и типы полей во всей цепочке
CLI→web→pytest-плагин, но **runtime-представление остаётся обычным `dict`** —
это по-прежнему та же форма на границе JSON-вывода. Solution/Run-уровни пока
остаются нетипизированными `dict` ядра (см. docstring `run_tests`); Web маппит
их в JSON ViewModel. Контракт описывает **имена и смысл полей**, а не
конкретный Python-тип — любая типизированная модель (`CaseResult`, `TestResult`)
обязана сохранить эти имена.

## Case result — поля

Возврат `run_single_test` (режимы 1–3). Источник истины полей — docstring
функции; здесь — их семантика и стабильность.

| Поле | Тип | Всегда | Описание |
|---|---|:--:|---|
| `passed` | `bool` | ✓ | Прошёл ли кейс (вывод совпал с ожидаемым) |
| `verdict` | `"AC"\|"WA"\|"TLE"\|"RE"\|"CANCELLED"\|"SANDBOX_VIOLATION"` | ✓ | Вердикт кейса (см. ниже); при ошибке до запуска — `"RE"` |
| `output` | `list[str]` | ✓ | Фактический вывод решения (строки) |
| `expected` | `list[str]` | ✓ | Ожидаемый вывод кейса (строки) |
| `diff` | `str` | ✓ | Unified-diff при несовпадении; пустой при `AC` |
| `time` | `float` | ✓ | Время выполнения, секунды |
| `memory` | `float` | ✓ | Пик памяти, МБ (`0.0`, если замер выключен) |
| `error` | `str` | ✓ | Сообщение об ошибке; пустая строка = ошибки нет |
| `timed_out` | `bool` | ✓ | Истёк ли таймаут |
| `exit_code` | `int \| None` | ✓ | Код возврата процесса решения; `None`, если процесс не завершился нормально (ошибка запуска/таймаут) — issue #125 |
| `stdin` | `str` | — | `NotRequired` (issue #397): stdin кейса, если он был подан на вход решению; ключ отсутствует, когда входа не было |

**Инвариант согласованности:** `verdict` — производное от остальных полей и
должно с ними согласоваться:

- `AC` ⟺ `passed is True`;
- `TLE` ⟹ `timed_out is True`, `passed is False`;
- `RE` ⟹ `error != ""` (и/или ненулевой код возврата процесса), `passed is False`;
- `WA` ⟹ `passed is False and not timed_out and error == ""` — вывод получен,
  но не совпал; `diff` непустой.
- `CANCELLED` ⟹ `passed is False`, `timed_out is False`, `error != ""` — кейс
  прерван через `cancel_event` (async job-модель, issue #262), не таймаутом
  и не ошибкой решения; UI не должен показывать его как провал решения.
- `SANDBOX_VIOLATION` ⟹ `passed is False`, `timed_out is False`, `error != ""`
  — только у `SandboxRunner` (`--sandbox`, issue #266): решение превысило
  sandbox-квоту (память/процессы/сеть/ФС/размер вывода), `LocalRunner`
  никогда не даёт этот verdict. В отличие от `CANCELLED` — это провал
  решения (реально сделало что-то запрещённое), UI может стилизовать как
  ошибку (см. `core/reporter._STATUS_COLORS`).

Потребитель может доверять `verdict` как единственному полю для ветвления UI,
не пересобирая логику из `passed`/`timed_out`/`error`.

## Вердикты (семантика)

Канонический список — [configuration.md § Вердикты](configuration.md#вердикты-тест-кейсов).
Контрактно закреплено:

| Вердикт | Значение | Терминальность |
|---|---|---|
| `AC` | Accepted — вывод совпал | успех |
| `WA` | Wrong Answer — вывод не совпал | провал (детерминированный) |
| `TLE` | Time Limit Exceeded — превышен таймаут | провал (недетерминированный по времени) |
| `RE` | Runtime Error — процесс упал / ошибка до запуска | провал (крэш) |
| `CANCELLED` | Cancelled — прерван пользователем через async job-модель (issue #262) | не провал; терминально, но не оценивает решение |
| `SANDBOX_VIOLATION` | Sandbox Violation — превышена квота изоляции (issue #266, только `--sandbox`) | провал (решение нарушило sandbox) |

Бенчмарк-режимы (3/4) добавляют **перформанс-вердикты** решения (не кейса):
`SIMILAR` / `SLOWER` / `MUCH SLOWER` относительно быстрейшего решения —
пороги `similar_threshold`/`much_slower_threshold`
([configuration.md](configuration.md#toolstepik-grader-в-pyprojecttoml)). Они
живут на уровне solution result и не смешиваются с корректностными вердиктами
кейса.

Там же возможен `SKIPPED` (issue #729) — решение **не допущено к замеру**:
пре-флайт (один прогон тестов перед бенчмарком) показал, что оно не проходит
тесты. Строка приходит без метрик (`runs: 0`, нет `median`), с человекочитаемой
причиной в `error` вида «не прошёл проверку: 2 из 3 (первый провал: WA)», и не
участвует в ранжировании. Сравнивать по времени решения с разным результатом
бессмысленно: `run_benchmark` меряет время, не сверяя вывод, поэтому до #729
решение с неверным ответом получало медиану и место в рейтинге наравне с
корректными. Отсутствие тест-кейсов — **не** `SKIPPED`: там нечего сверять, и
режим сообщает об этом своим обычным «нет тест-кейсов».

## Форма ошибки и таймаута

- **RE.** `error` содержит человекочитаемое сообщение; для реального крэша
  процесса — фрагмент stderr/трейсбека. Ошибки до запуска (не найдено имя
  функции, битый wrapper) тоже дают `verdict="RE"` с заполненным `error` и
  `time=0.0` — потребитель не должен различать «упал в рантайме» и «не удалось
  собрать запуск» по форме результата, только по тексту `error`.
- **TLE.** `timed_out=True`, `verdict="TLE"`, `time` ≈ лимиту
  (`CONFIG.timeout_seconds`). Частичный `output` может присутствовать.
- **Микро-бенчмарк (режим 4).** Локального per-call таймаута нет — зависание
  упирается в общий `subprocess.run(timeout=60)`; сообщение об ошибке содержит
  `number=<N>` (см. [configuration.md § Ограничения](configuration.md#ограничения-и-безопасность)).
- **Секреты.** `error`/`diff`/`output` — это вывод пользовательского решения;
  токены и содержимое `secrets.json` в них попадать не должны (см.
  [SECURITY.md](../SECURITY.md)). Для будущего логирования — правила редакции в
  [logging.md](logging.md).

## Solution result и Run result

- **Solution result** (`run_tests`) агрегирует кейсы: `passed` (int),
  `total` (int), `cases` (список case result), суммарное/среднее `time`,
  `memory`. Решение считается `OK`, когда `total > 0 and passed == total`;
  `NO TESTS` — когда тестов не найдено (`total == 0`).
- **Run result** — обёртка над набором решений с полями `kind`
  (`"file"|"dir"|"error"`), `mode` (`"tests"|"bench"`), `base` (база для
  относительных имён), `rows` (по решению), `message`/`message_id`/
  `message_params` (только при `kind="error"`, см. § Локализация
  сообщений (`message_id`) ниже). Это уже адаптерный слой; Web отдаёт его
  как `ResultViewModel` — см. [web-current.md](web-current.md#resultviewmodel).

### Опциональное поле `lint` (issue #346, #403) — реализовано

> **Статус (#403, замкнуто).** Поле `lint` продюсится: `core/lint.py`
> (`run_lint`) даёт нарушения стиля, которые `core/history_recording.py`
> (`lint_records_from_violations`) превращает в `LintRecord`, а
> `record_run(lint=...)` пишет в таблицу `lint_violations` (`core/history.py`) —
> из CLI (`cli/commands.py`, `--lint --history`, режимы 1/2) и из web-грейдинга
> (`web/viewmodels.py`). Категория «lint» в разделе «Подучить» **достижима**
> (`core/insights.py`). Ниже — формат поля.

Формат (при включённой PEP-проверке, extra `[lint]`, эпик #342):
результат решения может нести дополнительное поле `lint` — список нарушений
стиля от `core/lint.py`:

| Поле | Тип | Описание |
|---|---|---|
| `rule_code` | `str` | Код правила ruff/pycodestyle (`E501`, `F401`) — ключ карточки в `rules/` |
| `line_no` | `int` | 1-based номер строки (`0`, если ruff не сообщил) |
| `message` | `str` | Текст нарушения от ruff |
| `column` | `int` | 1-based колонка (`0`, если не сообщена) |

**Инвариант:** `lint` **не влияет** на `verdict`/`passed`/`OK` —
это информационный канал. Поле отсутствует, когда ruff недоступен
(`LintUnavailable`) или проверка стиля не запрашивалась; потребитель обязан
работать без него (обратная совместимость). Формат `Violation` и границы —
[rules-insights.md](rules-insights.md).

### Локализация сообщений (`message_id`) — issue #264

Ответы веб-API с человекочитаемым `message` (не только Run result — та же
пара полей стоит рядом с `message` в error-конвертах `/api/*`, включая обе
существующие формы — `{"kind": "error", ...}` и `{"ok": False, ...}`, см.
`web/server.py`) дополнены двумя полями:

| Поле | Тип | Описание |
|---|---|---|
| `message` | `str` | Человекочитаемый текст, отрендеренный сервером из каталога сообщений (см. ниже). Сохранён для обратной совместимости — потребители, не знающие про `message_id`, продолжают работать без изменений. |
| `message_id` | `str` | Машиночитаемый ключ каталога (`core/locales/<lang>.json`), например `"path_not_found"`. Позволяет клиенту локализовать/кастомизировать текст самостоятельно, не парся `message`. |
| `message_params` | `dict[str, Any]` | Значения, подставленные в шаблон `message_id` при рендере (например `{"path": "..."}`); пустой `dict`, если подстановок не было. |

**Локаль.** Выбирается query-параметром `?lang=` на GET/POST `/api/*`
эндпойнтах (`ru`/`en`; любое другое значение или отсутствие параметра —
`ru`, поведение по умолчанию не меняется). Рендерит и выбирает локаль
`stepik_grader.web.i18n` (`render_message()`/`message_fields()`) —
надстройка веб-слоя над `core.i18n.load_locale_messages()` (issue #144):
`core/i18n.py` остаётся leaf-модулем (только stdlib), сам каталог и
интерполяция `message_params` — забота `web/i18n.py`, не ядра. Guardrail
`scripts/check_locale_guardrails.py` (CI) следит, чтобы все `message_id`,
на которые ссылается `web/*.py`, существовали в `ru.json`, а `ru.json`/
`en.json` имели одинаковый набор ключей.

## Ожидания стабильности (для будущих потребителей)

Контракт задаёт правила эволюции, чтобы CLI/Web/API не расходились:

1. **Имена и семантика перечисленных полей стабильны.** Переименование или
   смена смысла `passed`/`verdict`/`error`/`timed_out`/`diff`/`time`/`memory` —
   ломающее изменение; допускается только вместе с миграцией всех потребителей
   (CLI, `web.py`-мэпперы) и записью в [CHANGELOG.md](../CHANGELOG.md).
2. **Расширение — аддитивно.** Новые поля добавляются как опциональные;
   потребитель обязан игнорировать незнакомые ключи (как `GraderConfig`
   игнорирует незнакомые ключи `pyproject.toml`).
3. **`verdict` — единственная точка ветвления UI.** Новый вердикт (напр.
   отдельный для перформанса или sandbox-нарушения будущего server mode)
   добавляется в перечисление, а не переопределяет существующие.
4. **Адаптеры, не ядро, знают про транспорт.** JSON-сериализация, HTTP-коды,
   версия API — забота адаптеров (`web.py`, будущий API — см.
   [server-mode.md § Контракт API удалённого исполнения](server-mode.md#контракт-api-удалённого-исполнения-issue-156)).
   Ядро отдаёт данные, а не транспорт.
5. **Версионирование API.** Когда появится сетевой API
   ([server-mode.md](server-mode.md)), он версионирует именно этот контракт
   (`/api/v1/...`); поля case/solution result — его семантическое ядро.

> **Типизированный `TestResult` реализован** (issue #112/#113):
> `stepik_grader.core.result.TestResult` — frozen dataclass с полями case
> result выше + `Verdict = Literal["AC", "WA", "TLE", "RE", "CANCELLED", "SANDBOX_VIOLATION"]`. Рядом
> живёт `CaseResult` (`TypedDict`, issue #442) — статический тип **того же
> словаря**: `run_single_test()` теперь аннотирован `-> CaseResult`, а
> `from_dict()` принимает любой `Mapping[str, Any]` (в т.ч. `CaseResult`).
> Runtime-форма при этом не менялась — обычный `dict` на границе CLI
> JSON-вывода, `run_tests()`/`run_benchmark()` и `/api/grade`. `TestResult`
> используется там, где нужна типобезопасность поверх словаря — сейчас:
> `core/reporter.print_case_verbose` (issue #114) конвертирует dict в
> `TestResult` на входе вместо чтения произвольных dict-ключей. Источник истины
> формы по-прежнему — этот документ + docstring `run_single_test`.
