# Прогонный корпус

Набор задач целиком — условие, эталонное решение, тест-кейсы — на котором
проверяется, что грейдер **выдаёт правильный вердикт**. Не путать с
микробенчмарком (`run_benchmark`, `core/microbench_runner.py`): там меряют
скорость, здесь — корректность вердикта.

Запуск и устройство стенда — [`docs/dev/corpus.md`](../docs/dev/corpus.md).
Короткая версия:

```bash
python scripts/corpus_run.py                 # весь корпус, exit 1 при расхождении
python scripts/corpus_run.py --task fizzbuzz # одна задача
python scripts/corpus_run.py --output json   # машиночитаемый отчёт
```

---

## Что здесь лежит

```
corpus/
├── README.md
└── tasks/
    └── <slug>/
        ├── task_1.py      # эталонное решение (обязано давать AC)
        ├── meta.json      # тема, условие, теги глоссария, происхождение
        └── tests/
            ├── input_1.txt / expected_1.txt
            └── input_2.txt / expected_2.txt
```

Формат тест-кейсов — «Named» (формат 2), канон описан в
[docs/use/configuration.md](../docs/use/configuration.md#формат-тест-кейсов).
Директория без `task_1.py` или без `tests/` молча пропускается — служебные
папки рядом с задачами стенду не мешают.

---

## Правило о содержимом: только свои условия

**В `corpus/tasks/` кладутся задачи с собственными условиями.** Не копировать
сюда условия задач со Stepik, из учебников и из чужих задачников: репозиторий
публичный и лежит под MIT, а чужой текст этой лицензией накрыть нельзя.
Поле `source` в `meta.json` фиксирует происхождение задачи — заполнять честно.

Скачанные задачи Stepik — материал **локальный**: держать их в `corpus/local/`
(в `.gitignore`, как и `StepikTasks/`) и гонять стенд с `--corpus`:

```bash
python scripts/corpus_run.py --corpus corpus/local
```

Наружу из такого прогона едут только **производные данные** — какой вердикт
разошёлся с ожиданием и на какой мутации, — но не тексты условий.

---

## Как добавить задачу

1. Создать `corpus/tasks/<slug>/` с `task_1.py`, `tests/` и `meta.json`.
2. Убедиться, что эталон проходит: `python scripts/corpus_run.py --task <slug>`
   — строка `baseline` обязана быть `AC`. Если нет, дефект в задаче, а не в ядре.
3. Выбирать задачи так, чтобы они **расширяли покрытие мутаций**, а не
   повторяли уже покрытое. Мутации применяются не ко всякой задаче: регистр
   вывода нечего портить в числовом ответе, а шум в младших разрядах — в целом.
   Полезные пробелы: вывод с плавающей точкой, текстовый вывод, многострочный
   вывод, многострочный ввод, пустой вывод при некоторых входах.

Мутации живут в [`scripts/corpus_mutations.py`](../scripts/corpus_mutations.py)
— каждая с ожидаемым вердиктом и пояснением, что именно она проверяет в ядре.
