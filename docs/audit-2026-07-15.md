## 0. Исполнительное резюме

Проект — в **отличной инженерной форме** и это подтверждается кодом, а не только
доками. Дисциплина процессов (Conventional Commits, CHANGELOG в каждом PR,
CI-матрица на 3 ОС, guardrail-скрипты документации/локалей/версий, динамическая
версия из git-тегов) — на уровне зрелых open-source библиотек. Архитектурный DAG
без циклов подтверждён AST-обходом 74 файлов, God-object'ов нет, тесты
содержательные (**1442 собранных**, ~1420 passed / 22 skipped за ~82 c,
покрытие 87.5 % single-OS / 92.9 % combined). Три из четырёх «двойников» прошлого
аудита (v1.7.0) реально консолидированы; десять пунктов документационного долга
того же аудита закрыты (#353).

**Общая оценка: 8.1 / 10** (внешний шаблон ставил 8.5 — мы понижаем на честном
факт-чекинге: один **критический краш первого запуска**, разорванная петля
удержания и ряд подтверждённых репро-багов исполнителя и web-слоя, которые шаблон
не увидел, потому что смотрел на документацию, а не на поведение).

### E1 · [Epic] Надёжность исполнения решений: runner, executor, sandbox

**Цель эпика.** Устранить зависания, процессы-сироты, deadlock'и и пробелы sandbox-покрытия в пути исполнения кода студента. Runner остаётся единственным choke point'ом исполнения, а его гарантии (timeout, cancel, изоляция) — честными и проверяемыми в CI.


#### A01. `fix(sandbox): --sandbox --mode 4 исполняет stdin-блоки мимо песочницы — провести run_microbench через Runner или честно отказывать`
- **Приоритет:** 🔴 high  |  **Роли:** 🏛️
- **Зачем:** Под явным флагом безопасности часть кода решения исполняется неизолированным subprocess'ом python -c (microbench_runner.py:210-214), при этом help --sandbox обещает покрытие режимов 1/2/3/4. Тот же класс проблемы, что закрытый #351: тихое ослабление явно запрошенной гарантии.
- **Критерии приёмки:**
  - [ ] Либо run_microbench исполняет bench-скрипт через активный _RUNNER, либо --sandbox --mode 4 завершается parser.error с понятным сообщением
  - [ ] SECURITY.md § «Именованные пробелы» описывает принятое решение
  - [ ] Тест: под set_runner(fake) режим 4 не запускает неподменённый subprocess (или CLI отказывает)
  - [ ] Help-текст --sandbox в cli/options.py соответствует фактическому покрытию

#### A02. `fix(runner): убивать группу процессов решения при TLE/cancel и ограничивать communicate() после kill`
- **Приоритет:** 🔴 high  |  **Роли:** 🐍 🧪
- **Зачем:** Подтверждённый репро у двух ролей независимо: LocalRunner.run при таймауте убивает только прямого ребёнка. Внук, унаследовавший stdout/stderr, держит pipe и блокирует communicate() без таймаута (зависание 8.1 с при timeout=2.0), демонизированный внук вешает грейдер/синхронный web-эндпоинт навсегда; решения с multiprocessing/subprocess оставляют пожирающих CPU сирот после каждого прогона (batch-режим 2 умножает утечку). Sandbox сдерживает, но он opt-in и не проброшен в web.
- **Критерии приёмки:**
  - [ ] Popen в LocalRunner с start_new_session=True (POSIX); при TLE/cancel убивается группа через os.killpg
  - [ ] communicate() после kill вызывается с ограниченным timeout и не блокируется дольше ~5 с
  - [ ] Регрессионный тест: решение спавнит внука со sleep — LocalRunner возвращает timed_out за время ~timeout, после run() всё дерево процессов мертво
  - [ ] Поведение _posix_common.run_argv_with_limits проверено на тот же сценарий (join reader'ов bounded)
  - [ ] На Windows поведение не деградирует: taskkill /T, Job Object по прецеденту core/sandbox/_windows.py или документированный fallback
  - [ ] Поведение AC/RE/WA-путей не изменилось (существующие тесты зелёные)

#### A03. `fix(runner): устранить deadlock блокирующей записи stdin в _run_with_polling`
- **Приоритет:** 🔴 high  |  **Роли:** 🧪
- **Зачем:** Подтверждённый репро: stdin больше pipe-буфера + решение, не читающее ввод, блокируют воркер навсегда — timeout и cancel_event не срабатывают, воркеры ThreadPoolExecutor утекают, async-подсистема web умирает до рестарта. communicate()-путь CLI не затронут — фиксить только polling-ветку (запись stdin в отдельном потоке, как делает сам communicate()).
- **Критерии приёмки:**
  - [ ] Тест: RunSpec(stdin=1 MiB, решение while True без чтения stdin, timeout=2, cancel_event задан) возвращается за <5 с с timed_out=True
  - [ ] Парный тест: тот же сценарий, cancel_event.set() через 0.5 с → cancelled=True
  - [ ] После возврата дочерний процесс мёртв (poll() is not None)
  - [ ] Существующие тесты test_runner.py/test_runs.py зелёные без правок

#### A04. `ci(sandbox): установить bubblewrap в ubuntu-job и добавить guard от молчаливого skip нативных sandbox-тестов`
- **Приоритет:** 🔴 high  |  **Роли:** 🧪
- **Зачем:** Все функциональные тесты linux-бэкенда скипаются и локально, и в CI (bwrap нет в образе ubuntu-24.04, workflow его не ставит): _linux.py — 0% даже в combined coverage, изоляция ФС/сети/fork-bomb на Linux не проверяется нигде автоматически, combined-гейт 90% это не ловит.
- **Критерии приёмки:**
  - [ ] apt-get install -y bubblewrap в ubuntu-джобах матрицы test
  - [ ] TestLinuxSandboxRunner реально выполняется в CI (0 skipped в linux-классе на ubuntu-job)
  - [ ] Guard: job падает, если на нативной ОС sandbox-тесты этой ОС скипнулись
  - [ ] _linux.py > 0% в combined coverage

#### A05. `refactor(core): вывести из эксплуатации legacy core/executor.py или починить его контракт (main-guard, timeout, stdin)`
- **Приоритет:** 🟡 medium  |  **Роли:** 🏛️ 🐍 🔧
- **Зачем:** 183-строчная параллельная система запуска со своей политикой таймаута (SIGALRM + EXECUTOR_TIMEOUT) не вызывается грейдером и жива только ради tests/test_executor.py и реэкспорта RunResult — единственный из четырёх «двойников» аудита v1.7.0, не консолидированный к v1.8.0. При этом её контракт сломан: if __name__ == "__main__": молча пропускается (__name__ резолвится в "builtins"), run_solution(timeout=...) не влияет на SIGALRM ребёнка, параметр stdin молча игнорируется (executor.py:128) — собственные тесты его передают, и он не доходит, — поле RunResult.extra мёртвое.
