## 0. Методика и фактическая база

Аудит выполнен **мультиагентно по реальному коду**: 8 независимых агентов-ролей прочитали
`src/stepik_grader/**` (≈14.8k строк), тесты (81 файл, ≈18.4k строк), `docs/` (23 файла),
CI и `web/static/`. Ключевые находки **перепроверены вручную по `file:line`** (11 адверсариальных
проверок, ниже помечены ✅ verified). Квалити-гейты прогнаны на чистом окружении под Python 3.13:

| Гейт | Результат |
|---|---|
| `pytest tests/` | **1420 passed, 22 skipped**, 9 warnings, ~81 с |
| Покрытие (single-OS) | **87.55 %** (порог `fail_under=85`) |
| `ruff check .` / `ruff format --check .` | 0 ошибок / 163 файла |
| `mypy src/stepik_grader --ignore-missing-imports` | 0 ошибок (72 файла) |
| Инварианты стиля (греп) | 0 `Optional/List/Dict/Union`, 0 голых `except:`, 0 файлов без `from __future__`, 0 модулей без `__all__` |
| Git-гигиена | секретов в трекинге нет, только `*.example`, `.gitignore` полный |

> ⚠️ **Замечание об окружении:** контейнер по умолчанию несёт Python **3.11**, а проект требует
> 3.12+ (PEP 695: `class MtimeCache[T]`). Под 3.11 `mypy` даёт ложную «синтаксическую ошибку»,
> а `pytest` не собирается. Все гейты выше прогнаны под явным **3.13** — это и есть истинная картина.

### Сводный вердикт

Проект в **отличной инженерной форме**. Базовая дисциплина — эталонная: инварианты стиля
соблюдены на 100 %, гейты зелёные, процессы (Conventional Commits, CHANGELOG в каждом PR,
CI-матрица на 3 ОС, guardrail-скрипты, динамическая версия) на уровне зрелых OSS-библиотек.
**Три из четырёх «двойников» прошлого аудита реально закрыты** (единый i18n-каталог #355,
единый URL-резолвер `card_url()` #356, мост глоссариев `core/error_glossary.py`).

Но зелёные гейты ≠ отсутствие дефектов. Аудит вскрыл **системные темы**, невидимые для
line-coverage и линтеров:

1. **Обучающий контур эпика #342 замкнут наполовину.** История прогонов пишется **только из
   CLI**; веб-грейдинг не пишет ни одной записи → раздел «Подучить» у веб-аудитории (той, ради
   которой делали браузерную оболочку) **всегда пуст**. Плюс `lint`-половина недостижима
   (`LintRecord` нигде не конструируется, `#346`).
2. **`history.py` под конкуренцией теряет данные и течёт ресурсами** — воспроизведённый P1-баг
   гонки миграции + утечка `sqlite3.Connection`. Оба объясняют `ResourceWarning`, который
   «размывает» зелёные гейты.
3. **Web-слой — концентратор риска:** исполняет чужой код без OS-изоляции (`--sandbox` не
   проброшен), диффузная граница с `core/` (дублирование доменной логики), три отдельных
   security-бреши на стыках (CSRF, права токенов, конфайнмент `/api/download`).
4. **Дрейф числовых снапшотов** — метрики «1317/93 %» в трёх канонических файлах устарели
   (реально 1364+ теста / 87.55 %), разнобой числа карточек глоссария (581/787/832/1388).

Ни одного дефекта, роняющего грейдинг «в лоб», нет — риски **тихие** (потеря данных, ложный
вердикт, утечка), и именно поэтому они опаснее видимых.

## 2. Сквозные темы

1. **«Реализовано, но не подключено».** history (только CLI, PR1) · lint (`LintRecord` не пишется, PR3) ·
   `--sandbox` (не в web, S1) · `TestResult` (обойдён, A4) · `executor.py` (мёртв, A2). Паттерн: слой
   написан и покрыт тестами, но реальный путь исполнения его не использует. Line-coverage это скрывает.
2. **Web-слой — концентратор долга и риска.** Диффузная граница (A1), дублирование (A1+бонус),
   3 security-бреши (S2–S4), исполнение без изоляции (S1), перф на горячем пути (E1–E2, E5),
   монолит фронтенда (U2), непокрытая конкурентность (T1, T3). Сервисный слой в `core/` (issue #E5 ниже)
   — корневое лекарство сразу для нескольких.
3. **Тихие потери данных под конкуренцией.** history-гонка (T1) + утечка (B1) + неатомарные записи (B4)
   + перескачивание тестов (B2). Все проходят мимо зелёных гейтов, все — best-effort-`except` их маскирует.
4. **Числовой дрейф доков** (D1, D2) — мягкий CI-guard не ловит.

#### I1 — fix(history): устойчивость соединения и миграции SQLite под конкуренцией `[P1]`

**Цель.** Устранить два дефекта жизненного цикла соединения в `core/history.py`, из-за которых
`--history` под конкуренцией **тихо теряет прогоны** и **течёт ресурсами**.

**Доказательство (✅ verified).**
- Гонка миграции (воспроизведено): свежая БД, `threading.Barrier` на 12 потоков → все читают
  `user_version=0` до первого commit → все зовут `executescript(_SCHEMA_V1)` → один выигрывает,
  остальные падают `OperationalError: table runs already exists`, что best-effort `except
  (sqlite3.Error, OSError)` в `record_run` глотает → `return None`. **40 трайлов × 12 → 440
  потерянных записей, выживает ровно 1 из 12.** Это ровно сценарий «первый запуск CLI+web
  одновременно», ради которого выбран WAL. (`history.py:116-129`)
- Утечка: `_connect` создаёт `conn = sqlite3.connect(...)`, затем `PRAGMA journal_mode=WAL` /
  `_migrate` — и лишь потом `return`; при сбое любого шага (битая БД, `database is locked`)
  соединение создано, но `closing` над ним ещё не построен → не закрывается до GC →
  `ResourceWarning: unclosed database`. (`history.py:139-143`)

**Что сделать.**
- В `_connect`: `try: <pragma/migrate> except BaseException: conn.close(); raise`.
- Сериализовать миграцию: `BEGIN IMMEDIATE` перед проверкой версии, `CREATE TABLE IF NOT EXISTS`,
  либо retry на `table already exists`; задать явный `sqlite3.connect(..., timeout=...)`.

**Acceptance criteria.**
- [ ] Concurrency-тест: свежая БД, N потоков через `Barrier` **без прогрева**, assert `persisted == N`.
- [ ] `pytest` не печатает `ResourceWarning` (проверить `-W error::ResourceWarning` на `test_history`).
- [ ] `test_corrupt_db_is_graceful` не оставляет незакрытых соединений.

**Links.** Аудит B1, T1. Область #130/#344.

   фундамент #342, из-за неё же шумит `ResourceWarning`. Дёшево, изолированно, высокая ценность.
2. **I3 + I4 (web пишет историю + sandbox)** — «Подучить» в web пуст и web исполняет чужой код без
   изоляции. Вместе замыкают главную ценность спринта #342 и закрывают самую заметную брешь.
3. **I5 (сервисный слой core)** — корневое лекарство от диффузной границы web↔core, дублирования,
   расхождения контракта и части перф-проблем; разблокирует будущий remote-execution API.
