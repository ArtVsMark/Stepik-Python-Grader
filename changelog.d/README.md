# Фрагменты CHANGELOG

Каждый PR кладёт сюда **свой файл** вместо строки в общий `CHANGELOG.md`. Два
файла с разными именами не конфликтуют никогда — поэтому очередь мержа
перестаёт зависеть от порядка, а PR не становится `dirty` от того, что соседний
успел смержиться первым.

## Как добавить запись

```
changelog.d/<slug>.<секция>.md
```

- `slug` — что угодно уникальное, обычно имя ветки без префикса
  (`preflight-stamp`, `find-solutions-fallback`);
- секция — одна из `added`, `changed`, `fixed`, `removed`, `internal`;
- внутри — **одна строка** текста записи: без ведущего `-` и без имени секции,
  их подставит сборка. Номер PR указывается в тексте как раньше — `(#1234)`.

Пример — файл `preflight-stamp.fixed.md`:

```
pre-push гейт больше не отклоняет пуш только что проверенного состояния — штамп привязан к содержимому рабочего дерева, а не к SHA коммита (#1115)
```

## Что с этим делает проект

```bash
python scripts/collect_changelog.py --check     # валидация (в CI и в preflight)
python scripts/collect_changelog.py --preview   # как соберётся, ничего не меняя
python scripts/collect_changelog.py --collect   # перенести в ## [Unreleased] и удалить файлы
```

Релизная процедура не меняется: `--collect` кладёт записи в `[Unreleased]`,
который при релизе переименовывается в `[X.Y.0] - ДАТА`.

## Язык записи: русский, но перевод — забота мержащего

Запись уезжает в `CHANGELOG.md` и оттуда в GitHub Release и на PyPI, поэтому
пишется по-русски. От внешнего участника русский при этом **не требуется**:
англоязычная заготовка принимается как есть, а переводит её тот, кто мержит —
отдельным коммитом в ветку PR перед мержем либо переписывая фрагмент целиком
(`CONTRIBUTING.md` § Английский вклад).

Пропуск перевода ловит `python scripts/check_changelog_translated.py`: запись,
в которой вне кода нет ни одной кириллической буквы, помечается как
непереведённая. Запись из одних идентификаторов (флаги, имена файлов, ключи
локали) проходит молча — после вырезания кода в ней не остаётся текста, а
значит, и переводить нечего.

Строгость разная по месту, и это не непоследовательность: на PR —
предупреждение, потому что запись в ветке может быть черновиком, а на релизе —
отказ, потому что версия в PyPI неперезаписываема и замеченное после публикации
правится только следующим релизом.

## Почему не строка в общем файле

Так было раньше, и это стоило конфликта на каждый параллельный PR. Отдельный
раздел `## Буфер` в `CHANGELOG.md` проблему смягчал, но не убирал: драйвер
`merge=union` из `.gitattributes` работает **только локально** — `git merge`
сливает буфер без вмешательства ровно тогда, когда GitHub уже показывает
`mergeable_state=dirty`. А конфликтный PR остаётся вовсе без проверок: прогон
идёт по merge-коммиту, которого при конфликте не существует, и пустой список
проверок читается как «CI сломался».

Записи, уже лежащие в `## Буфер`, никуда не переносятся — они разберутся при
ближайшем релизе вместе с остальными.
