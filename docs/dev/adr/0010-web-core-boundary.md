# ADR-0010 — Граница web↔core: адаптеры как сервисный слой, фасад `web/grading`

- **Статус:** Accepted (реализовано: фасад `web/grading.py` + активный boundary-guard тест #549/#550)
- **Дата:** 2026-07-19
- **Связанные issue:** #529 (эпик E5), #548 (этот ADR), #549 (фасад `web/grading`
  + boundary-guard в `test_import_dag`), #550 (capability на Runner Protocol);
  развязывает #151 (server mode)
- **Связанный дизайн:** [../architecture.md](../architecture.md) (DAG/слои),
  [../design/server-mode.md](../design/server-mode.md), [../api.md](../api.md)
- **Опирается на:** [ADR-0001](0001-server-mode.md) (направление на server mode),
  [ADR-0006](0006-runner-abstraction.md) (Runner-абстракция)

## Контекст

web-слой берёт core-внутренности напрямую, без структурного правила:

- `web/viewmodels.py` импортирует ~10 core-модулей (`grader_core`,
  `test_loader`, `microbench_runner`, `history`/`history_recording`, `lint`,
  `cache`, `reporter`, `error_glossary`, `mtime_cache`, `glossary.*`);
- `web/runs.py` оборачивает `viewmodels` в async-job + `core.tracer`;
- `web/playground.py:66` обращается к **приватному** синглтону
  `grader_core._RUNNER` — единственный доступ web к приватному core-имени.

grade/bench/microbench-логика живёт прямо в `web/viewmodels.py`
(`grade_path`/`grade_benchmark`/`grade_microbench` — три точки входа), отдельного
web-фасада нет. Ничто структурно не мешает web дотянуться до приватных
`_`-хелперов core; при server mode (#151) такие прямые импорты станут
связностью, мешающей перемаршрутизации исполнения на удалённый backend.

Параллельно в аудите 2026-07-18 фигурировала премиса «общего `ContentProvider`
нет, надо его ввести». Премиса **фактически неверна**: `glossary/json_provider.py:49`
(`GlossaryProvider`) и `rules/json_provider.py:41` (`RulesProvider`) — это уже два
`@runtime_checkable` Protocol с `get()`/`search()`.

Нужно зафиксировать три развилки: (1) что является сервисным слоем, (2) вводить
ли общий `ContentProvider`, (3) как оформить вход web в грейдинг.

## Решение

1. **Адаптеры (`web/*_adapter.py`) — и есть сервисный слой.** Шесть адаптеров
   (`glossary`/`rules`/`insights`/`downloader`/`reference`/`auth`) уже играют роль
   тонкого сервисного слоя над core (пас-through + web-специфика: без
   интерактивного `input()`, неблокирующая аутентификация). Отдельный тяжёлый
   Service-слой (ещё один уровень объектов между web и core) **не вводим** — он
   дублировал бы адаптеры без новой ответственности.
2. **Общий `ContentProvider` Protocol НЕ вводим (правило трёх).**
   `GlossaryProvider` и `RulesProvider` остаются двумя раздельными
   `runtime_checkable`-протоколами. Объединять в общий `ContentProvider` — только
   при появлении ТРЕТЬЕГО типа контента, и тогда через generic-композицию, а не
   задним числом ради двух.
3. **Ввести web-фасад `web/grading`** (реализация — #549) как единственную точку
   входа web в grade/bench/microbench. `viewmodels.py` становится чистым
   JSON-маппером над фасадом; `runs.py`/`playground.py` ходят в грейдинг через
   фасад, а приватный `grader_core._RUNNER` уходит за публичную поверхность core.
4. **Структурный boundary-guard в `test_import_dag`** (реализация — #549):
   allowlist-проверка, что web импортирует только ПУБЛИЧНУЮ поверхность core (имена
   без ведущего `_`). Новый приватный импорт из web краснит тест.

## Альтернативы

- **A. Отдельный тяжёлый Service-слой** (объекты-сервисы между web и core). Минус:
  дублирует уже сложившиеся адаптеры, добавляет уровень без новой ответственности —
  оверинжиниринг для локального инструмента. Отклонено.
- **B. Ввести общий `ContentProvider` Protocol сейчас.** Минус: премиса ложна (два
  Protocol уже есть); объединение двух реализаций нарушает правило трёх/YAGNI,
  усложняет типы ради гипотетического третьего провайдера. Отклонено.
- **C. Статус-кво** (прямые импорты, grade-логика в `viewmodels`, приватный
  `_RUNNER` из web). Минус: нет структурной границы; server mode упрётся в
  связность. Отклонено.
- **D. Адаптеры-как-сервис + фасад `web/grading` + boundary-guard (выбрано).**
  Минимальный шаг: формализует уже существующий сервисный слой, сводит грейдинг в
  одну поверхность, охраняет границу тестом — без нового тяжёлого слоя и без
  преждевременного `ContentProvider`.

## Последствия

**Положительные:**

- Явная, тестируемая граница web↔core; server mode (#151) сможет
  перемаршрутизировать исполнение через фасад, не трогая web-вью.
- `viewmodels.py` худеет до JSON-маппинга; приватный `grader_core._RUNNER`
  уходит с web-стороны за публичный фасад.
- Правило трёх зафиксировано документально — будущие «а давайте общий Provider»
  отсылаются к этому ADR.

**Отрицательные / издержки:**

- Ещё один модуль (`web/grading`) — небольшой оверхед; митигируется тем, что он
  лишь собирает уже существующие вызовы в одну поверхность (не новая логика).

**Нейтральные:**

- Адаптеры остаются как есть — ADR называет их сервисным слоем, а не меняет.
- Реализация фасада и guard'а — issue #549; этот ADR фиксирует только решение.
