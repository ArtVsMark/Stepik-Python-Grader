# Производительность: базовые замеры

Грейдер умеет бенчмаркать чужой код, а собственная стоимость до сих пор не
измерялась ни разу — заметить регресс холодного старта или загрузки глоссария
было нечем. Здесь зафиксированы базовые цифры и способ их повторить.

Документ отвечает на один вопрос: **сколько стоит сам инструмент**. Оптимизаций
он не предписывает — сперва измерение, потом решения.

## Как повторить

```bash
python scripts/perf_baseline.py                 # полный отчёт
python scripts/perf_baseline.py --quick         # без долгих сценариев
python scripts/perf_baseline.py --output json   # машиночитаемо
python scripts/perf_baseline.py --cases 500     # своё число кейсов
```

Каждый сценарий повторяется несколько раз, в отчёт идёт **медиана**: одиночное
измерение на рабочей машине шумит на десятки процентов (антивирус, планировщик,
турбо-буст). Абсолютные числа привязаны к железу — сравнивать имеет смысл
прогоны на одной и той же машине, а не с таблицей ниже.

## Снимок

Условия: Windows 11, Python 3.14.4, AMD64 (Family 26), 200 тест-кейсов,
5 повторов на сценарий. Снято 2026-08-03.

| Сценарий | Медиана | Что это значит |
|---|---|---|
| Холодный старт CLI (`--version`) | 0.41 с | Столько ждёт пользователь при каждом запуске |
| Импорт пакета (`import stepik_grader`) | 0.08 с | Сам пакет лёгкий |
| Импорт CLI-слоя (`import stepik_grader.cli`) | 0.37 с | **Почти весь старт — здесь** |
| Загрузка карточек глоссария | 0.22 с | Включая ~0.08 с старта процесса |
| Загрузка stdlib-инвентаря | 0.21 с | Панель «Функции в коде» |
| Загрузка карточек правил (PEP) | 0.13 с | Раздел «Правила», блок «Стиль» |
| Проверка решения на 200 кейсах | 16.6 с | **83 мс на кейс** |
| 4 параллельных прогона по 200 кейсов (job-пул) | 76 с | Пул на 2 воркера |

## Что из этого следует

**Старт CLI — это импорт фасада, а не пакета.** Голый `import stepik_grader`
стоит 0.08 с, а `import stepik_grader.cli` — 0.37 с, то есть в 4,5 раза дороже:
фасад тянет core-модули, локали и argparse. Если холодный старт когда-нибудь
станет проблемой, оптимизировать нужно именно ленивость импортов в `cli/`, а не
пакет вообще.

**Цена кейса — это цена процесса.** 83 мс на тест-кейс при решении из одной
строки: собственно исполнение здесь пренебрежимо, всё уходит на запуск
интерпретатора. Отсюда практический вывод для пользователя: время проверки
линейно числу кейсов, и папка на 500 кейсов займёт минуту независимо от того,
насколько быстрое решение.

**Параллелизм на job-пуле выигрыша не даёт.** Четыре прогона по 200 кейсов
последовательно стоили бы ≈66 с (4 × 16.6), а через пул на двух воркерах вышло
76 с — то есть медленнее. Нагрузка упирается не в ожидание, а в CPU и запуск
процессов, и два воркера конкурируют за те же ресурсы. Это не дефект: пул
существует ради отзывчивости UI и возможности отменить прогон, а
не ради ускорения. Наращивать `job_workers` в расчёте на скорость бессмысленно.

## Чего здесь нет

Замеры сняты на одной машине и одной ОС — это отправная точка, а не эталон для
CI-гейта. Порога «не медленнее N» нет намеренно: на разделяемых раннерах разброс
таких измерений сопоставим с величиной регресса, который они должны ловить, и
гейт стал бы источником ложных падений. Когда понадобится следить за динамикой,
правильнее прогонять скрипт на фиксированном железе и сравнивать с прошлым
снимком.
