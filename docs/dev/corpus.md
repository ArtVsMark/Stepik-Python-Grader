# Прогонный корпус: сверка вердиктов

> Канонический документ по стенду `scripts/corpus_run.py` и каталогу мутаций
> `scripts/corpus_mutations.py`. Сам корпус задач и правила пополнения —
> [`corpus/README.md`](../../corpus/README.md).

Стенд отвечает на один вопрос: **выдаёт ли ядро тот вердикт, который обязано
выдать?** Для каждой задачи прогоняются эталонное решение (ожидание — `AC`) и
каждая применимая мутация — детерминированная порча эталона с заранее
известным вердиктом. Расхождение факта с ожиданием — дефект с готовым репро:
известны задача, мутация и обе стороны сравнения.

---

## Зачем он, если есть тесты

`tests/` проверяют функции ядра поодиночке и на синтетике. Корпус гоняет
**полный путь** «файл решения → subprocess → сравнение вывода → вердикт» на
задачах целиком, и ловит то, что на уровне юнитов невидимо:

- **Ложный AC** — грейдер принял неверное решение. Худший дефект учебного
  инструмента: студент считает задачу сданной, Stepik её не принимает, доверия
  к грейдеру больше нет. Такое уже случалось: разбор строк через `splitlines()`
  считал переводом строки ещё восемь управляющих символов, и вывод `a<VT>b`
  признавался равным ожиданию из двух строк. Регрессия на этот дефект держится
  мутацией `vertical_tab`.
- **Ложный WA** — грейдер завернул верное решение. Студент правит рабочий код и
  теряет время. Мутации `float_noise` и `crlf_newlines` держат эту сторону.

С микробенчмарком (`run_benchmark`, `core/microbench_runner.py`) стенд не
пересекается: там меряют скорость, здесь — корректность вердикта.

## Запуск

```bash
python scripts/corpus_run.py                          # весь корпус, exit 1 при расхождении
python scripts/corpus_run.py --task fizzbuzz          # одна задача
python scripts/corpus_run.py --mutation trailing_space --mutation upper_case
python scripts/corpus_run.py --output json            # машиночитаемый отчёт
python scripts/corpus_run.py --report                 # отчёт без падения (exit 0)
python scripts/corpus_run.py --corpus corpus/local    # локальные задачи вне репозитория
```

Таймаут кейса по умолчанию — 2 с (`--timeout`), а не рабочие 10 с из
`GraderConfig`: мутация `timeout` намеренно виснет на каждом кейсе, и дефолт
растянул бы прогон впятеро без единого дополнительного сигнала.

## Каталог мутаций

Мутация — чистая функция от исходника эталона плюс ожидаемый вердикт. Почему
детерминированная порча, а не решения от LLM: корпус должен быть
**воспроизводим**. У сгенерированного решения ошибка сегодня одна, завтра
другая, и упавший прогон нечем объяснить; мутация же на том же входе даёт тот
же вердикт на любой машине и в CI.

| Ключ | Ожидание | Что проверяет в ядре |
|---|---|---|
| `timeout` | `TLE` | срабатывание таймаута и снятие зависшего процесса |
| `runtime_error` | `RE` | перехват ненулевого кода возврата и трейсбека |
| `syntax_error` | `RE` | некомпилируемое решение не выдаётся за верное |
| `no_output` | `WA` | пустой вывод против непустого ожидания |
| `extra_line` | `WA` | лишняя строка не съедается сравнением |
| `dropped_last_line` | `WA` | недобор строк (обрыв цикла вывода) |
| `blank_line_append` | `WA` | хвостовая пустая строка значима |
| `trailing_space` | `WA` | хвостовые пробелы значимы |
| `upper_case` | `WA` | регистр значим |
| `vertical_tab` | `WA` | VT — данные внутри строки, а не разделитель |
| `float_noise` | `AC` | фолбэк `normalize_floats` действительно работает |
| `crlf_newlines` | `AC` | CRLF-поток разбирается как LF |

Ожидания опираются на реальную политику сравнения — построчное равенство с
фолбэком на `normalizers.normalize_floats` при совпадении числа строк
(`core/grader_core.py`). Меняется политика — меняется каталог, и это осознанный
шаг, а не правка «чтобы позеленело».

**Применимость.** Не всякая мутация осмысленна для всякой задачи: перевод в
верхний регистр ничего не испортит в числовом ответе. У мутации есть предикат
по ожидаемым строкам эталона, и неприменимые пропускаются — вместо того чтобы
записать заведомо ложное ожидание.

### Второе семейство: ошибка в алгоритме

Все мутации выше — механическая порча **вывода**. Она предсказуема, но студент
так не ошибается: настоящие ошибки живут в самом решении. Второе семейство
(`family="algorithmic"`) правит код, а не вывод:

| Ключ | Ожидание | Что портит |
|---|---|---|
| `off_by_one_range` | `WA` / `RE` | `range(n)` → `range(n - 1)` |
| `int_division_swap` | `WA` / `RE` | `//` → `/` (`3` печатается как `3.0`) |
| `boundary_flip` | `WA` / `RE` | `<` ↔ `<=`, `>` ↔ `>=` |
| `reversed_order` | `WA` | `sorted(x)` → `sorted(x, reverse=True)` |
| `accumulator_reset` | `WA` / `RE` | инициализация накопителя переезжает внутрь цикла |

Это материал для «Подучить» и проверка **диагностики**, а не только вердикта: на
off-by-one грейдер обязан показать понятный diff, а не просто `WA`.

Правится AST, а не текст: замена по регулярному выражению испортила бы первое же
совпадение внутри строкового литерала (`"путь//к//файлу"`), а разобранное дерево
либо меняется корректно, либо не меняется вовсе. Из той же трансформации
получается и предикат применимости — «применимо» здесь буквально значит «в этом
исходнике есть что менять», поэтому мутация-пустышка невозможна.

Платить за это семейство приходится двумя послаблениями:

- **Вердикт не один.** Сужение диапазона обычно даёт `WA`, но там, где по нему
  идёт индексация, — `RE`. Проверяется «ядро не выдало `AC` на сломанном
  решении», конкретный вердикт зависит от задачи.
- **Мутация может не проявиться.** Сдвиг `>=` → `>` ничего не изменит, если на
  тестовых данных граница не достигается. Такой исход помечается в отчёте `~`
  («не проявилась на данных этой задачи»), считается отдельной строкой сводки и
  прогон не роняет — но и за проверку не выдаётся: покрытия там нет.

Послабление про нейтральность **не распространяется** на семейство `output`:
`AC` на порче вывода — это ложный `AC` ядра, худший из дефектов, и он остаётся
расхождением.

Чего в каталоге намеренно нет — необработанного крайнего случая (пустой ввод,
один элемент, все элементы равны). Это мутация **данных**, а не решения: её
место в наборе тест-кейсов задачи, а не в трансформации исходника.

**Ожидание — гипотеза, пока не проверено снаружи.** Каталог сверяет наш грейдер
с нашими же представлениями: если мы неверно решили, каким должен быть вердикт,
тест этого не поймает — он написан из того же заблуждения. Внешнюю валидацию
даёт только вердикт самой платформы.

**Откуда берутся расхождения с платформой.** Не из батч-отправки мутантов (её
нет и не будет, см. § Границы стенда), а из обычной работы человека с
грейдером. Каждая отправка решения пишет вердикт Stepik в локальную историю
рядом с нашим — таблица `stepik_submissions`, схема v4, issue #1175; сбор лежит
на пути отправки **в ядре** (`core/submission.submit_and_record`), поэтому его
получает и веб, и любой будущий потребитель, а не только стенд. Флаг
расхождения считается в момент записи: «наш AC / платформа `wrong`» и обратное.

Это меняет природу сверки. Разовая акция «прогнали корпус — сравнили таблицы»
превращается в непрерывный сбор: расхождение фиксируется тогда, когда
случилось, и накапливается между прогонами. Именно накопленный диф, а не память
о том, что чинили, отличает повторный прогон от первого. Состав записи и
причины решений — [rules-insights.md § История прогонов](rules-insights.md).
Запись идёт только при включённой истории (`--history`, ADR-0002).

**Фильтр вывода.** Мутации, портящие вывод, подменяют `sys.stdout` на буфер и
преобразуют текст целиком на выходе процесса: `print("a", "b")` дробится на
четыре `write`, и трансформация каждого куска порознь дала бы непредсказуемый
результат. Пишется результат в `sys.stdout.buffer` готовыми UTF-8 байтами —
текстовый `sys.stdout` на Windows транслирует `\n` в `\r\n`, и мутации про
переводы строк там проверяли бы не то, что задумано.

## Как читать расхождение

Порядок разбора — **сначала подозревай мутацию, потом ядро**. Ожидание в
каталоге написано человеком и может быть неверным для конкретной задачи; ядро
покрыто тестами.

1. Воспроизвести точечно: `--task <slug> --mutation <key>`.
2. Посмотреть, какие байты реально выдаёт мутант, и сверить с ожиданием кейса.
3. Если мутация испортила вывод не так, как заявлено, — дефект в каталоге.
4. Если испортила ровно как заявлено, а вердикт другой — дефект в ядре: заводить
   issue с этим репро.

Первый прогон корпуса дал ровно случай (3). На задаче со средней температурой
`float_noise` ожидал `AC`, а получил `WA`: кейс `-5.0 / 5.0` даёт среднее `0.0`,
и абсолютная прибавка `1e-13` превращала ноль в `1e-13` — не «шум в младших
разрядах», а другое число, к тому же в научной нотации, которую `_FLOAT_RE` не
матчит (нет десятичной точки). Ядро отвечало `WA` законно; ложным было
ожидание. Шум стал относительным (`x * (1 + 1e-13)`), ноль остаётся нулём,
регрессия закреплена тестом.

## Границы стенда

- **Живёт в `scripts/`, не в пакете.** Это инструмент разработки грейдера, а не
  функция продукта: в `stepik_grader` он не импортируется и в поставку не
  входит.
- **Не ходит в Stepik и ничего туда не отправляет.** Батч-отправка решений под
  живым аккаунтом — накрутка прогресса на учебной платформе: риск для аккаунта и
  для репутации проекта. Отправка одного решения студентом остаётся ручной
  операцией `core/stepik_client.submit_and_wait` и стендом не вызывается.
- **Задачи в репозитории — только со своими условиями.** Скачанное со Stepik
  живёт в `corpus/local/` (в `.gitignore`); наружу из такого прогона едут
  производные данные — какой вердикт разошёлся и на какой мутации, — но не
  тексты условий. Полное правило — [`corpus/README.md`](../../corpus/README.md).
- **В CI не включён.** Стенд запускается руками; прогон с мутацией `timeout`
  упирается в таймауты и медленнее юнит-тестов. Регрессии, которые он находит,
  переезжают в `tests/` обычными тестами — там им и место.
