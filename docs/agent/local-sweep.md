# Локальный сквозной прогон: инструкция

> Пошаговый сценарий для **локальной сессии** — на машине пользователя, где есть
> сеть до Stepik и его `secrets.json`. Из удалённой сессии этот прогон не
> выполняется: сетевой доступ к `stepik.org` там закрыт политикой окружения, а
> токен пользователя туда передавать нельзя.

Цель прогона — не «пройти курс», а **проверить грейдер на настоящих данных**:
собрать локальную базу задач и прогнать по ней все пользовательские подсистемы,
собрав список того, что сломалось. Курс уже пройден, решения существуют —
новых сочинять не нужно, они приезжают вместе с задачами.

Чем это дополняет прогонный корпус ([`../dev/corpus.md`](../dev/corpus.md)):
корпус проверяет **вердикт** на шести собственных задачах, этот прогон —
**все подсистемы** на сотнях реальных.

Чем от него отличается прогон по курсам
([`course-walkthrough.md`](course-walkthrough.md)): здесь база **уже собрана** и
по ней гоняются подсистемы, там база **создаётся** шаг за шагом — с решениями от
трёх ролей и сверкой вердикта с самим Stepik. Оба нужны, порядок такой: сначала
прогон по курсам наполняет базу и историю, затем этот прогон проходит по ней
подсистемами.

---

## Что понадобится

- Установленный пакет: `pip install -e ".[dev,lint]"` (extra `lint` нужен для
  проверки правил PEP-8; без него эта проверка пропускается с предупреждением).
- `secrets.json` с токеном Stepik в рабочей директории — как его получить,
  описано в [`../use/installation.md`](../use/installation.md).
- Свободное место под базу: сотни задач с тестами.
- Время: полный прогон по всем группам — часы, поэтому первые заходы делаются
  с `--limit`.

---

## Шаг 1. Проверить авторизацию

```bash
python -m stepik_grader.diagnostic_stepik
```

Диагностика показывает, валиден ли токен и виден ли API. Если нет — сначала
авторизация (мастер в загрузчике, пункт 8 меню или
[`../use/installation.md`](../use/installation.md)); без рабочего токена
следующий шаг не имеет смысла.

---

## Шаг 2. Собрать базу задач

```bash
# Сначала посмотреть, что вообще есть в курсе, ничего не скачивая:
python scripts/corpus_fetch.py --course <ID_КУРСА> --dry-run

# Пробный заход — двадцать задач:
python scripts/corpus_fetch.py --course <ID_КУРСА> --limit 20

# Полный сбор:
python scripts/corpus_fetch.py --course <ID_КУРСА>
```

Что делает скрипт: обходит курс (курс → секции → юниты → уроки → шаги),
отбирает шаги-задачи с кодом и скачивает каждый штатным загрузчиком. В папке
задачи оказываются условие (`task.md`), тесты (`tests/`), метаданные
(`meta.json`) и — если решение когда-то отправлялось — `solution.py` с принятым
кодом. Именно он станет эталоном на следующем шаге.

Идентификатор курса виден в его URL на Stepik (`stepik.org/course/<ID>/…`).

Альтернатива, если нужен точечный список, а не курс целиком: сложить URL шагов
в файл по одному в строке (пустые строки и `#`-комментарии игнорируются) и
позвать `--steps steps.txt`.

**Куда качается.** По умолчанию — `corpus/local/`, папка в `.gitignore`. Это не
случайность: условия и тесты чужого курса не должны попасть в публичный
репозиторий. Менять `--target` на путь внутри git-дерева — осознанное решение,
и последствия на вас.

**Скрипт только читает.** Единственные операции — GET к API и запись файлов.
Ничего на Stepik не отправляется.

---

## Шаг 3. Посмотреть, что собралось

```bash
python scripts/corpus_sweep.py --base corpus/local --inventory
```

Инвентарь печатает, сколько задач найдено и сколько готовы к прогону (есть и
тесты, и решение), а также перечисляет неполные: без тестов и без решения.
Задача без решения не пропадает молча — её видно в списке, и это нормальная
ситуация для шагов, которые не отправлялись.

---

## Шаг 4. Прогнать подсистемы

```bash
# Пробный заход на пяти задачах, чтобы оценить время:
python scripts/corpus_sweep.py --base corpus/local --limit 5

# Только ядро — самый ценный сигнал, самый быстрый прогон:
python scripts/corpus_sweep.py --base corpus/local --modules core

# Всё и по всей базе, с отчётом в файл:
python scripts/corpus_sweep.py --base corpus/local --output json > sweep.json
```

Четыре группы проверок (`--modules`, по умолчанию все):

| Группа | Что проверяет | Что означает находка |
|---|---|---|
| `core` | вердикт эталона (обязан быть `AC`) и каталог мутаций | ложный AC (приняли неверное) или ложный WA (завернули верное) |
| `learning` | запись истории, карточки «Подучить», экспорт прогресса | подсистема не собралась на реальных данных |
| `glossary` | карточка ошибки при RE, правила PEP-8, детектор концептов | студент увидит голый трейсбек без объяснения |
| `extras` | микробенчмарк, пошаговый трейс, кэш, статистика | подсистема падает на задаче определённого вида |

Полезные флаги: `--limit N` (взять не больше N задач), `--timeout` (таймаут
кейса, по умолчанию 2 с), `--report` (не падать при находках), `--work-dir`
(куда писать служебные файлы прогона).

**Побочные эффекты изолированы.** История, статистика и кэш пишутся во
временную рабочую директорию, а не в ваши `.grader_history.db` и
`.grader_stats.jsonl`: прогон не имеет права портить реальный прогресс. База
задач читается только на чтение, мутанты живут во временных файлах.

---

## Шаг 5. Разобрать находки

Порядок разбора — **сначала подозревай стенд, потом ядро**. Ожидания в каталоге
мутаций написаны человеком и могут не подходить конкретной задаче; ядро покрыто
тестами. Первый же прогон корпуса это подтвердил: расхождение оказалось ошибкой
в мутации, а не в грейдере.

Для каждой находки:

1. Воспроизвести точечно — `--limit 1` на этой задаче, нужная группа в
   `--modules`, а для вердиктов ещё и `corpus_run.py --mutation <ключ>`.
2. Посмотреть, что подсистема получила на вход и что вернула.
3. Если виноват стенд (неверное ожидание, неподходящая мутация) — правится
   каталог, и в докстринге фиксируется, почему ожидание было ложным.
4. Если виновато ядро — заводится issue с этим репро и метками по
   [CONTRIBUTING.md](../../CONTRIBUTING.md): `area/*`, `difficulty/*`, тип.
5. Починили — регрессия переезжает в `tests/` обычным тестом. Стенд ищет
   дефекты, а сторожит их набор тестов.

Виды находок в отчёте: `mismatch` — вердикт разошёлся с ожидаемым; `error` —
подсистема упала с исключением; `missing` — не хватило данных (нет эталона, нет
карточки для ошибки).

## Границы

- **Ничего не отправляется на Stepik.** Ни сбор базы, ни прогон не публикуют
  решений. Батч-отправка под живым аккаунтом — накрутка прогресса на учебной
  платформе: риск для аккаунта и для репутации проекта. Отправка одного решения
  остаётся ручной операцией пользователя.
- **Чужой контент не коммитится.** Условия и тесты курса живут в
  `corpus/local/` вне git. В репозиторий из прогона едут только производные
  данные: какая подсистема на какой задаче дала сбой. В публичный
  `corpus/tasks/` кладутся задачи только с собственными условиями — правило в
  [`../../corpus/README.md`](../../corpus/README.md).
- **Прогон не в CI.** Он требует сети, аккаунта и часов времени. В CI живут
  тесты, в том числе те, что выросли из находок.

## Готовность к фазе L: чего сейчас не хватает

Этот прогон — исполнение **фазы L** двухоконного аудита
([`environments.md`](environments.md)). Он выполняется **после того, как закрыты
кодовые issue аудита**, и служит финальной приёмкой: наполнить базу реальными
задачами курса и снять всё, что сломалось на настоящих данных.

**Кодовые — не все.** Ждать документационных issue незачем: прогон не читает
README, ADR и docstring, поэтому их состояние на его результат не влияет
физически. Ждать кодовые, наоборот, обязательно — иначе прогон выдаст заново то,
что уже разбирается, и настоящие находки утонут в известных.

Граница проходит по вопросу: **изменит ли фикс то, что продукт делает в прогоне**
— что напечатает грейдер, что покажет браузер, что ляжет в базу? Если да — issue
блокирует фазу L, даже когда правится «всего одна строка». Тексты ошибок, строки
интерфейса и локали — это **код**: пользователь видит их в прогоне. Docstring,
README, ADR и документы `docs/` — нет.

Чтобы приёмка не выродилась в «прогнали и ничего не нашли», подготовка делается
**заранее и в облачном окне**. Сегодня в стенде три дыры — каждая закрывается до
того, как владелец сядет за локальный прогон:

| Дыра | Почему это важно для фазы L |
|---|---|
| **Нет группы `ai`** — `MODULE_KEYS` покрывает `core`, `learning`, `glossary`, `extras` | подсказки AI (`core/ai_hints.py`, `core/ai_grounding.py`) не прогоняются ничем: ни лимит `ai_max_hints`, ни попадание карточек глоссария в промпт, ни поведение без согласия, с отозванным согласием и без настроенного провайдера. Полный цикл «решил → упал → получил объяснение» сейчас проверяется только вручную |
| **Нет сценария «полный цикл на одной задаче»** — группы гоняются по отдельности | облако и так проверяет узлы. Фаза L существует ради **цепочки**: скачал → решил → проверил → история записалась → «Прогресс» показал верное → «Подучить» дал рекомендацию → экспорт собрался. Разрывы живут на стыках, а стыки сейчас не прогоняются |
| **Нет режима «только чтение настоящей базы»** — прогон намеренно пишет во временную папку | это правильно для прогона, но отдельно нужен отчёт по **реальной** истории владельца (месяцы прогонов): именно на ней видно, врут ли агрегаты «Прогресса», серия и бейджи. Без записи, только чтение |

Плюс **фаза 0** — короткий слепок реальности, снимаемый до облачных волн: формы
накопленной истории (числа и структура, не содержимое), реальные имена папок
задач курса, инвентарь курса `--dry-run`, версии ОС и Python. По нему строятся
фикстуры облачных волн: фикстура по настоящим объёмам ловит то, что
синтетическая пропускает.

**Порядок такой и не другой.** Прогон до закрытия issue даст лавину находок,
которые и так известны аудиту, и утопит в них новое. Прогон после закрытия
отвечает на единственный вопрос, ради которого он и нужен: **осталось ли что-то,
чего не видно ни из облака, ни из тестов.**

## Что проверено, а что нет

Честно о степени готовности, чтобы локальная сессия знала, где ждать сюрпризов:

- `corpus_sweep.py` — прогонялся целиком на шести задачах публичного корпуса,
  все четыре группы отработали без находок. Логика покрыта тестами.
- `corpus_fetch.py` и `fetch_section_units` — покрыты тестами **на моках**.
  Живьём против Stepik API не проверялись: в удалённой сессии, где они писались,
  доступ к `stepik.org` закрыт политикой окружения. Первый реальный запуск
  делайте с `--dry-run`, затем с `--limit`, и только потом на весь курс.
